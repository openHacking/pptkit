# Experimental SVG importer

This private workspace package is not a published or stable API. `importSimpleSvg` is an all-or-nothing experiment for a small viewport-contained subset of SVG rectangle, circle and ellipse geometry. Explicit pixel viewport dimensions map at 96 px/in to points. An optional numeric `viewBox` supports `none` and all nine alignments with `meet` or `slice`; shapes crossing the viewBox or mapped viewport reject rather than approximating clipping. Shapes and nested groups accept bounded lists of `translate` and `scale`, including nonuniform and negative scale, and root/group literal fill inheritance. Their geometry is baked into axis-aligned Core boxes; source transform lists and group structure are not retained. When groups occur, the editable result includes a `flattened-groups` warning. Unsupported markup returns diagnostics and no editable objects; malformed or over-limit input throws `SvgImportError`. It does not fetch, execute, rasterize or sanitize external SVG for another consumer. Full limits and outstanding gates are in the [SVG import plan](../../docs/planning/svg-import-plan.md).

Root, group and shape elements accept literal `stroke` and nonnegative numeric `stroke-width`, with inherited values defaulting to no stroke and one user unit respectively. Circle and ellipse visible strokes require uniform combined shape/group and viewport scaling, and their full bounds must remain inside both viewBox and viewport. Strokes are solid and centered; zero width is invisible. Visible rectangle strokes, dash patterns and other stroke attributes are unsupported. A [limited PowerPoint observation](../../docs/testing/svg-stroke-powerpoint-evidence.json) covers three stroke samples and one interactive move/save/reopen; it does not establish complete native visual parity.

Explicit `inherit` is accepted for fill, stroke, stroke width, fill/stroke opacity, line cap and line join, as well as the corresponding omitted-property inheritance. The root uses the SVG initial values when it explicitly inherits. Other CSS-wide keywords and stylesheet rules remain unsupported.

Fill and stroke colors accept `#RGB`, `#RGBA`, `#RRGGBB`, `#RRGGBBAA`, `transparent`, the 148 CSS named sRGB colors, or `rgb()` / `rgba()` with integer channels in 0–255. Both comma-separated and space-separated forms are supported; optional alpha is a bounded 0–1 number or 0–100 percentage, separated by a comma in legacy syntax or a slash in space syntax. Names and functions are case-insensitive and outer XML whitespace is ignored. `none` is also supported. Color alpha maps to paint opacity, independently for fill and stroke. Root, group and element `fill-opacity` and `stroke-opacity` inherit separately; bounded numeric 0–1 and percentage 0–100 values multiply the corresponding color alpha. PPTX stores opacity in increments of 1/100,000. Percentage or fractional RGB channels, system colors, color references and CSS expressions are rejected rather than approximated. Group `opacity`, which composites an entire group, remains unsupported.

A [limited PowerPoint observation](../../docs/testing/svg-opacity-powerpoint-evidence.json) checks three transparent fill/stroke samples and one move/save/reopen. Its screen samples show color trends and reopening consistency, not exact sRGB parity or transparency editing.

Single-subpath linear `path`, `polyline` and `polygon` elements can map to editable Core connectors. Paths support `M`, `L`, `H`, `V` and `Z` commands, including lowercase relative forms and implicit coordinate repetitions; subsequent `M` coordinate pairs act as `L` commands. The geometry must have no fill, a positive solid stroke, and effective round joins; open paths and polylines also need round caps. These properties may be inherited from root or groups, with SVG's default butt cap and miter join when unspecified. Combined viewport and element scaling must be uniform, and the entire stroke must remain inside the viewport and viewBox. Geometry is limited to 4,096 characters and 256 points. A `path-converted` warning identifies loss of the original SVG element and commands. Closed geometry becomes a connector with matching endpoints and explicit closure. Filled polygons, curves, zero-length segments, multiple subpaths and other path styles are rejected. Browser sampling and PPTX structure are tested; [two PowerPoint path samples](../../docs/testing/svg-path-powerpoint-evidence.json) were observed and one moved, saved and reopened, but full native visual parity remains unverified.

`createSvgRasterFallback` is a separate, explicit choice: supply a nonempty caller-owned `Uint8Array` (maximum 20,000,000 bytes), PNG or JPEG MIME type, asset ID, source ID, and positive viewport width and height in Core points (at most 1,000,000 each). It copies the bytes and returns a Core asset and a stretched image element, plus a `rasterized` warning. The caller must register the asset and add the element to the presentation. The function does not decode or validate image bytes, prove the MIME type or source identity, render SVG, or check correspondence and fidelity; callers must supply trusted, correctly rendered bytes. Source identity is caller metadata, not a digest. A raster image remains editable as an image, but its constituent SVG objects are not editable. Import errors and unsupported results do not automatically invoke fallback.

`importSvgWithFallback(source, { sourceId, fallback? })` combines these operations only when the caller explicitly supplies `fallback` (the same raster fields except `sourceId`). An editable result keeps import warnings and the caller identity. Without a fallback, unsupported markup returns its issues and malformed or over-limit input returns `parse-error`; invalid non-string input remains an exception. With a fallback, those failure outcomes become `raster-fallback`, with the original outcome in `reason` and the rasterization warning in `issue`. Fallback fields are validated only when used; malformed or missing raster fields then throw. This function does not verify raster content. Exporting invalid caller bytes produces `asset-read-failed` and `image-omitted` warnings and no image, so callers must inspect export warnings rather than treating the fallback decision as proof of successful packaging.

Run `pnpm --filter @pptkit/svg-parser test`. Bundles are experimental and not published; general paths, text, rotation, skew, CSS styles and public release integration are not yet implemented.
