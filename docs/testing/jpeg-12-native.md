# 12-bit JPEG first-open observation

On macOS 26.5 (25F71), PowerPoint 16.104 opened the generated `probe.pptx` without a repair prompt. Its edit view and first slideshow displayed both the named 12-bit sequential and progressive JPEGs alongside a PNG control. All three displayed the same broad brown-to-blue arrangement. The two JPEG images agreed within 3 RGB levels at nine sampled slideshow pixels; the PNG differed by at most 35 levels at those samples. The source JPEGs are lossy and the control is the original RGB input, so equality is not expected. This is a first-open observation of two 3×2 images stretched into square frames, not a general color-fidelity, editability or save/reopen result. The UI action was observed through the computer interface; the oracle does not independently witness it.

The local artifacts are `.tmp/native-jpeg-12/probe.pptx` (SHA-256 `19c3013b319a40d04232e507b3cf301c9ef93fe3f0275ee9e7adbc2798d1bceb`) and `.tmp/native-jpeg-12/first.png` (`cf4f7a5e25b5a874ea230306b2877c54e7d24daa2e8cd335e3b2cf3d7a432816`). The PNG control has SHA-256 `af203fd8104f6973067688046c4fc595ccdfc4e1dc0ac31d83143f0fc39dbe65`. The JPEG hashes and encoder provenance are recorded in the [JPEG test](../../packages/pptx-parser/test/picture-save-jpeg-validation.test.mjs). The [oracle](../../scripts/research/oracles/jpeg-12-native.py) follows each slide image relationship to the exact supplied bytes, checks nine screenshot samples and two color landmarks, and rejects three controls that independently blank each displayed image. It does not compare all pixels or validate PowerPoint rendering beyond this screenshot. These local `.tmp` artifacts are not distributed.

To reproduce the package with Pillow and the built packages:

```sh
mkdir -p .tmp/native-jpeg-12-repro
python3 -c 'from PIL import Image; Image.open("tests/fixtures/exif-orientation6.jpg").convert("RGB").save(".tmp/native-jpeg-12-repro/control.png")'
node scripts/prepare-jpeg-12-native.mjs .tmp/native-jpeg-12-repro
```

The reproduced package matched the observed package byte for byte. `python3 scripts/research/oracles/jpeg-12-native.py` checks the retained original artifacts.

## Chromium SVG preview difference

PPTKit imported that native crop and generated SVG containing the exact three JPEG byte streams. In headless Chromium 149.0.7827.55 on the same Mac, all three SVG image regions were white, unlike the PowerPoint slideshow. Three independent `HTMLImageElement.decode()` calls resolved and reported 3×2 dimensions, but drawing each decoded image to canvas yielded transparent `[0,0,0,0]` at its first pixel. An 8-bit JPEG control decoded to an opaque pixel. External requests were blocked, and the SVG preserved the source bytes. This demonstrates that a successful browser decode promise and dimensions do not prove visible pixels for these two named 12-bit files; it does not establish all 12-bit JPEGs or browser versions.

The renderer now reports `jpeg-preview-precision-unverified` for directly embedded JPEG byte assets whose bounded header prefix declares non-8-bit precision, while retaining the source URL. It does not decode or convert the image; a caller may supply a compatible conversion through its resolver. The [probe script](../../scripts/research/inspect-jpeg-12-crop-preview.mjs) records canvas results, warnings and SVG/PNG hashes; the [independent oracle](../../scripts/research/oracles/jpeg-12-preview.py) checks the report, exact embedded JPEG bytes and white browser versus visible PowerPoint samples. Local `crop-preview.svg` and `crop-preview.png` hash to `0c7ab048ed75662d55a6fdec3f001f2206075fdadfad36c1c263d60df7219306` and `e6a631c637299620104885e6a7a2aaa23cc9e80ee91d2a3e07242683458c3a40`; the generated report hashes to `e42d6dcbc6aa5c06192becd059f22abd3af8a5cf3b5e2e5e5778453bbc015b8f`. These `.tmp` artifacts are local; absence of the warning cannot certify a viewer can decode or display an image.

## Explicit resolver conversion experiment

For these two files, libjpeg-turbo 3.1.3 `djpeg -strict` decoded the 12-bit JPEGs to 3×2 PPM images with 0–4095 samples. Pillow converted those samples to 8-bit PNG; the [oracle](../../scripts/research/oracles/jpeg-12-resolved-preview.py) independently checks all 18 channel values against rounded 12-to-8-bit scaling. A caller-owned resolver matched the captured JPEG bytes by SHA-256 and returned the corresponding PNG data URL. The imported PPTX was not modified. Chromium decoded all three returned images to opaque pixels and displayed the original crop geometry, including white space outside the cropped frame.

The [probe](../../scripts/research/inspect-jpeg-12-resolved-preview.mjs) records the actual source/PNG hashes, SVG, image decode results and blocked external requests. Across 27 sample points, the maximum per-channel difference from the PowerPoint screenshot was 25; this is an observed difference, not pixel equality or a general color-fidelity guarantee. Three independently blanked image controls are rejected. The two decoded PPMs have SHA-256 `66b3dc997f382b46c18ace6e108806f490f3aa470f26a0507cd37f710a68ab63`, and both PNGs `9a97dc59c82a5c8a85aaf799625d63b9f97849d53f316227c8ebbfed5862a381`. The resolved SVG, screenshot and report hash to `dfab8dd32a4b74a52209f02889b58b5e62b1ba1fe06a43ee61f96a620c31e8a5`, `53fb6714b04db1f3f7fb50294d949ac3a1d6b2c18387638acbf9006fc9fd6bfc` and `24d6379f349cbda536078e5253f80ff3595b9c4cd20c902f987fb87e4702eadb`. These artifacts remain local.

To repeat the conversion with those installed research tools and retained crop file:

```sh

python3 -c 'from PIL import Image; Image.open(".tmp/native-jpeg-12/decoded-sequential.ppm").save(".tmp/native-jpeg-12/decoded-sequential.png"); Image.open(".tmp/native-jpeg-12/decoded12.ppm").save(".tmp/native-jpeg-12/decoded-progressive.png")'

python3 scripts/research/oracles/jpeg-12-resolved-preview.py
```

This is a specific caller-managed conversion, not a built-in converter or universal fallback. It discards extra sample precision; metadata, ICC/color management, failure handling, other viewers and other JPEGs were not verified.
