# Authored native sections: PowerPoint observation

On macOS 26.5 (25F71), Microsoft PowerPoint 16.104 opened [this PPTKit-authored sample](../../tests/fixtures/authored-native-sections.pptx) without a visible repair prompt. Its normal-view thumbnail pane reported Introduction (1 slide), Empty (0 slides), and Conclusion (1 slide), in that order. The second slide was hidden. After Save As and closing and reopening the [saved copy](../../tests/fixtures/authored-native-sections-powerpoint.pptx), the same section names, order and counts appeared in the pane. This is one manual observation; section editing in PowerPoint and other applications are not established by it.

The two retained files have SHA-256 hashes `194f12063b331f75cc262e1421ca16448b7bddca9527c51259b8d34a2f311344` and `c9917f74ae175e53bb383442b56536b36d46400d58dd557bba305881cc819189`. [A registered integration test](../../scripts/import-content-parity.test.mjs) regenerates the first file through public authoring and export APIs, checks both hashes, and compares Core inspection with an independent Python ZIP/XML reader. Both files retain the three GUIDs, ordered memberships `[256]`, `[]`, `[257]`, and names. Separate [parser tests](../../packages/pptx-parser/test/sections.test.mjs) exercise unknown nested section and presentation extensions as uninterpreted descriptors in both dialects. The observed sample does not contain unknown extensions.

The legacy slide label remains independent of native collection authoring. Default import projects member names to labels; the explicit collection projection additionally maps section membership into Core. No-op source save and preservation-aware structural editing remain separate contracts.
