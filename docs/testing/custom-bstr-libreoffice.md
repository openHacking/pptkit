# Custom `bstr` strings: LibreOfficeDev headless observation

A synthetic source was built from a hash-verified PPTKit-created package by replacing its custom-property part with four `bstr` samples: Unicode text, an empty string, a literal escape-like sequence and emoji. PPTKit edited all four; an unchanged branch is the control. Independent ZIP and byte checks found that only the four approved value texts changed in the custom part, preserving source tags and IDs.

LibreOfficeDev **26.8.0.0.alpha0**, on macOS 26.5 arm64, headlessly resaved each branch three times. The XML inventories retained the four respective text values in both branches, including the empty value and escaped literal forms. The application converted `bstr` to `lpwstr`, reordered entries, reassigned IDs, and added `PresentationFormat` and `Slides`. Subsequent resaves retained that inventory. This observation is limited to the XML values in these samples; it does not prove interactive display or complete type/identity preservation.

The [record](custom-bstr-libreoffice-evidence.json) contains hashes, exact inventories and process logs. Check retained files with `python3 scripts/research/verify-custom-bstr-libreoffice.py` and reproduce in the recorded environment with `python3 scripts/research/custom-bstr-libreoffice.py`. Artifacts under `.tmp` are local, not a portable fixture corpus. PowerPoint, interactive property editing, repair prompts and other strings remain untested.
