# Four timing specimens: playback observation protocol

This protocol prepares ADV-06.2.1.2; its preliminary observations below do not admit an effect. The [hand-authored fixture](../../scripts/research/native-timing-fixture.mjs) is research input, not a certified Office animation preset. The four pages have one named rectangular shape each, `p:cNvPr id="2"`, with authored box `(100, 100, 240, 80)` in presentation units. Each timing tree targets that shape, contains `clickEffect`, a 500 ms behavior with `fill="hold"`, an indefinite start condition and slide `onNext`/`onPrev` conditions. These are source declarations, not proof of click behavior.

The recorded source package SHA-256 is `548fd061927d5d1a68173e87fe85c72f19dce977ae2aa5754a2644a560b2fb03`. It is the four-page `source.pptx` in the local directory recorded in [the evidence manifest](animation-mapping-evidence.json); the file is not distributed. Generate a fresh specimen with `node scripts/inspect-animation-mapping.mjs [soffice-executable]` after building. Record the **new** source hash and retain that exact input: package bytes and hashes may differ. The script also overwrites the manifest, so preserve the existing record before running it. Independently inspect page/target identity and timing XML before comparing observations.

| Page and target | Source declaration | Expected states to test, not observed results | Coordinate question |
| --- | --- | --- | --- |
| 1 `fade-in` | `animEffect transition="in" filter="fade"` | Before trigger hidden; during transition partially visible; after visible. | Same authored box throughout. |
| 2 `spin` | `animRot by="21600000"`, attribute `r` | Before trigger unrotated; during transition rotates; after a full turn looks unrotated. Direction, pivot and retained rotation require observation. | Rotation about the application's interpreted pivot; 60,000 units per degree. |
| 3 `fade-out` | `animEffect transition="out" filter="fade"` | Before trigger visible; during transition partially visible; after hidden. | Same authored box throughout. |
| 4 `line-path` | `animMotion origin="layout" path="M 0 0 L 0.25 0 E" pathEditMode="relative"` | Before trigger at authored position; during transition moves; after stays at interpreted endpoint. | Test whether 0.25 represents a quarter of slide width, another coordinate basis, or is ignored; do not infer units from XML alone. |

All middle states are hypotheses: a 500 ms effect may require frame-by-frame inspection to distinguish them from a jump. A full rotation's first and last frame cannot prove that rotation happened. The static PDF from a save/reopen cannot establish any of these states.

## Capture procedure

1. Use separate untouched copies of the same hashed source for PowerPoint 16.104 on macOS 26.5 and LibreOfficeDev 26.8.0.0.alpha0 on macOS. Record exact installed versions, OS, display scale, slide-show settings and any opening or repair prompt; if an application or version is unavailable, mark it `untested` and record the actual environment separately. Do not substitute the existing headless output for interactive playback.
2. Record the complete slide show from before entering each page through its trigger, animation and final state, including the physical click or key action and the application window. Record frame rate, resolution, timing and the original recording hash. Capture a static ruler/reference with slide bounds and the original shape box; preserve an unaltered copy of each video. A screen recording may drop frames and is not a precise clock.
3. For each page record the initial visible state before any trigger, each click/key and its count, intermediate frames and final state. Measure shape bounds, opacity or angle where discernible, and path endpoint relative to the slide and shape. Record uncertainty and missing frames; don't infer intermediate visibility from first and last frames. Test additional click, previous/next and re-entry separately and record actual order and reset behavior. Capture raw frame timestamps and extracted image hashes; distinguish application events from recording frames.
4. On a new copy, use the application's animation UI to change duration, then edit the target text without deleting the shape. Record the exact UI actions and values. Save to a new path, close, reopen that path and repeat playback. Record whether each setting remained editable, the target identity and timing/geometry XML before and after, file hashes and any warnings. Do not treat a saved value as proof of playback.
5. Keep source, recordings, extracted frames and saved copies with a manifest linking page, application, operation and SHA-256. Independently inspect package relationships and timing trees; record application rewrites and compare target IDs after resolving them to shapes. If timing, visibility, path or the UI cannot be measured, report `untested` or `inconclusive`, not pass. Preserve negative observations and the unmodified baseline.

## Preliminary PowerPoint observation

On macOS 26.5 (25F71), PowerPoint 16.104 opened the source with the hash above, without an observed repair prompt; the slide thumbnails indicated animations. A manual slideshow inspection used the right-arrow key once per effect and once to advance to the next page. Screen snapshots were observed in the automation session but were not retained as independent artifacts; this is exploratory evidence, not the recording and edit/reopen acceptance required by ADV-06.2.1.2.

| Page | Observed in this session | Remaining uncertainty |
| --- | --- | --- |
| fade-in | The black text was already visible before the first right-arrow; the next snapshot after the key showed lighter text and a later snapshot showed black text again. | The initial-hidden hypothesis above does not hold for this opening. No frame-timed recording establishes the full fade or exact duration. |
| spin | The text began upright; a snapshot after the first key showed it rotated, and a later snapshot showed it upright again. | Direction, pivot and exact angle/time were not measured. |

A snapshot during a transition is not a calibrated clock, and the transient images cannot substitute for retained video or independent pixel analysis. ## PowerPoint fade-in edit and reopen

On a separate copy of the same source, PowerPoint 16.104's animation pane identified the first effect as custom and its start as unknown. Its timing panel displayed 0.5 seconds; selecting 2 seconds and appending ` edited` to the target text were followed by save, close and reopening the exact copy. On the reopened first slide the edited text was visible before triggering; a right-arrow produced a lighter intermediate snapshot and the text later appeared black. This was a manual UI observation without a retained video or calibrated timing. Other effects were not edited or replayed in this experiment.

The local saved file `.tmp/animation-native/run-UKB5dV/powerpoint-edit.pptx` has SHA-256 `051fbc51167f3d974af019dcf7474cc0fc5173d970220044f75b607801617615`. The independent [ZIP/XML oracle](../../scripts/research/oracles/animation-powerpoint-edit.py) checks the source and saved package: slide 1 still targets shape ID 2, stores `animEffect` fade-in with duration 2000 ms, and contains the edited text split over three runs; slides 2–4 retain their named targets, behavior parameters and 500 ms durations. The oracle rejects the unedited source and separately mutated duration, target and text packages. It does not prove the UI actions, complete package equivalence, playback duration, or preservation of arbitrary timing trees. This first experiment did not edit the other effects; no recording, LibreOffice GUI test or full re-entry matrix is supplied, and ADV-06.2.1.2 remains open.

## Four edited effects in PowerPoint

From that first edited file, a new copy was saved and the other three custom effects were each changed from 0.5 to 2 seconds in the timing pane, with their target text replaced by the original name plus ` edited`. An accidental extra text object was undone before saving. PowerPoint 16.104 on macOS 26.5 saved, closed and reopened the new copy at `.tmp/animation-native/run-UKB5dV/powerpoint-all-edits.pptx`, SHA-256 `0c5d1906e945002c4b9f58dda1ca7a2271983b3f49b184dab69cd28cf478b3fb`. The first edited file remains separate. No repair prompt was observed.

Manual slideshow inspection used one right-arrow to trigger each effect and another to advance. Snapshots showed the edited fade-in text lighter after triggering, the edited spin rotated, and the edited path text moved right and later reached its endpoint; fade-out started visible, but the transient post-trigger snapshot did not independently establish its final state in this run. Images were not retained, and no duration, direction, pixel positions or complete re-entry sequence was measured. These are observations rather than a reusable video record.

Run the oracle with the source and new file plus `--all`: it checks one shape and behavior per slide, their named IDs and edited text, all four 2000 ms values and their original effect attributes/targets. It compares the full expanded-name timing trees, attributes, text and child order after changing only the expected source durations, ignoring indentation. Both the single-edit and four-edit files pass; this is semantic XML comparison, not byte equality. It rejected the previous partial-edit file and independently altered packages (duration, target, text, path, event, restart, fill and path-edit mode). The checks establish those package fields, not UI provenance or playback fidelity.

A subsequent manual check of the four-edit copy entered slide 3 directly. After one right-arrow the edited text disappeared; a left-arrow on the same slide restored it. After another right-arrow and a second right-arrow to slide 4, a left-arrow returned to slide 3 with the text still absent; one further left-arrow restored it. Going back to slide 2 and then forward through its effect returned to slide 3 with text visible. These transient UI observations have no retained video or calibrated timing. LibreOffice GUI, retained video, other effects' complete terminal states/re-entry and broader samples remain open; the playback task and parent stay unchecked.
