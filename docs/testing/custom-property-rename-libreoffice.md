# Source-preserved custom-property rename: LibreOfficeDev headless observation

One PPTKit-authored presentation served as an unchanged control. The `scalar-and-name-v2` source-preserving profile renamed the text property from `Text` to `Renamed 中文` and changed its value, alongside four other scalar values. Independent ZIP comparison found only `docProps/custom.xml` changed before application conversion. LibreOfficeDev 26.8.0.0.alpha0 headlessly resaved the control and edited files separately for three rounds; the [manifest](custom-property-rename-libreoffice-evidence.json) records hashes, logs and independent ZIP/XML property inventories.

The renamed property and its edited value remained paired through all three resaves, while the control retained its original name and value. On the first resave both files reordered and renumbered properties, converted `i4` integers to `r8`, changed boolean spellings, shortened UTC dates, and added `PresentationFormat` and `Slides`; the observed property lists remained stable for the next two rounds. These are observations from one fixture and one headless application version. They do not establish interactive UI, repair prompts, visual fidelity, general interoperability or PowerPoint behavior.

On the machine retaining the `.tmp` files, `python3 scripts/research/verify-custom-property-rename-libreoffice.py` verifies runner and reader hashes, eight PPTX hashes, inventories, paired round order and the source-part difference. The corresponding runner uses the currently built packages and an earlier retained authored sample; its manifest does not pin all build dependencies. Portable [producer fixture tests](../../packages/pptx-parser/test/custom-properties-producer.test.mjs) additionally exercise renaming and value edits after actual LibreOfficeDev resaves without changing other source parts.
