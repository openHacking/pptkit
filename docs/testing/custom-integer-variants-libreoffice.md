# Custom integer variants: LibreOfficeDev headless observation

A synthetic source package was constructed from the hash-verified PPTKit-created custom-property sample by replacing its custom part with ten named variants: `i1`, `i2`, `i4`, `int`, `i8`, `ui1`, `ui2`, `ui4`, `uint` and `ui8`. Each starts at zero. The edited branch uses PPTKit source preservation to replace them with values 1–10; an unchanged branch is the control. An independent comparison found identical ZIP entry sets and exactly one changed part; within it, only the ten value texts changed and the source tags and IDs remained intact.

LibreOfficeDev **26.8.0.0.alpha0**, on macOS 26.5 arm64, headlessly resaved each branch three times. After the first save, both branches retained only `i1`, `i2`, `i4` and `int`, all rewritten to `r8` with reassigned IDs. The other six variants (`i8`, `ui1`, `ui2`, `ui4`, `uint`, `ui8`) were absent from both outputs. The four retained values remained consistent with their respective branches through the following two resaves; the application also added `PresentationFormat` and `Slides` properties. This is a loss observation for this sample, not proof about all values or applications.

The [record](custom-integer-variants-libreoffice-evidence.json) contains hashes, exact inventories and process logs. Check retained files with `python3 scripts/research/verify-custom-integer-variants-libreoffice.py` and reproduce in the recorded environment with `python3 scripts/research/custom-integer-variants-libreoffice.py`. Artifacts under `.tmp` are local, not a portable fixture corpus. PowerPoint, repair prompts, interactive property editing and boundary values remain untested.
