# Tab-stop PDF observation

The retained [evidence](tab-stops-libreoffice-evidence.json) covers one generated four-slide deck, plus a same-run variant and a variant with explicit tab lists removed. Each slide has three strings and a 280 pt tab stop relative to a 60 pt text-box left edge, with a vertical guide at 340 pt. The four slides request left, center, right and decimal alignment. The generated source uses two text runs around the tab; the same-run variant merges them without changing the text. The no-stops variant keeps the two runs but removes the lists.

A separate [PowerPoint shape-text observation](tab-shape-powerpoint-evidence.json) covers 12 named no-wrap samples on four slides, with an independently measured first-open PDF and three Save As/close/reopen rounds. Each saved package retains all sample text, fill and tab declarations; the first page was observed after each reopen. `python3 scripts/research/verify-native-shape-tabs.py` checks the source, saved XML, PDF coordinates and capture hashes. A separate [Chromium SVG comparison](tab-svg-shape-browser-powerpoint-evidence.json) checks matching shape fills, run weights, source text and prefix/suffix edges: maximum difference is 0.251 pt across these samples. `node scripts/research/verify-svg-shape-tab-powerpoint.mjs` checks the dependencies and recorded arithmetic, while [the producer](../../scripts/inspect-svg-shape-tab-powerpoint.mjs) performs a live comparison. A separate [third-reopen PDF comparison](tab-shape-reopened-powerpoint-evidence.json) checks all 12 word positions, tab anchors and shape fills against the first-open print; `python3 scripts/research/verify-shape-tabs-reopened.py` repeats the comparison. A separate [native shape-text edit observation](tab-shape-native-edit-powerpoint-evidence.json) appends one character, saves and reopens it, and compares its print and all 12 saved sample declarations; `python3 scripts/research/verify-shape-tab-native-edit.py` checks the retained evidence. Other shape editing and rotated shapes were not tested; screenshot/AX hashes do not independently prove provenance.

A [mixed-size shape-text observation](tab-shape-mixed-size-powerpoint-evidence.json) checks the first-open PowerPoint print of 12 Arial samples. Their anchors are within 0.5 scaled PDF pt of the guide; PowerPoint baselines differ by at most 0.84 presentation pt from the revised mixed-size SVG baseline estimate; the previous 0.8-em estimate was 3.16–6.93 pt higher. A separate [Chromium comparison](tab-svg-shape-mixed-size-powerpoint-evidence.json) checks the 44 suffix characters: the maximum horizontal edge difference is 0.596 pt and baseline difference 0.838 pt. A [three-round PowerPoint save/reopen observation](tab-shape-mixed-size-three-reopen-powerpoint-evidence.json) checks all 12 saved texts, sizes, fills and tab declarations in each round and compares four-page prints after rounds one and three. Only the first-page windows were captured; native edits and other-font parity remain unverified. `python3 scripts/research/verify-shape-mixed-size-powerpoint.py` rechecks the retained measurements.

A [Chinese shape-text observation](tab-cjk-shape-powerpoint-evidence.json) and [Chromium comparison](tab-svg-cjk-shape-powerpoint-evidence.json) cover 12 first-open samples in Hiragino Sans GB. Across 32 suffix characters, maximum horizontal and baseline differences are 0.331 pt and 0.247 pt. Browser tests additionally exercise Japanese and Korean script anchoring, but their native rendering, all editing and save/reopen are unverified. `node scripts/research/verify-svg-cjk-shape-powerpoint.mjs` verifies retained evidence and font/build bindings.

`python3 scripts/research/verify-shape-tab-source.py` also compares the 12 named shape text bodies and transforms with the retained PowerPoint text-box source, verifies the shape fill, and binds both source hashes. Its companion test changes text, geometry and fill while recomputing the package hash to check the comparison itself. This establishes input equivalence, distinct from the shape PDF observation above.

For this specific LibreOfficeDev headless PDF conversion, every selected word starts at approximately 131.981 pt in all three variants and all four alignments. Thus these artifacts do not demonstrate that LibreOffice applied the declared stops; changing the run boundary did not alter the observation. PDF word boxes and the expected source XML are checked against retained artifact hashes by `python3 scripts/research/verify-tab-stops.py`. The [producer](../../scripts/research/probe-tab-stops.py) and [deck generator](../../scripts/prepare-native-tab-stops.mjs) are also hashed. The evidence verifier requires the retained `.tmp/native-tab-stops` artifacts.

This is one application/version and one headless conversion per variant. It is not evidence of PowerPoint behavior, visual equality, native editing or save/reopen stability. The guide indicates an expected coordinate derived from the source declaration, not a measured claim about an application's layout. A native PowerPoint control and independent save/reopen observations remain necessary.

A separate [attribute isolation](tab-stop-indent-libreoffice-evidence.json) starts from the same PPTX and changes exactly one property per variant. Removing `indent="-0"` from the affected paragraph makes LibreOffice place the samples at the requested left/center/right/decimal stops; removing `marL`, `algn` or `buNone`, or changing `-0` to `0`, leaves the initial positions unchanged. `python3 scripts/research/verify-tab-stop-indent.py` checks the complete package content, permitted XML change and measured PDF words. This isolates the behavior for the tested zero-indent sample; it does not establish behavior for nonzero indentation or other applications. Omitting the explicit zero in production could change inherited paragraph formatting, so the exporter preserves it and warns for the observed combination.

Separate [synthetic ODF controls](tab-stop-paragraph-libreoffice-evidence.json) varied paragraph left margin and first-line indent while keeping the text and tab declarations fixed. In the tested conversion, a 36 pt left margin shifted the tab-aligned words by 36 pt; an 18 pt hanging indent changed the prefix position by −18 pt but left the tab-aligned words at the same positions. The four alignments were checked. `python3 scripts/research/verify-tab-stop-paragraph.py` verifies ODF controls, unchanged non-control content and retained PDF geometry. These are not PowerPoint controls, PPTX edit/save tests, or proof for untested indentation cases.

The [browser comparison](tab-stop-browser-libreoffice-evidence.json) measures all 48 combinations of those four paragraph controls, four alignments and three strings. The ODF source names Arial, but the PDF identifies its rendered samples as Liberation Sans regular/bold. Chromium registered same-PostScript-name Liberation font candidates from the local LibreOffice bundle; CDP confirmed those custom faces on matching regular/bold controls. HarfBuzz advances from the candidate files differ from PDF word widths by at most 0.121 pt, and browser Layout right edges differ from PDF word edges by at most 0.146 pt. This is evidence of named, metric-compatible candidates, not proof that the PDF embeds byte-identical font files. `node scripts/research/verify-tab-cross-app.mjs` rechecks retained source/PDF controls, font file hashes, HarfBuzz and recorded comparison arithmetic; rerunning [the comparison](../../scripts/inspect-tab-stops-cross-app.mjs) performs a new live Chromium measurement. The comparison is limited to those samples and does not establish PowerPoint behavior, live native editing or general wrapping/bidi fidelity.

The separate [narrow-frame controls](tab-stop-wrap-libreoffice-evidence.json) compare wrapping at 150 pt with a 300 pt fitting frame, a 150 pt no-wrap frame, and ordinary text without a tab. In this LibreOfficeDev conversion, the tested tab-aligned words that exceed the narrow frame move as whole words to the next line; the fitting right-aligned samples remain on their original line. The ordinary-text control also wraps. `python3 scripts/research/verify-tab-stop-wrap.py` checks the ODF declarations, artifact hashes and measured PDF word boxes. A [36-case comparison](tab-stop-wrap-browser-libreoffice-evidence.json) checks those tabbed samples against live Chromium measurements using named Liberation font candidates; breaks agree and the largest right-edge difference is 0.161 pt. `node scripts/research/verify-tab-wrap-cross-app.mjs` rechecks the recorded comparison and dependencies, while [the producer](../../scripts/inspect-tab-wrap-cross-app.mjs) runs a new browser comparison. These observations cover only the recorded samples and do not establish PowerPoint behavior or native save/reopen stability.

[Multiword controls](tab-stop-multiword-libreoffice-evidence.json) append `WORD` to each sample in the fitting, narrow and no-wrap ODF variants. The selected left, center and decimal pages produce 27 observations; right-aligned samples overlap their prefixes and are excluded. The [Chromium comparison](tab-stop-multiword-browser-libreoffice-evidence.json) agrees on line counts and has a maximum right-edge difference of 0.263 pt. The verifiers `python3 scripts/research/verify-tab-stop-multiword.py` and `node scripts/research/verify-tab-multiword-cross-app.mjs` recheck retained inputs, PDF geometry, font candidates and recorded arithmetic. These controls do not cover arbitrary whitespace, scripts or PowerPoint wrapping.

A separate [PowerPoint observation](tab-stop-powerpoint-evidence.json) opened a fresh four-slide PPTX, recorded all four windows, and printed a scaled A4 PDF. In the 12 recorded samples, the appropriate left edge, center, right edge or decimal point falls within 0.25 PDF pt of the red guide. Three Save As/close/reopen rounds retain all 12 texts and stop declarations in independently inspected XML; the recorded reopened window covers only slide 1. PowerPoint merged some adjacent same-style runs and normalized `indent="-0"` to `"0"`. A further native edit appended `X` to one left-aligned sample and was saved and reopened once; its changed text and all 12 stop declarations were checked in XML. `python3 scripts/research/verify-native-tab-stops.py` rechecks the original declarations, PDF positions, saved XML and retained window records. No reopened PDF or remaining-slide visual comparison was captured, so this is not a general editability or three-round visual-fidelity result.

A separate [PowerPoint narrow-frame observation](tab-stop-wrap-powerpoint-evidence.json) uses 150 pt text boxes and a 120 pt stop. Unlike the LibreOffice examples above, PowerPoint splits the left-aligned `WIDE` and `MIXED` samples across lines: the first letter remains at the stop on its own line and the remainder starts at the frame edge. The longer decimal samples also shift their decimal point away from the guide when the frame is narrow. `python3 scripts/research/verify-native-tab-wrap.py` checks the source declarations, PDF characters and line grouping; only the first slide has a retained window capture, and no edit or reopen was performed. Font, application and source format differ between the LibreOffice and PowerPoint fixtures, so this is a concrete difference between these observed combinations, not a controlled attribution to application alone. The browser estimate is not PowerPoint-equivalent; its optional reject policy avoids a measurement when a tabbed explicit line requires automatic wrapping.

A [16-page PowerPoint width matrix](tab-stop-wrap-matrix-powerpoint-evidence.json) varies text-box width over 135, 150, 180 and 240 pt for four alignments and three strings. For the left-aligned `WIDE WORD` sample, `WIDE` starts after a blank line following the prefix at 135 pt, splits after `W` at 150 pt, splits after `WID` at 180 pt, and remains on the first line at 240 pt. The [browser comparison](tab-stop-wrap-matrix-browser-powerpoint-evidence.json) covers 36 left, center and decimal matrix samples with named Arial font candidates and the opt-in PowerPoint profile. All 316 non-space characters occupy the observed lines; their maximum horizontal-position difference is 0.235 pt, and the largest right-edge difference is 0.273 pt. Browser line spacing was set to 1.2 to approximate the observed PDF line advance and is not derived as a general mapping from PowerPoint spacing. The comparison does not prove byte-identical embedded fonts. `python3 scripts/research/verify-native-tab-wrap-matrix.py` checks source, PDF characters and selected control relationships, and `node scripts/research/verify-tab-wrap-matrix-cross-app.mjs` rechecks the recorded comparison and dependencies. This does not establish native editing, save/reopen, right-tab wrapping or arbitrary text behavior.

The [tab-position LibreOffice control](tab-position-libreoffice-evidence.json) varies stops over 90, 120, 180 and 240 pt at a fixed 150 pt frame width for center, right and decimal samples. Its PPTX differs from the generated matrix only by removal of the explicit zero first-line indentation on the sample paragraphs, addressing the LibreOffice-specific behavior noted above; `python3 scripts/research/verify-tab-position-libreoffice.py` checks that controlled change, source properties and 36 PDF character records. Some right-aligned results place the first word immediately after the prefix when the nominal aligned segment would overlap it.

The corresponding [PowerPoint first-open position matrix](tab-position-powerpoint-evidence.json) includes 36 samples with the same authored PPTX, including the explicit zero indent. The [browser comparison](tab-position-browser-powerpoint-evidence.json) matches line membership for 316 non-space characters and has a maximum horizontal-position difference of 0.235 pt and right-edge difference of 0.335 pt. It uses named Arial font candidates and the same calibrated browser line spacing 1.2; neither byte-identical embedded fonts nor a general line-spacing mapping is established. `python3 scripts/research/verify-native-tab-position.py` and `node scripts/research/verify-tab-position-cross-app.mjs` recheck the retained inputs and measurements. This is not an edit or save/reopen observation.

A separate [six-sample comparison](tab-shared-source-apps-evidence.json) checks equal authored text bodies and geometry for the 150 pt frame and 120 pt stop; three samples have different recorded line groups. `python3 scripts/research/verify-tab-shared-source-apps.py` verifies both prior records and the source equality. The LibreOffice input removes zero indentation and the applications use different fonts and PDF outputs, so the result does not isolate one cause.

An [eight-page three-item PowerPoint matrix](tab-phrases-powerpoint-evidence.json) covers four tab alignments at 150 and 220 pt with 24 samples. Frames were increased to 180 pt after an initial 120 pt control clipped the final word; the verifier requires every non-space source character in the PDF. The [browser comparison](tab-phrases-browser-powerpoint-evidence.json) matches line membership for 304 characters, with a maximum horizontal-position difference of 0.335 pt and right-edge difference of 0.468 pt. It uses named Arial candidates and calibrated browser line spacing 1.2. `python3 scripts/research/verify-native-tab-phrases.py` checks source and PDF characters; `node scripts/research/verify-tab-phrases-cross-app.mjs` rechecks the comparison and dependencies. The evidence is first-open printing, not native editing or save/reopen, and does not establish behavior for longer phrases, arbitrary fonts or spacing.

The [SVG anchor comparison](tab-svg-browser-powerpoint-evidence.json) checks the 12 suffixes from the no-wrap PowerPoint PDF against native SVG text rendered in Chromium, using named Arial candidates. Left and right suffix edges differ by at most 0.251 pt. The SVG fixture uses a single run; the PowerPoint source has two runs and uses a regular prefix, so the comparison is limited to suffix geometry. `node scripts/research/verify-svg-tab-powerpoint.mjs` rechecks the recorded arithmetic, font files and source evidence; [the producer](../../scripts/inspect-svg-tab-powerpoint.mjs) runs a new browser comparison. This is not evidence for overlap, wrapped text, mixed runs, shape/table text or general SVG viewer behavior.

The [two-run SVG comparison](tab-svg-mixed-browser-powerpoint-evidence.json) uses the same regular prefix and regular or bold suffix structure as those 12 PowerPoint samples. It checks source text including the tab, SVG run weights, prefix right edge and both suffix edges; the largest measured difference is 0.251 pt. `node scripts/research/verify-svg-mixed-tab-powerpoint.mjs` rechecks the source evidence, browser bundle and font hashes, recorded styles and arithmetic; [the producer](../../scripts/inspect-svg-mixed-tab-powerpoint.mjs) performs a new live browser comparison. This remains limited to named no-wrap samples and does not establish mixed-size, linked-run, shape/table, overlap, wrapping or general viewer behavior.

The separate [multiword SVG comparison](tab-svg-multiword-browser-powerpoint-evidence.json) compares ten non-space character edges for the centered `P` / `I WIDE WORD` sample, with a maximum difference of 0.331 pt. The PowerPoint source permits wrapping but this sample fits on one line; the SVG fixture explicitly disables wrapping. `node scripts/research/verify-svg-multiword-powerpoint.mjs` binds the retained PDF observation, candidate font, browser bundles and recorded arithmetic; [the producer](../../scripts/inspect-svg-multiword-powerpoint.mjs) repeats the Chromium measurement. This is one text-box sample, not a PowerPoint no-wrap, shape, editing or reopening observation. In the retained right-aligned sample the nominal phrase position collides with its prefix and PowerPoint shifts it; the current SVG anchor does not model that adjustment, so the tab warning remains necessary.
