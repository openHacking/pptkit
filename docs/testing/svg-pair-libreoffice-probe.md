# SVG and fallback selection in LibreOfficeDev

On macOS 26.5 (25F71) with LibreOfficeDev 26.8.0.0.alpha0 (2c87e51eeaa2b413ff4ae097b2705eea1995d8e5), the [optional probe](../../scripts/research/svg-pair-libreoffice-probe.mjs) builds a PPTKit slide with a blue PNG. It then manually adds a red SVG part, image relationship and Office `svgBlip` extension to a copy, independently of PPTKit's pair-generation path. Both resources deliberately disagree to expose which one is used.

Headless LibreOffice PDF export followed by Poppler rasterization produced a blue center pixel `[0, 0, 255]` for the original PNG-only slide and a red center pixel `[255, 0, 0]` for the paired slide. Both rendered pages were 101 × 101 pixels at the probe's chosen resolution. On the same paired input, PPTKit content projection mapped the blue PNG, reported the SVG extension as uninterpreted, and produced an exact original-byte no-op save. The result demonstrates that a valid-looking raster projection can differ from the source application's visible SVG. It does not prove general SVG conformance, native PowerPoint behavior, editing, or visual agreement when resources match.

The probe also exports an equivalent pair using the explicit PPTKit resolver contract; LibreOfficeDev rendered its center red as well. After each of three headless LibreOfficeDev PPTX save/reopen cycles, independent ZIP/XML inspection found one `svgBlip`, with the base relationship resolving to `ppt/media/image1.png` and the SVG relationship to `ppt/media/image2.svg`. Each reopened PDF remained red at the center, and PPTKit's no-op save was byte-identical to that cycle's actual LibreOffice output. The SVG SHA-256 remained `342048b552c12845e6d8d6ce03f3761ecb89b4b4dfb7ea1e8a247557b4dc9bfe`.

The base image did **not** retain its original blue content. The input was 20 × 20 with SHA-256 `fd298a04c9d501c6bc2f4900c902cbe49f5031717600c7a0de9a6ebe83803ee9`; the first saved file contained a 21 × 21 red PNG with SHA-256 `c6f186734c510643587bbfd5a385cfd684b1196cddc0d751347a9b95c892a1a8`, unchanged in the next two cycles. The application therefore replaced the fallback for this deliberately inconsistent sample. These are headless observations for one sample, not native Office validation or a guarantee of preservation, conversion fidelity, or behavior for arbitrary resources.

Run `node scripts/research/svg-pair-libreoffice-probe.mjs` after building Core, the parser and exporter. The probe requires `soffice`, `pdftoppm`, and Python Pillow; it uses and deletes an isolated temporary directory. It reports observations rather than asserting that other application versions must make the same choice. The extension's element and relationship semantics are described by Microsoft for [`svgBlip`](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-odrawxml/2451f45e-5d77-4661-86d1-0a017fced779) and [`CT_SVGBlip`](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-odrawxml/68e0150d-6a01-4ba5-ac4d-5a18d685229b).
