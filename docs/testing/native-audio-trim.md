# PowerPoint audio trim observation

In PowerPoint for Mac 16.104, the third object in the [four-audio baseline](../../tests/fixtures/pptkit-audio-loop.pptx) was trimmed from 0.100 to 0.950 seconds and saved as a [native sample](../../tests/fixtures/powerpoint-audio-trim.pptx). The retained copy anonymizes the last-modifier field. The full WAV remains unchanged and shared. That object's `p14:trim` stores `st="100"` and `end="50"` (amounts removed from each end), and its play command duration becomes 850 ms. PowerPoint also changed its direct audio relationship to external `NULL` while retaining the embedded Office media relationship. The [Microsoft format specification](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-pptx/c835eea3-fd6f-4055-8a57-92b193b7b2e3) describes the two trim attributes and their duration bounds.

The [generated sample](../../tests/fixtures/pptkit-audio-trim.pptx), reproducible with `node scripts/research/generate-audio-trim.mjs <output.pptx>`, retains internal audio and Office media relationships and has four independent instances sharing the WAV. PowerPoint opened it without a visible repair prompt; the third object's trim dialog displayed 0.100–0.950 seconds and 0.850-second duration. This confirms recognition in that version, not actual playback, loop segment boundaries, source editability after resaving, or compatibility elsewhere. The generated sample includes a separate looped trimmed object, but its actual repeat behavior was not observed.

The [independent verifier](../../scripts/research/verify-audio-trim.py) checks trim attributes and play command durations by target. Automated tests cover native and generated samples, shared assets, both start modes, mixed video, boundary and invalid values, preflight, and default bytes. Import does not map trim; no-op source preservation is separate.
