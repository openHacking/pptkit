# Headless group and slide ordering experiment

The [record](reorder-libreoffice-evidence.json) describes two repository-authored single-slide fixtures: an overlapping control and one produced after `reorderElements` and two nested `reorderGroupElements` calls. The independent [Python oracle](../../scripts/research/reorder-libreoffice-oracle.py) verifies source drawing order and per-object XML properties with drawing IDs excluded; only `ppt/slides/slide1.xml` differs between source packages. The overlap makes the stacking changes observable, and both fixtures contain the same caption, notes and six named colored shapes.

LibreOfficeDev 26.8.0.0.alpha0 saved and reopened each file three times headlessly. The parsed name/kind trees retain the authored top-level and nested orders through all rounds. The XML caption and notes, and extracted PDF caption, remain present. The exporter-generated descriptions on both groups, initially their fallback names, are absent after the first native save in both control and reordered files; this is an observed producer change, not attributed to PPTKit reordering. Other object properties are inventoried by hash and are not asserted preserved.

At 1× rasterization, the control and reordered outputs differ by 4,460 of 80,400 pixels initially and by 4,632, 4,460 and 4,632 in rounds one through three. Each saved rendering also differs from its respective initial rendering: control 889/431/948 pixels and reordered 890/600/1,007. These are raw pixel counts, not a classification of visual severity or a claim of exact native fidelity. A separate fresh run produced identical independent inventories and pixel counts; generated artifact bytes are tracked individually by hash rather than assumed identical.

The independent XML inventory also records each object's local transform. For both top-level squares A and B in both control and reordered files, width and height follow 762,000 → 761,760 → 761,400 → 761,040 EMU: the first native save removes 240 EMU, and each later save removes another 360 EMU. The same drift in the control shows that this observed shrink is not specific to the reorder. The application rewrites group-local coordinate representations, so the recorded nested transforms must not be compared as if they all used the same coordinate space. The object-size observation is consistent with render changes but does not prove the cause of every changed pixel.

Reproduce after building with `node scripts/inspect-reorder-libreoffice.mjs [soffice-executable]`; it uses a fresh local directory and isolated profile. [Negative tests](../../scripts/research/test_reorder_libreoffice_oracle.py) exercise wrong order at each level and changed raster pixels. The evidence does not prove native interactive editability, absence of repair dialogs, PowerPoint behavior, assistive-technology reading order, arbitrary grouped objects, or source-preserving reorder saves. The LibreOfficeDev build is not a stable-release compatibility claim.
