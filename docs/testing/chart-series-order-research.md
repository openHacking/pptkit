# Chart series-order source research

This is an experimental order-source profile for IMP-09.2.6.3; **order saves are blocked** by a PowerPoint counterexample described below. The importer collects each projected series' original `c:idx` and direct `c:order/@val` with raw element identity and series-to-chart ancestry. It records an incomplete candidate when these fields have unknown attributes, their raw ancestry differs, chart source ownership is unsafe, or chart formulas are not fully interpreted. A bounded raw scan rejects slide timing or extensions, chart extensions or foreign elements, and auxiliary or external chart relationships. The `complete` flag describes only these conservative checks; it does **not** establish complete package-wide dependency closure or guarantee a save.

On 2026-11-12 PowerPoint for Mac 16.104 opened [the retained order-only output](../../tests/fixtures/chart-order-powerpoint-round-1.pptx), SHA-256 `ab78ff44368fea9f05a4a11c38bedeec8a94d0493f28b657a3813f9c19b2b20c`. The chart accessibility tree listed the original legend order, `First _x005F_` followed by `Second & series`, and the original series values 1–3 and 4–6. An independent Python ZIP/XML check confirms that this file reverses the two `c:order` values while every other chart byte and all other package payloads match the input. Thus Parser reimport and cross-runtime agreement do not establish PowerPoint rendering order. This is one generated clustered-column chart and one application version; physical series movement and any dependent chart references still require investigation.

Visual inspection of the same file confirms the first series' blue bars are left of the second series' orange bars and the legend lists first then second. Two further controlled files swap only the complete `c:ser` byte ranges: [move only](../../tests/fixtures/chart-order-powerpoint-move-only.pptx), SHA-256 `acf0189959a55a9ee4531fbaabc26a1a81b51b59a1c2b3a02ac9e781174c588b`, retains the original `c:order` values; [move and order](../../tests/fixtures/chart-order-powerpoint-move-and-order.pptx), SHA-256 `bf27735149a585f07414e8b98053833705291935d68296b701cff29a43f75797`, also swaps those values. PowerPoint showed the orange second-series bars on the left and its legend entry first for both. The accessibility tree also reported the second series and its values 4–6 before the first and its values 1–3. Independent Python checks establish the exact byte swaps and unchanged remaining payloads, but these manually generated controls do not demonstrate a production writer, workbook editing, resaving, other chart families or applications.

Parser currently projects series by `c:order`: consequently it reverses the order-only file but retains the original order for the move-only file, unlike the observed PowerPoint rendering. When XML element order and `c:order` differ, import now records a `chart.series-order` finding explaining this discrepancy; it does not silently redefine existing Core ordering. Determining a broader cross-application projection policy remains open.

A private lexical sibling-reordering primitive now binds element spans through the validated XML tree, requires a single parent and whitespace-only gaps, preserves each element's exact lexical content and surrounding whitespace, and reparses the output. Tests cover UTF-8 and both UTF-16 byte orders, the retained PowerPoint control, incorrect identities, non-whitespace gaps, resource limits and cancellation. This is only a source-edit building block: it does not prove chart dependency closure, update `c:order`, reconcile mixed scalar-edit locations, or enable public order saves.

An indexed legend entry is a confirmed dependency. The [before](../../tests/fixtures/chart-order-legend-before.pptx) and [after](../../tests/fixtures/chart-order-legend-after.pptx) controls each add the same `legendEntry` with `idx=0` and `delete=1` to the original and physically reordered chart respectively. PowerPoint for Mac 16.104's accessibility tree showed only `Second & series` in the first legend, but only `First _x005F_` after reordering; both series remained in the plot. Thus preserving the override unchanged changes which series is hidden in this controlled example. Hashes and exact source changes are checked by `scripts/chart-order-evidence.test.mjs`. Microsoft documents that [chart indices are interpreted in their parent context](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.charts.index?view=openxml-3.0.1) and that [data labels may belong to either a series or an entire chart](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.charts.datalabels?view=openxml-3.0.1). The source-order candidate now rejects legend entries, pivot/band formatting and chart-level indexed data labels until their remapping is proved; it does not disable unrelated numeric source bindings.

A third [manually remapped control](../../tests/fixtures/chart-order-legend-remapped.pptx) changes the reordered file's legend index from 0 to 1. PowerPoint's accessibility tree again showed only `Second & series` in the legend while both series remained in the plot, matching the original hidden series. A private bounded planner maps position-based entries through explicit physical series identities; its attribute edit reproduces the retained control exactly. It rejects duplicate or out-of-range positions, invalid identities, incomplete permutations, exhausted budgets and cancellation. An internal research path checks raw single-column-chart and legend ancestry and simple index/delete markup, stages the edit with physical series movement, then reimports and verifies that each legend entry still targets its original series. A mixed test performs this across three internal candidate generations, and rejects extensions and unsupported legend markup. The public session cannot enable this research path and the existing public legend guard remains in force. Pie/doughnut legends, trendlines, combination charts, other index semantics and wider dependency coverage remain unproved.

The retained resave has two series-local `c:extLst` elements, each containing an `invertSolidFillFmt` extension and a `uniqueId` extension. Their placement suggests a possible future series-owned preservation rule, but this observation alone does not prove all references to those identifiers or the safety of moving them. They remain excluded from structural order edits pending dependency and native round-trip tests.

Microsoft describes `invertSolidFillFmt` as specifying negative-point color for the containing series in its [chart extensions documentation](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-odrawxml/78d69e36-6adf-4d87-a53f-958a7cce26cc). To test the specific retained resave, a manually constructed [extension-move control](../../tests/fixtures/chart-order-powerpoint-extensions-moved.pptx), SHA-256 `e006eb02b16786ee30d27066f338b74831103aa355438b54ce65b8c37d78c607`, swaps the two complete series, swaps their `c:order` values, and remaps the hidden legend index. An independent byte-level oracle confirms that each complete extension stays with its original series, all non-chart payloads are unchanged, and each observed unique ID occurs once in the outer package's uncompressed part bytes. That last check does not inspect nested archives or prove absence of encoded or semantic references. This single manual control is not a Parser-produced save, a PowerPoint resave, or evidence that arbitrary extensions are safe; the existing guard remains active.

A private source inspector recognizes this exact transitional column-chart extension shape and records the containing series ID and unique ID. Tests compare the retained original and moved control and reject unknown extension URIs, duplicate IDs, altered fill structures, additional extension lists, unrelated foreign extension elements, work exhaustion and cancellation. It does not scan package-level references or grant edit permission and is not connected to the preservation profile.

A separate private bounded reference scan now requires every retained original XML document, including relationship parts, content types, inactive compatibility branches and document-level nodes. It searches decoded attributes, text, comments and processing instructions for each GUID, verifies exactly one matching chart declaration, and reports non-XML parts separately. The retained PowerPoint resave has no additional literal GUID occurrences in its parsed outer XML, while its embedded workbook remains opaque to this scan. Tests inject references in another slide, including an inactive compatibility branch and entity-normalized text, and reject incomplete source retention, duplicate declarations, exhausted work and cancellation. This is an XML literal-reference inventory, not proof against transformed identifiers, implicit semantics, binary content or nested package references; it does not enable series reordering.

The private planner accepts a permutation of source series IDs, rejects missing/duplicate IDs and source fields, checks family boundaries, and reassigns the existing distinct order lexemes by rank. It does not use series names as identity and does not move the series XML or change workbook data. Work and cancellation are bounded. A focused test applies the resulting attribute edits to the generated two-series chart and verifies the reprojected series names and values reverse together while every other package part remains byte-identical. Additional cases cover unknown metadata/formulas, lexical forms such as `002`, invalid permutations, family boundaries and budgets.

The internal chart candidate staging function combines an order plan with numeric and label edits: it batches order-attribute changes, applies cache text changes while original element indexes still apply, then physically reorders series within each chart family. It stages worksheet changes in the same candidate. The lexical move records old-to-new element indexes for each moved descendant; full candidate reimport uses that mapping to verify order, numeric cache, series-name and category cache sources alongside workbook identities. A mixed test verifies physical element order and that edited values remain with their original source series. This staging function trusts its internal caller to supply a proven order candidate; public order saves remain disabled.

A private request capture validates explicit source IDs before any asynchronous work, copies arrays, rejects accessor fields, sparse arrays, duplicate owners or IDs, and applies change and work limits. The order analyzer reports its consumed work so a future session integration can subtract it from the shared analysis budget. Neither helper itself grants save authority.

The internal full-candidate path accepts an explicitly supplied order proposal, includes its chart in package-closure inspection, and reprojects the candidate. It compares the complete Core snapshot, rechecks source series IDs, order attributes and raw element locations, and remaps simultaneous numeric and series-name bindings by source ID before verifying their workbook/cache identities. Analysis restores candidate series to baseline indexing for ordinary scalar analysis; it does not guess identity from names or values. These checks passed mixed programmatic reopens but missed the native behavior above, so the public session blocks all order requests. Complete package-wide dependency policy remains open.

Each requested chart also receives its own bounded raw OPC relationship-closure inspection. The candidate requires complete relationship coverage, exactly one incoming chart relationship from its recorded owning slide, and no auxiliary chart relationships; the scan's work and expanded bytes are charged to the shared validation budget. A real duplicate incoming relationship and synthetic incomplete/incorrect graph cases are rejected. This proves only the recognized relationship graph: non-relationship references and broader extension/animation semantics are not implied by a clean result. The session separately applies its signature/VBA guards.

The source-order inspection also scans every available raw XML part for extension lists and presentation timing, rejecting such packages conservatively even when the markup is outside the owning slide and chart. This scan shares the chart binding work budget. It cannot establish that arbitrary non-relationship references or unrecognized binary payloads are absent, and it does not replace the signature/VBA guard.

Before this profile can be considered complete, establish package-wide and less conservative chart/slide dependency handling, shared-object policy, broader mixed-edit conflict semantics, independent package validation and native application behavior. Adding, removing or changing categories and series is not addressed here. Fresh export remains a separate operation.
