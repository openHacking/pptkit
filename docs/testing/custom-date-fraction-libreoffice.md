# Custom fractional dates: LibreOfficeDev headless observation

A synthetic source was built from a hash-verified PPTKit-created package with four custom `date` and `filetime` values. They cover one and two fractional digits, a millisecond value with trailing zeros, and a zero fraction, with explicit positive or negative offsets. PPTKit explicitly edited all four to canonical UTC values; an unchanged branch is the control. Independent ZIP and byte checks found only the four approved value texts changed in the custom part, preserving source tags and IDs.

LibreOfficeDev **26.8.0.0.alpha0**, on macOS 26.5 arm64, headlessly resaved each branch three times. On the first save it converted `date` to `filetime`, converted the source offsets to UTC, removed fractional seconds and reassigned IDs. This removed nonzero fractions in the control samples and nonzero milliseconds in the edited samples; the zero-fraction control retained its second-level instant. The application also added `PresentationFormat` and `Slides`, and the next two resaves retained the resulting inventory. This does not establish fractional precision, original offset notation or type preservation across applications.

The [record](custom-date-fraction-libreoffice-evidence.json) contains hashes, exact inventories and process logs. Check retained files with `python3 scripts/research/verify-custom-date-fraction-libreoffice.py` and reproduce in the recorded environment with `python3 scripts/research/custom-date-fraction-libreoffice.py`. Artifacts under `.tmp` are local, not a portable fixture corpus. PowerPoint, interactive property editing, repair prompts and other fractional values remain untested.
