# JPEG ICC profile: LibreOfficeDev probe

On macOS 26.5 (25F71), LibreOfficeDev 26.8.0.0.alpha0 (2c87e51eeaa2b413ff4ae097b2705eea1995d8e5), Pillow 12.1.1 and Poppler, the [probe](../../scripts/research/jpeg-icc-libreoffice-probe.mjs) exports two pictures from the same JPEG scan data. The first is the repository's 6 × 4 sRGB-tagged JPEG; the second removes its ICC APP2 segment without re-encoding. PPTKit's exact-byte deduplication keeps two separate parts and the ICC diagnostic warns only for the tagged asset. Their independently decoded sampled pixel is `[181, 40, 20]` in both cases.

The tagged JPEG SHA-256 is `ce478c3cdc7e2cfca2d36542d1025631316e602e8bad3d25b7f198132b3b5189`; the untagged JPEG is `f8f21967809ba17800cff8345ce239645718c719397d787b57ded3b6f198992b`. The 588-byte embedded profile SHA-256 is `6f4869def0dbd07485f7e3a7332621772aa8cf64c5a4dd42a47c59d03bfa1b7f`.

After the first headless LibreOfficeDev PPTX save, both picture relationships pointed to the same tagged JPEG, byte-identical to the original tagged asset. Thus the untagged picture acquired the other picture's profile in the saved package. This state persisted for two more save/reopen cycles. Both positions sampled `[181, 40, 20]` in each rendered PDF, and PPTKit no-op saves were byte-identical to each actual source file. A matching sampled color does not establish full visual or colorimetric equivalence. This is a deliberately related pair in one application version; it does not establish general ICC preservation, profile validity, other profiles, native PowerPoint behavior, or preservation-aware editing.

After building Core, parser and exporter, run `node scripts/research/jpeg-icc-libreoffice-probe.mjs` with `soffice`, `pdftoppm` and Python Pillow available. The probe uses an isolated temporary directory and deletes it afterward. It asserts its input controls and no-op behavior, and reports later application behavior rather than requiring every LibreOffice version to rewrite the relationship in the same way.
