# Mixed bidirectional text: first-open observation

This is a limited investigation, not acceptance of the mixed-bidi backlog item. On macOS 26.5 (25F71), PowerPoint 16.104 opened the generated one-slide presentation and displayed it in slideshow view. Chromium 149.0.7827.55 displayed the generated SVG. Four unwrapped, left-to-right paragraphs contain `ABC (שלום 123) XYZ` or `ABC (مرحبا 123) XYZ`: each occurs once in one run and once in four runs, with a run boundary inside the right-to-left word. The package XML confirms the texts and the respective one/four run counts. Both screenshots visibly place the numbers to the left of the Hebrew or Arabic word, inside the parentheses. The Arabic word appears connected in both the single-run and split-run examples.

For these four samples, Chromium character positions obtained with DOM Range sort into exactly the visual index order returned independently by macOS ICU `ubidi_getVisualIndex` with paragraph level 0. This includes spaces and parentheses; it checks positions, not the appearance of mirrored glyphs. Within each screenshot, comparing the thresholded glyph masks after aligning their bounding boxes gave zero different pixels between the single- and split-run Chromium examples, and 18 Hebrew / 19 Arabic different pixels in the PowerPoint screenshot. The PowerPoint and Chromium line bounding boxes have vertical offsets of 11, 8, 11 and 8 pixels, respectively; this is not a pixel-perfect cross-application result. No claim is made about the exact font actually selected by either application.

The [generator](../../scripts/research/prepare-bidi-observation.mjs) writes the PPTX, SVG, screenshot and DOM character coordinates. It requests Arial and blocks external browser requests. The inspected PowerPoint file and Chromium screenshot are `.tmp/bidi-observation-v2/source.pptx` and `.tmp/bidi-observation-v2/preview.png`, SHA-256 `72cca5f40b311bee7ae17ae71e4f83a2d3cc2aefd5df3146f10e82f293625a05` and `3ef5a9394afdcf2f63d0c00a60d6384ad63d936998f6edb9f8383aab9618e076`; the PowerPoint screenshot is `.tmp/bidi-observation-v2/powerpoint.png`, SHA-256 `66fec62980bcfd0c0b8fa0358ce96e256395b20d2f665763cda4ef4e7bc4bb27`. The local source PPTX, Chromium image, PowerPoint screenshot, and DOM character positions have SHA-256 `f73341d6cd86d0fdd5d55204914af0d3f994966f9525f23c114ac4c226c63d35`, `d9398ade610a2912d516bd83bcaeafea5b4addaaa63f90d8c1fda0001cfbc2d0`, `c4042fc03ec30ffa3af8138c9e262c09e7e30327ec5f10341294d7666ae229b7`, and `0a8594bfd06b8c1c6269f73f88accfdef5116e0a612638c7fbf974b0d67f3d01`, respectively. The PowerPoint capture was directly observed and is not checked by the ICU oracle.

Before the renderer change, selecting all descendants of the Hebrew single-run SVG group yielded `ABC (שלום\n123) XYZ`, and its `textContent` was `ABC (שלום123) XYZ`; the four-run HTML group yielded `ABC (שלום 123) XYZ` for both. The Arabic pair behaved the same way. A subsequent attempt combined soft-wrapped lines into one SVG text element, improving Chromium selection but causing visible bidi misplacement in WebKit 26.5: portions of the Arabic and Hebrew words moved to the wrong line. That approach was removed. The interim renderer kept independent SVG text elements per visual line, retaining soft-break spaces at zero font size and hard-break characters in hidden spans. In the [three-browser probe](../../scripts/research/probe-bidi-browsers.mjs), DOM text preserved the first two named source strings and glyph positions matched otherwise identical independent-line controls in Chromium 149.0.7827.55, Firefox 151.0 and WebKit 26.5. Selection is not a source-text guarantee: on the mixed hard/soft-break sample, Chromium inserted soft-wrap newlines, Firefox omitted hard-break newlines, and WebKit inserted soft-wrap newlines. The resulting Chromium screenshot for the earlier four wrapped examples remained byte-identical to the prior screenshot. Browser comparison is not native PowerPoint acceptance, general bidi conformance or an accessibility-tree result; the generated element remains a `role="img"` with its element name as its default accessible label. List markers and tabs add generated text, and paragraph boundaries are not DOM text separators.

The same probe, before the later paragraph-context routing change, additionally covered a paragraph with leading, consecutive and trailing hard breaks and a spaces-only line, plus a bulleted mixed-script paragraph with an empty line. In all three browsers the DOM preserved their source characters (after the generated bullet marker) and each glyph's measured position matches an independent-line control without the hidden spans. Selections omit one or more empty lines and vary between browsers; this is not a selection-fidelity fix.

Unassigned Unicode 16 values were excluded from that independent comparison. Browser Unicode versions, shaping and font coverage may differ.

## Explicit paragraph direction: source boundary

Initially Core's paragraph style had no paragraph-direction field. The parser reported DrawingML `a:pPr/@rtl` as unmapped, so neither the preview projection nor a fresh export could reproduce its meaning. A four-box first-open control in PowerPoint 16.104 pairs `rtl="0"` and `rtl="1"` for each of two strings with Latin, Hebrew, digits and parentheses, retaining identical text, box dimensions and explicit left alignment within each pair. The two RTL settings visibly produce different orders; in the second pair, the Hebrew words on either side of the parenthesized Latin text exchange sides. This is evidence that script detection and paragraph direction are distinct; it does not establish a complete RTL authoring contract, native editing behavior or the exact treatment of every punctuation/run combination. The first pair's `rtl="1"` appearance also needs deeper native run-direction investigation before claiming Unicode parity.

The [control generator](../../scripts/research/prepare-bidi-direction-native.mjs) and [attribute patch](../../scripts/research/prepare-bidi-direction-native.py) produced local `.tmp/bidi-direction-native/direction.pptx` (SHA-256 `d6f701b96e9dc20fe9f783191d8e4465d31526d5e7395da671ad9b13bea321ff`); the directly observed PowerPoint screenshot hashes to `e797fb939aa76d9830e233e2f2574c5f637efa89d7627f6fdcef931ed11c790a`. ## Run-level direction is a separate source feature

DrawingML's [`a:rtl` run property](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.righttoleft?view=openxml-3.0.1) is a child element of run properties, distinct from paragraph `rtl`. Its documented effect includes complex-script font selection and selective directionality of weak or neutral characters; it cannot safely be modeled as a generic CSS direction override. Core now exposes optional `rightToLeft` on run styles, including explicit false and inheritance. Fresh export writes it and import maps supported declarations; source-preserving style edits remain blocked. SVG reports an approximation because CSS does not implement the selective override, and the built-in browser measurer rejects true runs.

A [four-box control](../../scripts/research/prepare-bidi-run-native.mjs) pairs the same five runs `ABC `, `مرحبا`, ` - `, `123`, ` XYZ` under explicit LTR and RTL paragraphs. In the right-hand boxes, the [patch](../../scripts/research/prepare-bidi-run-native.py) adds `<a:rtl/>` to the Arabic word, punctuation and digits; the Latin runs are unchanged. After aligning the two captured boxes, the [threshold-mask check](../../scripts/research/oracles/bidi-run-native.py) found 21 and 18 differing pixels respectively, with more than 7,000 ink pixels per box; independently blanking each of the four boxes was rejected.
