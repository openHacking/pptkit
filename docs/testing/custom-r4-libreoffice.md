# Custom `r4` values: LibreOfficeDev headless observation

A synthetic source was built from a hash-verified PPTKit-created package by replacing its custom-property part with five `r4` values: a normal value, a fraction, negative zero, the smallest positive binary32 subnormal and the largest finite binary32 value. PPTKit explicitly edited all five to other exactly representable binary32 values; an unchanged branch is the control. Independent ZIP and byte checks found only the five approved value texts changed in the custom part, preserving source tags and IDs.

LibreOfficeDev **26.8.0.0.alpha0**, on macOS 26.5 arm64, headlessly resaved each branch three times. It retained all five named properties but converted them to `r8`, reordered them and reassigned IDs; it also added `PresentationFormat` and `Slides`. Ordinary sample values and the sign of zero remained represented, while the written decimal text for the maximum and subnormal samples changed in both branches. Parsing those extreme output texts as binary64 produces values different from the original exact binary32 values. Results remained the same over the next two resaves. This sample therefore does **not** establish exact cross-application numeric or type preservation.

The [record](custom-r4-libreoffice-evidence.json) contains hashes, exact inventories and process logs. Check retained files with `python3 scripts/research/verify-custom-r4-libreoffice.py` and reproduce in the recorded environment with `python3 scripts/research/custom-r4-libreoffice.py`. Artifacts under `.tmp` are local, not a portable fixture corpus. PowerPoint, interactive property editing, repair prompts and other values remain untested.
