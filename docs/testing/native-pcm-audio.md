# PowerPoint PCM WAVE observation

On PowerPoint for Mac 16.104, a new one-slide presentation was created and the audio insertion UI was used to embed a generated one-second, 8 kHz, mono, 16-bit PCM 440 Hz WAV. The presentation was saved as PPTX. The retained [sample](../../tests/fixtures/pcm-wave-powerpoint.pptx) is that save with only the creator and last-modifier values in `docProps/core.xml` replaced by `PPTKit fixture`; ZIP container bytes were rewritten. This is not an untouched native package. The synthetic tone can be regenerated with `python3 scripts/research/generate-pcm-tone.py <output.wav>`.

An [independent verifier](../../scripts/research/verify-native-pcm-audio.py), using Python's ZIP, XML and WAVE libraries, checks the package and generates the [observation](native-pcm-audio-evidence.json). The original and embedded WAV have the same SHA-256 and 8,000 PCM frames. PowerPoint writes a direct `a:audioFile` audio relationship and `p14:media` relationship to the same WAV, a separate image relationship for the poster, and a timing tree with a `playFrom(0.0)` command and audio target pointing at the picture's object ID. The WAV content type is `audio/x-wav`.

The Parser's `wave-pcm-v1` inventory identifies both relationships, their same-part status and frame metadata; the unmodified no-op save returns the exact retained sample bytes. Six deliberate changes to relationships, timing, content type or WAV bytes are rejected by `python3 scripts/research/test_native_pcm_audio.py`.

This is one saved native sample and package-level observation. It does not establish audible playback, a reopen or resave cycle, browser playback, behavior of other encodings, or correctness of newly generated audio. It informs the authoring/export design without closing the audio implementation task.

## Experimental PPTKit output

The [generated sample](../../tests/fixtures/pcm-wave-pptkit-generated.pptx), SHA-256 `fc585b984ff27cb8240594ab244fcdf26bb6456e4354081b6a1dcd1979797249`, is reproducible with `node scripts/research/generate-pcm-export.mjs <output.pptx>` after building the workspace. It uses the PCM bytes above and the writer's generated speaker poster. PowerPoint for Mac 16.104 opened it without a visible repair prompt, identified the selected object as audio, and showed a 1-second duration. Clicking preview changed its button from play to pause and then back to play. This is a manual UI observation; no audio stream was captured, no slideshow click or native resave was checked, and it does not establish compatibility beyond this single sample. The package tests independently verify shared audio part bytes, paired relationships, timing targets and Parser inventory on generated files.

## Two audio objects on one slide

In PowerPoint for Mac 16.104, the generated single-audio sample above was opened, its audio object duplicated with the native UI, and the result saved as a new file. The retained [duplicated sample](../../tests/fixtures/pcm-wave-powerpoint-duplicate.pptx) has its creator and last-modifier values anonymized afterward. Its two object IDs reference the same WAV and poster parts; its click sequence contains one play command per object, followed by separate audio nodes. The [independent verifier](../../scripts/research/verify-multi-audio.py) checks those targets, unique timing IDs and shared WAV bytes, and its [negative controls](../../scripts/research/test_multi_audio.py) detect wrong targets, duplicate timing IDs, wrong relationships and damaged WAV bytes.

The separate [PPTKit-generated two-object sample](../../tests/fixtures/pcm-wave-pptkit-multi.pptx) follows that observed timing topology and passes the same verifier; it is reproducible with `node scripts/research/generate-multi-audio.mjs <output.pptx>`. Automated tests cover three same-slide instances with two distinct WAV durations, shared parts, fresh import/export and Node/browser parity. The two-object generated sample has not been opened or played in PowerPoint; this observation does not establish independent simultaneous playback or slideshow behavior.
