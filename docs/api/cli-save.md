# CLI create-only preservation save

`pptkit save source.pptx destination.pptx --mode no-op [--json]` captures a bounded regular-file input, imports its structure using the public Parser API, prepares an original-byte no-op plan and publishes it through `@pptkit/pptx-parser/node` in `create` mode. The destination must not exist, including as a symlink. Source and destination may be specified relative to the execution cwd; `--` terminates option parsing. The source may be a symlink to a regular file under the same rules as [CLI inspection](cli-inspection.md). No overwrite, lossy rebuild or implicit external resource fetching is provided.

`pptkit save source.pptx destination.pptx --mode edit --first-slide-number 17 --json` sets the starting number through the existing [attribute-v2 preservation profile](first-slide-number-save.md). The value is a canonical decimal integer from 0 to 9999, or `clear` to remove the declaration. An absent declaration and explicit `1` are distinct; attempting an unchanged edit returns `save-edit-no-changes` and creates no destination. Parser guards, source closure and candidate validation remain authoritative; blocked plans report their first diagnostic and do not publish a file.

`pptkit save source.pptx destination.pptx --mode edit --text-edits edits.json --json` applies an explicit batch of existing text-run character replacements through [text-runs-v1](text-edit-save.md). The UTF-8 manifest has this shape:

```json
{
  "version": "pptkit-text-edits-v1",
  "sourceSha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "edits": [
    { "slideId": "slide-id", "elementId": "text-id", "paragraphIndex": 0, "runIndex": 0, "expected": "Old text", "replacement": "New text" }
  ]
}
```

Use `inspect --projection content --edit-save-profile text-runs-v1 --text-values --json` to obtain the captured source SHA-256, source-bound run identities and current expected text. The hash in this example is a placeholder. The manifest must have 1–10,000 unique targets, an exact lowercase source hash, zero-based safe integer indices, and an exact expected string for each current run. Unknown fields and stale hashes reject. V1 supports existing text boxes at the slide root or inside imported groups. Each target must have exactly one bound Parser source record and an unambiguous imported owner. Multiple edits within one group are staged in one cloned root; all targets are checked before replacements are applied. Parser's whole-plan guards, closure inspection and candidate reprojection still decide whether the batch is saveable; a bound record alone is not permission. Any blocked or invalid batch creates no destination. Source and each manifest are separately bounded by `--max-input-bytes`. The report's `inputs` includes source and manifest hashes; successful changes may include the original and replacement text. This operation is synchronous while staging and checks cancellation between targets, but cannot preempt an individual synchronous clone or Core replacement.

`--text-values` adds `textEditCandidates` to the inspect JSON envelope, with the corresponding manifest `version`, `sourceSha256`, an ordered `targets` array and `unboundCount`. Each target contains the fields needed for that profile plus `expected`, but no `replacement`: select targets, add replacements and place them in the manifest's `edits` array. Unmapped runs are counted and remain in the ordinary source report, but are not candidates. Ambiguous or inconsistent bound identities fail rather than being silently dropped. This opt-in exposes document text in stdout; default inspection remains unchanged. Candidate listing does not run save guards or guarantee a subsequent save, and reports over `--max-output-bytes` fail without partial results. The flag requires JSON content inspection with an explicit text profile and cannot be combined with the capability view.

For the separate [text-runs-v2](text-owner-save.md) scope, use `version: "pptkit-text-edits-v2"` and specify `owner` on every edit: `"text-box"` or `"shape-text"` with `elementId`, or `"notes"` without `elementId`. Use `inspect --projection content --edit-save-profile text-runs-v2 --json` for drawing `textRuns` and the separate `notesTextRuns` identities. A single batch may combine existing bound text boxes, mapped shape text and direct notes-body runs, including mapped groups; wrong owners, unmapped or ambiguous sources, and a notes edit carrying an element ID reject. V1's manifest shape and profile are unchanged.

Use `version: "pptkit-text-edits-v3"` for the [table-cell character profile](table-text-save.md). It includes V2 owners and adds `owner: "table-cell"` with `elementId`, `rowIndex`, `cellIndex` and `columnIndex`, in addition to the paragraph/run indices and expected/replacement strings. Obtain these from `tableTextRuns` using `inspect --projection content --edit-save-profile text-runs-v3 --json`. `cellIndex` is the compact Core anchor index and `columnIndex` is the physical source grid column; both must match the same binding, including after merges. Tables nested in mapped groups are supported. Covered cells, wrong physical columns, missing/ambiguous bindings and unsupported ranges reject the batch. Cell styles, grid/merge changes, dynamic fields, structural edits and inferred inheritance remain unsupported. V1 and V2 do not gain table permission.

`--chart-edits charts.json` admits the separate [existing chart numeric profile](chart-value-save.md). Its manifest uses `version: "pptkit-chart-edits-v1"`, the captured `sourceSha256`, and 1–10,000 `edits` with `slideId`, `elementId`, `seriesIndex`, `pointIndex`, `expected` and `replacement`. The last two are **canonical finite numeric strings**, as produced by JavaScript's `String(number)`, with `"-0"` retained separately from `"0"`; noncanonical spellings such as `"1e3"`, non-finite numbers and JSON numeric values reject. Use `inspect --projection content --chart-edit-save-profile existing-values-v1 --chart-values --json` to obtain the matching `chartEditCandidates` with expected values; choose targets and add replacements. Unmapped values are counted, ambiguous identities fail and the full report must fit the output budget. Fixed axis ranges are not recalculated and may clip changed values.

When scatter-coordinate bindings are present, the same inspection also returns `chartEditCandidatesV2` with `version: "pptkit-chart-edits-v2"`. Its scatter targets add `coordinate: "x"` or `"y"`; category-chart targets omit that field. Use the v2 version, source hash and selected targets to construct a v2 `--chart-edits` manifest. X and Y at the same point are distinct targets and may be edited together with category values in one transaction. Sparse or otherwise unbound source coordinates remain excluded and count as unbound. The v1 candidates and manifest retain their previous behavior.

For the opt-in sparse-scatter profile, inspect with `--chart-edit-save-profile existing-values-v2 --chart-values --json`. This produces `chartEditCandidatesV3` for the v3 manifest instead of the v1/v2 candidate fields. V3 retains the same coordinate fields and numeric-string rules, and selects Parser's `existing-values-v2` during save. Existing nonblank coordinates are eligible only when sparse cache and workbook values agree, including blank positions; blanks themselves cannot be inserted, removed or edited. V1 and v2 manifests continue to select the v1 Parser profile and cannot be used to bypass these restrictions.

For dense bubble and column/line combination charts, use `inspect --projection content --chart-edit-save-profile existing-values-v3 --chart-values --json`. The output field `chartEditCandidatesV4` uses `version: "pptkit-chart-edits-v4"` and reports separate `coordinate: "x"`, `"y"` and `"size"` targets for bubbles. Combination targets omit `coordinate` and identify the column or line series by its global `seriesIndex`. Copy the selected targets into `edits`, add canonical numeric `replacement` strings, and pass the manifest to `save --mode edit --chart-edits`. Size replacements must be strictly positive. V4 selects Parser's `existing-values-v3`; V1–V3 retain their original behavior. Sources without matching cache and workbook cells yield unbound targets.

For supported category labels, inspect with `--chart-edit-save-profile existing-values-and-labels-v4 --chart-values --json`. `chartEditCandidatesV5` uses `pptkit-chart-edits-v5`: category targets carry `kind: "category"`, `slideId`, `elementId`, `categoryIndex` and the exact expected text. Copy targets into `edits` and add a nonempty string `replacement`; numeric targets keep the v4 format and may be included in the same manifest. The source SHA-256 and expected values protect against stale targets. Unsupported source bindings are omitted and counted in `unboundCount`; save rejects a stale, duplicate or unbound target without producing a partial output. See [chart source-save limits](chart-value-save.md).

For supported series names, inspect with `--chart-edit-save-profile existing-values-and-series-names-v5 --chart-values --json`. The `chartEditCandidatesV6` field uses `pptkit-chart-edits-v6` and adds `kind: "series-name"` targets identified by `slideId`, `elementId` and `seriesIndex`. Copy a target into `edits` and add a nonempty string `replacement`. V6 also accepts v5 category and numeric targets in the same transaction. Expected text and source SHA-256 must match; duplicate, missing, ambiguous or unbound targets are rejected without an output file.


In `--mode edit`, `--chart-edits`, `--text-edits` and `--first-slide-number` can be combined in one plan. Each manifest must match the same captured source hash. All requested modifications are staged before Parser preparation; any invalid target, unsupported combination, source-closure issue or candidate failure blocks the entire publication. The command creates a new file only and does not advance or overwrite the original source.

`--description-edits descriptions.json` edits directly bound slide-object descriptions. First run `inspect source.pptx --projection content --description-values --json`; its `descriptionEditCandidates` contains the manifest version, source SHA-256, eligible targets and `unboundCount`. Copy selected targets into `edits` and add `replacement` to each. Both `expected` and `replacement` are strings or `null`: `null` means the attribute is absent, while `""` means an explicitly empty description. The manifest requires 1–10,000 unique targets, exact source hash and expected values; unknown fields, ambiguous or unbound identities and stale values reject before publication. Groups and their nested objects are supported when directly bound. Candidate enumeration does not grant save authority: Parser guards and candidate validation remain decisive.

Description edits can be combined with `--text-edits`, `--chart-edits` and `--first-slide-number` in one plan. A combined text manifest must use `pptkit-text-edits-v3`; description-only commands also use the Parser's `mixed-v5` profile. For simultaneous candidate inspection, add `--edit-save-profile text-runs-v3 --text-values` and/or `--chart-edit-save-profile existing-values-v1 --chart-values`. `--description-values` requires JSON content inspection and cannot be combined with capabilities, picture-source, diagram or older text profiles. Descriptions appear in stdout and reports when requested. Picture replacement cannot be combined with description edits. The result is scoped preservation, not a native application verification.

`--name-edits names.json` accepts a `pptkit-name-edits-v1` manifest with `sourceSha256` and `edits`, each containing `slideId`, `elementId`, `expected` and `replacement`. Both values must be strings: an empty string is an explicit name and `null` is invalid. Obtain bound candidates from `inspect source.pptx --projection content --name-values --json`; absent or ambiguous source names are excluded or rejected. The same hash, expected-value, duplicate, budget and whole-plan checks apply as for description edits. Name edits may join description, V3 text, chart and starting-number edits in the same transaction. Candidate inspection may combine `--name-values` and `--description-values` with V3 text and chart-value inspection. Picture edits remain separate, and native application behavior is not verified by this CLI operation.

`--decorative-edits decorative.json` accepts a `pptkit-decorative-edits-v1` manifest with `sourceSha256` and `edits`, each containing `slideId`, `elementId`, and Boolean `expected` and `replacement`. Use `inspect source.pptx --projection content --decorative-values --json` to obtain `decorativeEditCandidates`. Only directly bound existing decorative values are candidates; absent, ambiguous, MCE-promoted or unsupported extensions are counted as unbound. This operation neither inserts nor removes an extension. The manifest may join name, description, V3 text, chart and starting-number edits in one guarded transaction. Source hash, expected value, duplicates, limits and Parser candidate checks apply; picture edits remain separate. No native or assistive technology behavior is inferred from a successful save.

`--visibility-edits visibility.json` accepts a `pptkit-visibility-edits-v1` manifest with `sourceSha256` and 1–10,000 `edits`, each containing `slideId`, Boolean `expected` and Boolean `replacement`. `true` means hidden. Obtain source-bound candidates via `inspect source.pptx --projection content --visibility-values --json`; select entries from `visibilityEditCandidates.targets` and add replacements. The report counts unbound slides separately. Duplicate identities, missing/unbound slides, stale hashes or expected states, and non-Boolean values reject before publication. A candidate does not guarantee a save: source guards, shared-source agreement and candidate validation apply. Visibility can be combined with compatible text, chart, name, description, decorative and starting-number edits; picture replacement remains separate. `--dry-run` reports the full plan without publication.

`--metadata-edits metadata.json` accepts a `pptkit-metadata-edits-v1` manifest with `sourceSha256` and 1–5 `edits`, each containing `field`, string `expected` and string `replacement`. Eligible field names are `title`, `author`, `subject`, `description` and `language`. Obtain them from `inspect source.pptx --projection content --metadata-values --json`; select entries from `metadataEditCandidates.targets` and add replacements. Missing or non-character-only properties are counted as unbound and cannot be inserted. Duplicate/unknown fields, stale hashes or baseline values and non-string values reject before publication. The command preserves other metadata values and does not implicitly change author, revision or timestamps. Metadata may join compatible text, chart, visibility, name, description, decorative and starting-number edits; picture replacement remains separate. The Parser's guards and candidate validation remain authoritative.

Add `--metadata-revision` to that inspection to request `pptkit-metadata-edits-v2`. It retains the string fields and adds a source-bound `revision` target when its existing XML text is a canonical nonnegative safe integer. Its `expected` and `replacement` are JSON numbers, both nonnegative safe integers; v1 still rejects revision edits. Missing or unbound revision values cannot be created by this manifest, and revision is never updated automatically.

Use `--metadata-values --metadata-keywords` to request `pptkit-metadata-edits-v3`, which also includes v2 revision targets. A bound `keywords` target uses string `expected` and `replacement` values for the single aggregate keyword entry. Missing, language-tagged or segmented keywords are unbound; v1 and v2 do not accept keyword edits. This operation does not split or combine keyword entries.

Use `--metadata-values --metadata-company` to request `pptkit-metadata-edits-v4`. It also includes v3 targets and admits string edits to a bound existing `company` in the extended-properties part. Missing, mixed-content or compatibility-processed sources remain unbound; earlier manifest versions cannot edit company.

Use `--metadata-values --metadata-insert` to request `pptkit-metadata-edits-v5`, including the v4 targets and missing direct core string fields eligible for insertion into an existing core-properties part. An insertion target has `expected: null`; supply a string `replacement`, including an empty string or the normalized default. Bound fields retain their existing string or numeric `expected` values. The manifest remains tied to the captured source hash, and missing, ambiguous or guarded parts cannot be inserted. Earlier manifest versions do not accept insertion targets.

Use `--metadata-values --metadata-dates` to request `pptkit-metadata-edits-v6`. This includes v5 targets and adds existing, bound `createdAt` and `modifiedAt` values. Their `expected` and `replacement` strings must be canonical UTC timestamps with millisecond precision, for example `2020-02-29T12:34:56.123Z`; an offset source is reported as its equivalent UTC value. Missing or unrepresentable dates remain unbound and cannot be inserted by this manifest. Date edits can be combined with the other admitted v5 metadata changes.

Use `--metadata-values --metadata-date-insert` to request `pptkit-metadata-edits-v7`. It includes v6 targets and exposes eligible absent dates as `expected: null`; provide a canonical UTC millisecond `replacement`. An existing core-properties part is required. Existing dates and other eligible fields may be edited in the same source-hash-bound manifest.

Use `--metadata-values --metadata-create` to request `pptkit-metadata-edits-v8`. It includes v7 targets and exposes eligible string and date insertions when the core-properties part is absent. A missing target has `expected: null`; a canonical UTC millisecond value is required for dates. Core and custom property creation may share one guarded save transaction. Revision and keywords cannot be created by this profile.

Use `--metadata-values --metadata-revision-insert` to request `pptkit-metadata-edits-v9`. It includes v8 targets and identifies an eligible missing revision as `expected: null`. Provide a nonnegative safe integer replacement, including `1` to explicitly insert the normalized default. Existing invalid or ambiguous revisions remain unbound.

Use `--metadata-values --metadata-keywords-insert` to request `pptkit-metadata-edits-v10`. It includes v9 targets and exposes an eligible missing aggregate keyword as `expected: null`. Provide one string `replacement`, including an empty string. Existing segmented or language-tagged source keywords remain unbound.

Use `--metadata-values --metadata-company-insert` to request `pptkit-metadata-edits-v11`. It includes v10 targets and exposes an eligible missing company as `expected: null`; supply one string `replacement`. An existing unambiguous extended-properties part is required.

Use `--metadata-values --metadata-extended-create` to request `pptkit-metadata-edits-v12` when the extended-properties part may be missing. An eligible missing company is exposed as `expected: null`, and saving can create extended, core and custom property parts in one transaction. Existing declaration conflicts and unsafe source graphs remain rejected. A [LibreOfficeDev headless observation](../testing/extended-create-libreoffice.md) covers one generated sample; interactive and PowerPoint behavior remain unverified.

Use `--metadata-values --metadata-remove` to request `pptkit-metadata-edits-v13`. The candidate report lists `removableFields`; for a listed bound field, supply its exact string `expected` and `replacement: null` to remove it. An empty string replacement writes an empty element instead. V13 retains v12 insertion and creation; `expected: null` with a string replacement still means insertion. Source guards and the final package validation can block a listed removal, and the complete transaction fails on stale or invalid edits. A [LibreOfficeDev comparison](../testing/metadata-remove-libreoffice.md) observed empty subject and description elements added after removal; interactive and PowerPoint behavior remain unverified.

`--metadata-values --metadata-date-remove` requests v14 and additionally permits deletion of listed `createdAt` and `modifiedAt` values with their canonical UTC `expected` and `replacement: null`. The same source eligibility and transaction guards apply. A [LibreOfficeDev headless comparison](../testing/metadata-date-remove-libreoffice.md) covers one synthetic sample; PowerPoint and interactive behavior remain unverified.

`--metadata-values --metadata-keywords-remove` requests v15 and additionally permits removal of an eligible single keyword using its exact string `expected` and `replacement: null`. A replacement of `""` retains an empty keyword instead. Segmented or language-tagged sources remain unavailable. A [LibreOfficeDev headless comparison](../testing/metadata-keywords-remove-libreoffice.md) covers one sample; PowerPoint and interactive behavior remain unverified.

`--metadata-values --metadata-revision-remove` requests v16 and additionally permits removal of an eligible canonical revision with its numeric `expected` and `replacement: null`. This explicit action also removes a source revision of 1, despite the normalized default. A [LibreOfficeDev comparison](../testing/metadata-revision-remove-libreoffice.md) observes an application-inserted revision `0` in one sample; PowerPoint and interactive behavior remain unverified.

`--metadata-values --metadata-default-remove` requests v17 and additionally permits removal of eligible `title`, `author` and `language` using their exact string `expected` and `replacement: null`. The operation is explicit even when the source equals its normalized default. A [LibreOfficeDev comparison](../testing/metadata-default-remove-libreoffice.md) covers one sample; PowerPoint and interactive behavior remain unverified.

For a single [source-bound picture replacement](picture-edit-save.md), use `--picture-edit picture.json --picture-bytes replacement.gif`. The manifest is an object with `version: "pptkit-picture-edit-v1"`, `sourceSha256`, `replacementSha256`, `slideId`, `elementId`, `expectedAssetId`, `mimeType`, `width` and `height`. Both hashes are exact lowercase SHA-256 of the captured files. MIME must be `image/png`, `image/jpeg` or `image/gif`, and dimensions must be positive safe integers matching the actual image. Use `inspect --projection content --picture-source-profile embedded-v1 --json` for the picture identity and asset ID. The replacement is a separately named local file, read as a bounded regular-file snapshot; all three captured inputs and hashes appear in the success report. Slide-root and mapped grouped pictures are supported. The Parser verifies the actual replacement, source closure and candidate before publication; its JPEG validation does not fully decode pixels, and native appearance is not guaranteed.

```json
{
  "version": "pptkit-picture-edit-v1",
  "sourceSha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "replacementSha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "slideId": "slide-id", "elementId": "picture-id", "expectedAssetId": "asset-id",
  "mimeType": "image/gif", "width": 1, "height": 1
}
```

The hashes and identities in this example are placeholders; calculate the replacement file's SHA-256 independently and use the source report for its hash and identities.

Picture replacement may be combined with `--first-slide-number`, but the Parser picture profile excludes text and chart edit profiles, so the CLI rejects those combinations as well as description, name, decorative, visibility or metadata edits. Only one picture can be replaced per plan. Existing media and relationships are retained, including when another picture shares the original media; no source-asset garbage collection or automatic recropping occurs. Source or replacement hash mismatch, unsupported picture effects, incompatible options or invalid bytes reject without publication. `--dry-run` reports Parser-blocked picture plans without publishing; malformed manifests or mismatched hashes remain command errors.

Add `--dry-run` to either save mode to prepare the same Parser plan without publishing a destination. A ready plan returns exit 0 and `status: "ready"`; a Parser-blocked plan returns exit 1 and `status: "blocked"`. The JSON report contains the full preservation report, including changes, losses and diagnostics when present, and `dryRun: true`. Manifest, import, resource and cancellation failures retain their normal error exits. The complete report must fit `--max-output-bytes`; no partial result is returned. The destination argument is recorded but is not opened or checked for existence, permissions or filesystem support. The plan is disposed at command exit and cannot be reused: a later save recaptures inputs and prepares a new plan, and may fail if inputs or the destination have changed. Dry-run success is not a native application or publication guarantee.

The JSON success envelope uses `pptkit-cli-report-v1`, `command: "save"`, captured source path/size/SHA-256, `nativeVerification: "not-performed"`, relative `destination`, and `report` with `status: "committed"`, assurance, `directorySynced`, `warnings` and any preservation changes. Edited saves also carry `edit.firstSlideNumber`, with `null` denoting clear. A successful command means the destination has been published, even if directory sync or postcommit cleanup has a warning. If details exceed the output limit, the successful report instead has `detailsTruncated: true` and conservative `directorySynced: false`; inspect the destination and its directory. Human output likewise indicates omitted details. Output capacity for that fallback is checked before publication, so an output-limit error cannot follow a successful commit. After commit, cancellation cannot undo publication.

Parser's [file adapter contract](file-save.md) specifies temp files, file sync, create-only atomic publication, cleanup warnings, cancellation boundaries and filesystem/platform limits. A precommit cleanup failure reports `file-cleanup-failed`, with `error.source.temporaryPath` when available so callers can locate the leftover; no destination was committed. Other file errors carry their Parser code and exit 3, resource limits exit 4, and cancellation before commit exits 130. `--max-input-bytes` and `--max-output-bytes` have the same bounds as inspection. The JSON stdout result is not a native PowerPoint/LibreOffice validation.

Focused tests cover byte identity, malformed input, existing files and symlink destinations, same-path refusal, output preflight, cancellation and competing create requests. Both dialects exercise number edits and three text replacement/reimport rounds for root, nested-group, shape, notes and merged-table text, with independent part comparison and stale, duplicate, missing, mixed-invalid and invalid-XML controls. The installed executable exercises V1–V3 text manifests against freshly generated decks. CLI-specific native reopen, broader text edits, replacement and lossy rebuild remain outstanding.

`inspect source.pptx --projection content --custom-property-values --json` returns `customPropertyEditCandidates`: source SHA-256, bound source `part` and `sourceObjectId`, and each target's expected `name`, `type` and `value`. Values are strings even for booleans and numbers, preserving `-0`. To edit, create a `pptkit-custom-property-edits-v1` JSON manifest with `sourceSha256` and an `edits` array; copy each target's `part`, `sourceObjectId` and `expected`, then add a string `replacement`. Boolean replacements are `true` or `false`; integers and finite reals use canonical JavaScript decimal notation; dates require canonical millisecond UTC form. String values are literal. Duplicate identities, stale hashes/baselines, noncanonical values and unbound sources reject before publishing. Names, types and membership cannot be changed through this profile. Custom edits may join compatible core metadata, text, visibility, chart and drawing-property transactions; picture replacement remains separate. `--dry-run` prepares the candidate without publishing it.

To rename an existing bound custom property, add `--custom-property-names` to the inspection command alongside `--custom-property-values`. The returned version is `pptkit-custom-property-edits-v2`; each edit may supply a nonempty `replacementName`, a `replacement` value, or both. The same source identity and expected baseline are mandatory. Renaming into an existing modeled or opaque property name rejects the transaction. When an opaque source name has undecidable escape semantics, v2 omits rename candidates; v1 can still offer bound value edits. V1 remains value-only and rejects `replacementName`.

To delete bound custom properties, inspect with `--custom-property-values --custom-property-deletions`. The returned `pptkit-custom-property-edits-v3` manifest accepts `delete: true` for an existing target, instead of `replacement` or `replacementName` for that target. Other targets in the same v3 manifest may be renamed or updated using the v2 fields. Each deletion retains its explicit source identity and expected baseline; unknown or unbound properties cannot be deleted. The original custom-properties part remains present. V1 and v2 manifests reject `delete`.

To append custom properties to an existing supported part, inspect with `--custom-property-values --custom-property-additions`. The `pptkit-custom-property-edits-v4` candidate report includes `insertion.status`. A v4 manifest contains `sourceSha256`, an `edits` array (which may be empty), and an `additions` array of `{ "name", "type", "value" }`; values use the same canonical string conventions as replacements. At least one edit or addition is required. V4 also accepts v3 deletes and v2 rename/value edits. Additions are appended in manifest order, and the Parser allocates new IDs without reusing any ID present in that source snapshot. A missing or ambiguous custom-properties part reports insertion unavailable and rejects insertion before publication. V1–V3 do not accept `additions`.

Add `--custom-property-create` to that inspection to request the `pptkit-custom-property-edits-v5` manifest. V5 has the same fields and edit operations as v4, and can also create a missing custom-properties part when the raw package graph and declarations permit it. The report's insertion status indicates whether creation or appending is available; source SHA-256 binding and dry-run behavior are unchanged. V4 continues to reject insertion when the part is missing.

For exact decimal source edits, inspect with `--projection content --custom-property-values --custom-property-decimal --json`. This returns a `pptkit-custom-property-edits-v7` report with bound targets and insertion status. V7 supports value changes, renames, deletions, appends and creation of a missing custom-properties part. Decimal values are canonical strings such as `"9007199254740993.0001"`; they are never converted to JavaScript numbers. The same source hash and baseline checks apply, and `--dry-run` does not publish. V7 combines with compatible text, metadata and visibility manifests, while currency, chart, drawing, picture and starting-number edit profiles remain incompatible. Previous manifest versions do not accept decimal additions. See [ADR 0066](../architecture/decisions/0066-exact-decimal-custom-properties.md) for precision and cross-application limits.

For exact currency source edits, inspect with `--projection content --custom-property-values --custom-property-currency --json`. The `pptkit-custom-property-edits-v6` manifest uses the v1 value-only fields and source/baseline checks. Copy a target and supply a canonical JavaScript numeric string such as `"0.5"`; currency replacements must additionally be nonnegative and mathematically exact at four decimal places, so `"0.1"` is rejected. V6 can edit other bound scalar values in the same custom-property manifest and can combine with compatible text, metadata and slide-visibility manifests. Each manifest must match the same source SHA-256 and its own expected baselines; any unsupported edit blocks the entire save. V6 cannot rename, delete or add custom properties, or combine with chart, drawing, picture or starting-number edits. Inspection rejects incompatible profile options. `--dry-run` does not publish. The existing v1–v5 behavior is unchanged. See [currency source-save limitations and the LibreOfficeDev observation](opaque-custom-properties.md).
