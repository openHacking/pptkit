# Byte assets and explicit export resolution

Core accepts `source: { type: "bytes", value: Uint8Array }` when registering an image. Node Buffer and offset views are accepted. Registration copies only the selected bytes before returning, then stores immutable canonical Base64 as `{ type: "bytes", encoding: "base64", value: string }`. Subsequent caller mutations cannot change the asset. Core does no filesystem access, fetching or image decoding.

Raw registration and resolver byte loading inspect the underlying typed-array view rather than overridable subclass properties; shared-memory-backed views are rejected. Resolver `maxAssetBytes` is checked against the actual view length before copying, including for typed-array subclasses.

`PresentationAssetSourceInput` includes raw inputs; `PresentationAssetSource` describes stored/normalized sources. Callers may also supply canonical Base64 directly with its explicit encoding. Empty data, malformed/noncanonical Base64, non-Uint8Array raw inputs and shared-memory buffers reject at registration. Rejected registration adds no asset. Stored sources and metadata are frozen; normalized IR is detached and JSON serializable. Base64 is a format-independent byte representation, not OOXML preservation state. IR remains version 2 with an additive source variant; exhaustive source switches must handle `bytes`. The source contract is now a discriminated union; consumers that previously extended the source interface should compose a type intersection or extend the specific path/URL member instead.

The existing explicit ID/dedupeKey policy applies after canonicalization: raw bytes and equivalent Base64 can share an identity; conflicting metadata rejects. Default registration does not deduplicate content without identity. Opt-in byte content matching, stable-ID replacement and guarded Core cleanup are now available through [asset lifecycle APIs](asset-lifecycle.md). Preservation-aware package garbage collection remains format-layer work.

See the [typechecked example](../examples/byte-assets.ts).

## Image profiles and preview

The byte loader and default byte preview recognize PNG, JPEG and GIF headers, infer MIME when absent, and reject a declared MIME that differs (comparison is case-insensitive with surrounding whitespace removed). `image/apng` is accepted as a PNG-signature declaration and packaged as `.png` / `image/png`; that declaration alone does not prove animation or even full structural validity. URL and path sources declaring `image/apng` likewise package as PNG but retain their existing unverified loading behavior. They verify signature classification, not complete decoding, dimensions, CRC, color profiles, animation playback or native application fidelity. The author supplies dimensions for contain/cover/crop geometry. Byte-backed SVG/EMF/WMF require an explicit conversion resolver for this export path.

The exporter packages the original bytes under the matching extension. Invalid/unsupported bytes produce `asset-read-failed`, followed by existing `image-omitted` diagnostics for affected uses. No misleading media part is emitted. One registered asset is loaded once per export and shared by its uses. The Renderer emits a self-contained data URL for supported bytes, without object URLs or hidden fetching; unsupported/mismatched headers produce `asset-bytes-unsupported` and a placeholder. An explicit SVG resolver can still provide an alternate URL.

Media part names are internal package details. Simple ASCII asset IDs retain their usual filenames when unique; IDs containing path separators or other unsafe characters, and case-insensitive filename collisions, receive deterministic generated names. Asset IDs and references in Core do not change. Consumers should use relationships rather than derive package paths from IDs.

Byte-backed EMF and WMF are not parsed or emitted natively. An explicit export resolver may return signature-checked PNG or JPEG bytes with `vectorRasterization: "emf"` or `"wmf"`, respectively, for an asset declaring the matching `image/emf` or `image/wmf` MIME. The exporter emits one `asset-vector-rasterized` warning per loaded asset because vector editability is lost. The declaration is the caller's assertion: PPTKit does not read or validate the source metafile, perform the conversion, or guarantee visual, color, font or crop fidelity. Resolver output still obeys `maxAssetBytes`; converter input limits, cancellation, and isolation are the caller's responsibility. The declaration cannot be combined with animation or orientation conversion declarations. Without a converter, byte-backed metafiles are omitted with diagnostics. Path/URL loaders without signature validation must not be treated as metafile support; use an explicit resolver. Preview conversion requires its own explicit resolver. Preservation of imported metafiles and application-specific native behavior remain separate, unverified work.

The same resolver contract accepts `vectorRasterization: "svg"` for `image/svg+xml` and emits the same loss warning. This is a static raster fallback: vector data and any SVG animation are not packaged, and source SVG validity, fonts, external resources, scripting, canvas size and conversion fidelity are the caller's responsibility. PPTKit does not fetch or interpret the source as part of this resolver path. An SVG-to-editable-shapes conversion remains separate unfinished work.

Alternatively, a resolver for an asset declared `image/svg+xml` can return `{ bytes: fallbackPng, mimeType: "image/png", svgPair: svgBytes }`. PPTKit emits the PNG or JPEG as the base picture and the SVG as a separate embedded Office SVG extension, shared across uses with relationships from each owning part. The two byte arrays count together against `maxAssetBytes`, are copied on receipt, and cannot use shared memory; an empty SVG, unsupported fallback or conflicting conversion declarations reject the asset. The exporter does **not** parse, sanitize, validate or execute SVG, verify that both images correspond, fetch external resources, or adjust authored geometry. `asset-svg-pair-unverified` is always emitted. Callers must supply trusted, self-contained, compatible SVG and a matching fallback; mismatches can produce different visuals across applications. Other applications may handle SVG, fonts, animations or external references differently. A named [LibreOfficeDev probe](../testing/svg-pair-libreoffice-probe.md) covers one intentionally mismatched pair: its first save replaced the blue fallback with a red raster, and three headless reopen cycles retained the SVG. A [PowerPoint save/reopen observation](../testing/svg-pair-powerpoint-evidence.json) for a deliberately mismatched red SVG and blue PNG also displayed red and rewrote the paired fallback to red, while a blue PNG control stayed unchanged. This is one opaque sample, not general application parity. A [cross-package test](../../scripts/svg-pair-crop-replacement.test.mjs) verifies cropped, rotated and flipped paired pictures through per-image replacement, fresh export/import and undo while a shared paired picture remains intact; it does not test native crop editing or SVG/raster equivalence.

The browser test rasterizes a self-contained red/blue SVG through Chromium Canvas, verifies both pixels, then checks the exact PNG bytes packaged by the resolver with no network requests. It does not establish safety for arbitrary SVG or parity for fonts, animations, external resources or other browsers.

Automated tests compare this resolver path with a PNG control for authored frame, crop, rotation and flip, and compare Chromium global output and budget failures with Node. These checks use caller-provided image bytes, not a real metafile conversion or native visual verification. A converter must produce dimensions and content consistent with the authored geometry; conversion does not change the geometry or rerun layout.

A [LibreOfficeDev conversion probe](../testing/metafile-rasterization-probe.md) demonstrates that a successful default EMF/WMF-to-PNG conversion may include a whole page around the image. A converter adapter needs an explicit extent and scaling policy; a successful process exit is not enough to establish geometry fidelity.

Existing URL/path sources retain their loading and MIME inference behavior; they do not acquire universal signature verification through this change. To require the new signature-checked profile for remote/local data, provide an explicit export resolver. A browser may fail to decode malformed image content even if its header is recognized; successful signature classification alone is not a visual guarantee.

`inspectPng(bytes, options?)`, available in the default, Node and browser exporter entries, inventories dimensions, bit depth, color type, interlacing, IDAT byte count, animation-related chunk presence and unknown critical chunk names. It checks signature, chunk length and CRC, core ordering, IHDR fields and bounded palette structure. `maxBytes` (default 64 MiB), `maxChunks` (default 100,000) and pre-aborted signals bound inspection. Input is copied after the size check; shared-memory-backed inputs are rejected to prevent concurrent mutation during capture. It does not decompress IDAT, validate pixel data, check ancillary/APNG semantics, or guarantee renderability. Unknown critical chunks are reported, not interpreted. This is an explicit opt-in inspection and does not change asset loading or export acceptance. See the [W3C PNG specification](https://www.w3.org/TR/png/) for the chunk format.

When one or more `iCCP` chunks occur, `inspectPng` and the PNG result within `inspectApng` also expose `iccProfileChunks`, their count. The field is absent when none are present. These inventories check chunk CRCs, but do not validate placement, multiplicity, compression, profile contents or color behavior. With `pngDiagnostics: "warn"`, a detected chunk emits `png-icc-color-unverified` once per asset. Export diagnostics also check the ICC envelope described below and emit `png-icc-inspection-incomplete` when that check fails, including when its limits are exceeded. Both warnings can occur for the same asset; media bytes remain unchanged. The repository-authored PNG fixture `tests/fixtures/png-icc-srgb.png` (SHA-256 `5bcb073c26860a55495b9ac7c095e6195e35b92b9041e0c42f50e26ac4316fba`) uses the same Pillow-generated sRGB profile as the JPEG fixture. This is a container and diagnostic test, not proof of rendering or color fidelity.

`inspectPngIcc(bytes, options?)` adds an explicit envelope check: it checks PNG framing and CRC as described above, then checks `iCCP` multiplicity and placement before palette/image data, the 1–79 byte printable Latin-1 profile name and spacing, method 0 and nonempty compressed data. It returns the profile name and compressed byte count when present, plus presence flags for `sRGB` and `cICP` without resolving their precedence or validating those chunks. `maxCompressedProfileBytes` defaults to 16 MiB; `maxBytes`, `maxChunks` and `signal` retain the PNG inspector semantics. The opt-in export diagnostic uses the same envelope checks and limits, with an additional synchronous scan of captured PNG bytes. Neither path decompresses the zlib stream or validates the ICC profile or color space; export warnings do not themselves reject or modify media. These boundaries follow the [PNG chunk specification](https://www.w3.org/TR/png-3/).

Node consumers can explicitly call `extractPngIccProfile(bytes, options?)` from `@pptkit/pptx-exporter/node`. It checks the same envelope, inflates the zlib stream using Node's zlib, checks its checksum and rejects trailing bytes. `maxProfileBytes` defaults to 16 MiB and limits the expanded result; the returned profile bytes are detached. An absent `iCCP` returns no profile bytes. This is synchronous and cannot be interrupted during decompression; a pre-aborted signal rejects. The limit does not cap every allocation inside Node's zlib. Neither successful decompression nor the profile name establishes ICC validity, safety, color space or rendering fidelity. See [Node zlib documentation](https://nodejs.org/api/zlib.html) for the underlying runtime.

Browser consumers may explicitly call `extractPngIccProfileInBrowser` from `@pptkit/pptx-exporter/dom`. It uses the browser's `DecompressionStream("deflate")`, checks cumulative output before retaining each chunk, returns detached bytes and cancels the reader on failure or cancellation. The output limit is checked after a browser-produced chunk arrives and cannot limit allocations internal to the decoder or that chunk. A browser without `DecompressionStream` rejects when extraction is needed; an image without `iCCP` returns without invoking a decoder. Chromium has been checked against Node with the real profile, malformed checksum, truncation, trailing data, a decompression bomb and cancellation. Other browser engines are unverified. The [Compression Standard](https://compression.spec.whatwg.org/) defines zlib checksum and trailing-input handling. Neither adapter fetches resources or changes export behavior.

`inspectIccProfile(profileBytes, options?)` is a separate opt-in header and tag-directory inventory for extracted or caller-supplied ICC bytes. It checks exact declared length, the `acsp` signature, bounded tag-table size, unique tag signatures, aligned in-bounds nonempty tag extents and partial overlaps. Different tags may reference exactly the same data. The result reports raw four-byte signatures, major version and tag offsets/sizes; `maxBytes` defaults to 16 MiB and `maxTags` to 4,096. Input is captured before inspection, shared-memory views reject, and work is synchronous. This is not complete [ICC profile validation](https://www.color.org/specification/ICC.1-2022-05.pdf): tag payloads, version-specific requirements, color transforms, profile IDs, padding, licensing and rendering are not interpreted. It is not run automatically during extraction or export.

`inspectApng(bytes, options?)` first performs the same PNG checks, then inventories an optional animation's frame rectangles, raw delay numerator/denominator, disposal and blend values, play count and whether the default image is its first frame. It checks the explicit control/data chunk sequence, frame count and bounds, and frame-data presence, with a separate `maxFrames` limit (default 10,000). A zero delay denominator is retained as zero; callers may apply the PNG-defined 100 denominator. It does not decompress or composite frames, interpret other ancillary chunks, prove playback, or change exporter acceptance. A static PNG returns no `animation` field.

GIF and JPEG EXIF inspectors also copy inputs after their configured byte and structural option checks, and reject shared-memory-backed inputs. This prevents concurrent source mutation during inspection; byte limits apply before the copy.

`inspectJpegIcc(bytes, options?)` inventories recognized pre-first-scan JPEG APP2 ICC chunks. It reports no recognized profile, complete chunk numbering, or missing sequence numbers, together with the expected and received counts, total chunk payload bytes and whether it stopped at the first scan or EOI. Out-of-order chunks are accepted; duplicate, inconsistent or invalid sequence metadata rejects. It does not assemble, validate or interpret the profile, inspect later scans, decode pixels or perform color management. `maxBytes` (64 MiB), `maxSegments` (100,000) and `maxProfileBytes` (16 MiB) are positive safe-integer bounds; inputs are copied and shared-memory views rejected. A no-profile result means no recognized pre-scan ICC chunk, not that no color metadata exists. The [ICC profile specification](https://www.color.org/specification/icc1v43_2010-12.pdf) describes the APP2 chunk convention.

`extractJpegIccProfile(bytes, options?)` uses the same bounds and captured input, reassembles complete pre-scan ICC chunks by sequence number, and returns detached `profileBytes` with the inspection. It returns no profile bytes when no chunk is recognized, and rejects incomplete or duplicate chunks rather than returning a partial profile. It does not inspect later scans or validate the extracted ICC data; callers can separately use `inspectIccProfile` for its limited directory checks. Node and Chromium tests compare the real JPEG profile with the separately extracted PNG profile and exercise shuffled chunks and missing data.

Exporter option `jpegIccDiagnostics: "warn"` reports `jpeg-icc-color-unverified` for complete recognized chunks and `jpeg-icc-inspection-incomplete` for missing, malformed or over-budget metadata; original image bytes remain unchanged. The default is `"off"`. A repository-authored 6 × 4 JPEG with Pillow-generated sRGB ICC data (`tests/fixtures/jpeg-icc-srgb.jpg`, SHA-256 `ce478c3cdc7e2cfca2d36542d1025631316e602e8bad3d25b7f198132b3b5189`) tests a real profile container, not color fidelity. Synthetic chunks test sequencing and limits; Chromium/Node parity tests do not establish rendering agreement.

A [LibreOfficeDev save/reopen probe](../testing/jpeg-icc-libreoffice-probe.md) compares the tagged image with the same JPEG scan data after removing its ICC segment. PPTKit emits separate media, while this LibreOffice version's first save makes both picture relationships point to the tagged JPEG. This shows why application round trips must not be assumed to retain distinct color metadata, even when a sampled pixel looks unchanged.

Exporter option `pngDiagnostics: "warn"` opts into that bounded check for loaded PNG assets. A structurally recognized APNG produces `apng-animation-playback-unverified`; malformed or over-budget input and unknown critical chunks produce `png-inspection-incomplete`. Warnings identify the asset and are emitted once per packaged asset. Media bytes are preserved even when inspection is incomplete; inspection does not prove decoding or application playback. The default `"off"` keeps existing behavior. A resolver's explicit first-frame declaration remains a separate caller assertion.

Use `pngDiagnostics: "reject-structure"` to omit PNG/APNG media when the bounded inspection fails, when the base PNG has no IDAT payload, when a critical chunk is unknown, or when the loaded MIME or extension disagrees with PNG bytes. This applies to the packaged base image, including resolver fallbacks. The exporter reports `asset-read-failed` and `image-omitted` for affected uses, while retaining other assets. Valid APNG and ICC diagnostics still apply. The limits are 64 MiB, 100,000 chunks and 10,000 animation frames per image; the check does not decompress IDAT/fdAT, certify ICC contents, or establish native playback. An invalid ICC envelope is still a warning.

`pngDiagnostics: "reject-scanlines"` also validates the zlib stream and exact scanline lengths and filter types for the base image and each APNG frame, including Adam7 interlace. It reconstructs indexed rows to check palette references. The total decoded scanline budget is 128 MiB per asset, including all animation frames; excess dimensions or output omit that image. The runtime must provide `DecompressionStream("deflate")`; missing support omits affected images with a diagnostic. This strict mode also rejects unused bytes after the zlib stream, including final-IDAT padding that tolerant PNG decoders may ignore. This does not render pixels, validate color profiles, or certify native animation playback. See the [PNG specification](https://www.w3.org/TR/png/) and the [Compression Standard](https://compression.spec.whatwg.org/).

SVG preview reports `apng-preview-playback-unverified` once per slide and requested asset explicitly declared `image/apng`; actual animation and timing depend on the viewer and any resolver. Opt-in `pngAnimationDiagnostics: "warn"` also scans byte-backed PNGs for an animation declaration before the first IDAT, including assets declared `image/png`. The scan is limited to 8 MiB and 100,000 chunks and does not check CRCs, frames or pixels; malformed or over-budget data report `png-preview-inspection-incomplete`. Resolver output and non-byte sources are not fetched or inspected: declared PNG/APNG assets report that inspection was incomplete. Undeclared URLs cannot be identified as PNG by this option.

The [two-frame fixture](../../tests/fixtures/two-frame-apng.png) was created with Pillow 12.1.1 from 3×2 red opaque and blue half-transparent RGBA images, with delays 100 and 250 ms and two plays; its SHA-256 is `880fc96f95e86ec26d9f8555584a2be40793cb2766e031eaeb9bdb84196f6af2`. Tests inspect its serialized frame controls plus synthetic default-image and malformed-sequence cases. This is producer evidence for structure only, not cross-application animation playback evidence.

## Optional JPEG EXIF orientation inspection

`inspectJpegExifOrientation(bytes, options?)` in the default, Node and browser exporter entries reads the primary image's EXIF orientation tag (0th IFD tag 274) from an `Exif\0\0` APP1 segment before the first JPEG scan, following the TIFF byte order and SHORT/count-one representation described by the [CIPA Exif specification](https://www.carlseibert.com/wp-content/uploads/2021/02/Exif_standard_2019_DC-008-Translation-2019-E.pdf). It reports `orientation` 1–8, `no-orientation`, or `no-exif`, and whether parsing stopped at the first scan or EOI. It rejects duplicate EXIF segments or orientation tags, invalid values/types/offsets, and out-of-bounds marker lengths. Non-EXIF APP1 is skipped. This is a deliberately bounded pre-scan inventory: later metadata, thumbnail orientation, ICC, pixel validity and actual JPEG rendering are not inspected. Absence before the first scan is not a claim about all later markers.

`maxBytes`, `maxSegments` and `maxIfdEntries` are positive safe integers, defaulting to 64 MiB, 100,000 and 65,535. An already aborted signal rejects; synchronous work cannot be interrupted by an event-loop callback during the scan. This opt-in function does not rotate pixels, alter geometry, fetch, or change the existing export/preview policy. Consumers must choose orientation normalization or retain bytes themselves; byte preservation alone does not establish native/preview orientation agreement.

A [named native/preview comparison](../testing/jpeg-orientation-native.md) found that PowerPoint 16.104 displayed the raw pixel layout while Chromium applied EXIF orientation 6. This is a verified mismatch for that sample, not a universal application claim.

## Optional GIF structure inspection

`inspectGif(bytes, options?)` is available from the default, browser and Node exporter entries. It reads the logical screen, image frame rectangles, graphic-control delays in centiseconds, disposal and transparency, interlace flags, and recognized Netscape/ANIMEXTS repeat counts (`0` means infinite). A frame's optional `userInputFlag: true` records the GIF89a control bit; with a delay, the specification allows input or expiry to continue processing, but actual application behavior is not verified. Disposal values 4–7 are reserved and remain observable as numeric source values; nonzero reserved high bits are reported as `reservedControlBits` in their original bit positions. The opt-in export diagnostic warns about these conditions, including on a single frame. An absent loop extension leaves `loopCount` undefined; zero frame delay is reported as zero, without guessing browser playback timing. The input is not mutated. This synchronous operation does not decompress LZW, validate pixels or palettes, render frames, derive total playback time, or certify native playback. Plain-text graphics consume their graphic control but are not reported as image frames; `plainTextBlocks` counts them. `unknownExtensionBlocks` counts skipped unrecognized application and extension blocks; comments are recognized and excluded. Those optional counts are absent when zero. Truncated, out-of-screen and unsupported structural forms reject rather than returning a partial result.

`maxBytes`, `maxFrames` and `maxBlocks` are positive safe integers, defaulting to 64 MiB, 10,000 and 1,000,000. Sub-blocks count toward the block budget. An already aborted `signal` rejects with its reason; synchronous inspection cannot be interrupted by an event-loop callback while running. Inspection is explicit and does not alter existing export/preview behavior, fetch data, or choose a poster. Use frame count and loop metadata to inform an application-owned fallback policy; actual decoding and playback remain unverified.

## Opt-in export diagnostics

Set `gifDiagnostics: "warn"` on `generatePptx` or `writePptx` to inspect each loaded GIF asset with the default GIF budgets. A multi-frame image emits one `gif-animation-playback-unverified` warning per packaged asset: the original bytes are preserved and actual playback and timing depend on the application. A malformed, unsupported or budget-exceeding GIF, or one containing plain-text graphics or unrecognized extension blocks, emits `gif-inspection-incomplete`; it is not classified as static and is still packaged under the existing asset policy. Registered assets are inspected even if unused; repeated uses of one asset share the warning. Inspection uses the loaded bytes, including resolver and Node path results, and cancellation still aborts export.

Set `gifDiagnostics: "reject-lzw"` to omit GIFs whose frame data or supported container structure fails validation. It checks the LZW dictionary, end code, exact frame index count, active color table and transparency index, with a total budget of 128 MiB of decoded indices per asset. It rejects extra full bytes after the end code; padding bits in the last byte are allowed. The verifier does not allocate a decoded raster. Failed assets report `asset-read-failed` and their uses report `image-omitted`. Valid animation and unverified-extension warnings still apply; the option does not render frames, validate compositing or prove playback. Some tolerant readers display frames missing an end code; this mode rejects them. See the [GIF89a specification, Appendix F](https://giflib.sourceforge.net/gifstandard/GIF89a.html#lzw).

Set `jpegOrientationDiagnostics: "warn"` to inspect loaded JPEG assets before packaging. EXIF orientation 2–8 produces one `jpeg-exif-orientation-unverified` warning per asset; malformed, unsupported or budget-exceeding pre-scan data produces `jpeg-exif-inspection-incomplete`. Original bytes are still packaged, including on an incomplete inspection. Orientation 1 or no recognized pre-scan orientation produces no orientation warning, which is not proof of a valid image or absence of later metadata. Registered but unused assets are also inspected; resolver and Node path results use the same policy. The option defaults to `"off"` and invalid modes reject. It does not rotate pixels or guarantee consistent display between applications.

Set `jpegValidation: "structure"` to omit a JPEG when its complete marker stream cannot be verified. The bounded profile admits standalone Huffman DCT images (baseline, extended sequential or progressive) with in-file tables, including supported multiscan images. It checks dimensions, component and table references, progressive scan order, byte stuffing, restart marker order and an exact end marker. The limits are 64 MiB and 100,000 markers per image. Lossless, arithmetic, hierarchical, abbreviated and DNL-based JPEGs are outside this profile; metadata payloads, entropy coefficients, restart interval spacing and decoded pixels are not validated. Failed assets report `asset-read-failed` and their uses report `image-omitted`; passing images retain their original bytes. The option is independent of EXIF and ICC diagnostics and is off by default. See [ITU-T T.81](https://www.w3.org/Graphics/JPEG/itu-t81.pdf).

The default `"off"` preserves prior warnings and output; invalid modes reject. The diagnostic does not claim animation was lost, detect all GIF visual effects, render pixels, create a poster, or prove playback. It also does not change preview behavior or inspect non-GIF formats. Static-first-frame resolvers can explicitly report the conversion as described below.

## Export resolver

Both the default and Node exporter entries accept these optional `GeneratePptxOptions` fields:

- `resolveAsset: PptxAssetResolver`: receives a detached, frozen asset request and a frozen context containing the optional signal. Returns `{ bytes: Uint8Array, mimeType?: string, animationFallback?: "first-frame", orientationNormalization?: "pixels" }`, synchronously or asynchronously, or `undefined` to omit.
- `signal: AbortSignal`: cancels generation, including waits for resource resolution. Abortion rejects with the signal reason and never becomes a successful package with omission warnings.
- `maxAssetBytes: number`: positive safe-integer per-asset byte limit. No limit is imposed by this option when omitted, preserving existing loading behavior.

When a resolver converts an animated source to a static first-frame PNG or JPEG, it may report `animationFallback: "first-frame"`. A successful load then emits one `asset-animation-flattened` warning for the asset, independent of `gifDiagnostics`; the resolver is responsible for the truth of this declaration and for conversion. PPTKit does not inspect the original bytes, establish that the image is the first frame, or validate complete PNG/JPEG contents. Missing declarations cannot be inferred from the converted output. Other values or GIF output with this declaration fail the asset read and produce no loss claim. Existing declared asset MIME constraints still apply to resolver output: a source declared as `image/gif` cannot be replaced with PNG under this resolver contract without changing that declaration.

A resolver that has already applied a JPEG's EXIF orientation to its pixels may return `orientationNormalization: "pixels"` with PNG or JPEG output. This explicit declaration allows a source declared `image/jpeg` to produce PNG; a declared source of another MIME rejects. The returned MIME, when present, must match the output signature. The exporter emits one `asset-orientation-normalized` warning per loaded asset because bytes or metadata may have changed. It does not decode either image or verify that the conversion is correct: the resolver attests to it. JPEG output is additionally checked with the bounded pre-scan inspector and is rejected if its recognized EXIF orientation remains 2–8 or the check fails; PNG gets signature classification only. This declaration cannot be combined with `animationFallback`. Existing `maxAssetBytes` applies, and normalized JPEG inspection has its own default 64 MiB and structural budgets.

### Explicit browser normalization

`normalizeJpegOrientationInBrowser(bytes, options?)` is available from `@pptkit/pptx-exporter/dom`. It snapshots supplied JPEG bytes, requires a recognized pre-scan EXIF orientation and frame dimensions, asks the browser to decode with `imageOrientation: "from-image"`, and returns PNG bytes, oriented dimensions, source orientation and `orientationNormalization: "pixels"`. The result can be returned directly from a JPEG asset resolver. This is opt-in and needs a browser document, `createImageBitmap` and Canvas 2D; it performs no network request. The [HTML specification](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html) defines the image orientation option.

The installed `/dom` entry points to the self-contained browser module, so it
does not require a separate import-map entry for the shared media-inspection
package. Importing the module itself remains safe without browser globals.

```ts
import { normalizeJpegOrientationInBrowser } from '@pptkit/pptx-exporter/dom';

const normalized = await normalizeJpegOrientationInBrowser(jpegBytes, {
  maxPixels: 20_000_000,
  signal,
});
// A resolveAsset callback for this JPEG can return normalized.
```

The caller must use the returned width and height to decide its own frame, crop and fit policy; the exporter does not rewrite them. Input, declared frame pixels and output are bounded by positive safe integer `maxInputBytes` (default 64 MiB), `maxPixels` (40 million), and `maxOutputBytes` (128 MiB). The pixel check precedes decoding and checks decoded dimensions afterward; it is not a guarantee about allocations inside a browser decoder for malformed images. The output limit is checked after the PNG blob is encoded. Cancellation stops waiting, but cannot forcibly interrupt browser decoding; a bitmap that arrives later is closed. Synchronous work is not preempted.

For a crop authored in the **raw JPEG pixel coordinate system**, `orientJpegCrop(crop, sourceOrientation)` maps its four fractional edges into the coordinate system of the oriented pixels. It is available from the default, browser, Node and DOM exporter entries. It returns a detached crop and rejects invalid orientations, non-finite or out-of-range edges, and crops with no visible area. For example, a raw top-left crop becomes a top-right crop under orientation 6. Use this only when the input crop refers to raw pixels; applying it to a crop already expressed in oriented coordinates transforms it twice. It preserves the selected source region, not the original on-screen orientation or aspect ratio. Supply the oriented asset dimensions before layout and select the desired frame and fit separately. `contain` and `cover` are resolved from registered asset dimensions before the export resolver runs; merely returning new bytes and dimensions from a resolver does not recompute layout.

Canvas encoding and color conversion are browser-owned: original JPEG metadata and ICC behavior are not guaranteed to survive. Chromium has been tested for all eight orientations; other browsers, broader crop and fit modes, color fidelity and native save/reopen remain unverified. A named orientation-6 crop has a [PowerPoint comparison](../testing/jpeg-orientation-native.md#exif-6-mapped-crop-in-powerpoint). See the [named native comparison](../testing/jpeg-orientation-native.md).


The conversion does not update asset dimensions, authored frame, fit, crop or other references. For non-stretch output, callers must supply dimensions/crop consistent with the normalized image and verify the result. A [named PowerPoint comparison](../testing/jpeg-orientation-native.md) shows this explicit path corrects the prior orientation-6 mismatch for a stretched sample, not a general crop or color-fidelity guarantee.

A supplied resolver owns resolution for **all registered assets**, including byte sources. There is no fallback to default fetching or filesystem access when it returns undefined or fails. Failures remain located `asset-read-failed` warnings; an undefined result deliberately omits the resource. The resolver's declared MIME and the asset's declared MIME must agree with the recognized signature, except for the explicit JPEG orientation-normalization, vector-rasterization and SVG-pair declarations above. Returned bytes are copied when consumed. The same resolver API works in Node and browsers; it cannot import a Node adapter into the browser bundle implicitly.

Options and the document snapshot are captured before asynchronous asset work. Callback requests cannot mutate the export's authoritative normalized asset. Resolver work is not globally cached and overlapping exports have independent output state. Callers must keep returned buffers stable until consumed; the exporter cannot reverse modifications that occur before it observes a resolved promise.

## Budgets, cancellation and ownership

For stored bytes, the decoded size is checked before allocation. Resolver results are checked before copying. URL bodies are read in chunks and their cumulative length is checked rather than trusting Content-Length; excess data cancels the reader. Node uses a regular-file handle, checks its size and cumulative reads, and closes it on success/failure. The per-asset cap does not bound aggregate deck memory, response chunk allocation, Core Base64 storage, caller resolver allocations or final ZIP memory.

Cancellation stops waiting even when a third-party resolver never settles. Late fulfillment/rejection cannot produce output or an unhandled rejection. The caller's resolver still owns its ongoing I/O and should observe the provided signal to release resources; the exporter cannot forcibly terminate arbitrary callback code. Default fetch receives the signal, and stream readers/file handles are cleaned up. Normalization, encoding and ZIP creation remain synchronous and are not preemptible mid-operation.

`writePptx` uses these options for generation; file write atomicity and cancellation after generation are separate output-adapter concerns. Preview URL resolvers retain their existing contract; this export cancellation option does not add a playback or preview cancellation API.

### External audio and video

The separate `resolveMedia` export option explicitly supplies bytes for referenced audio/video assets whose Core source is a path or URL. It receives a frozen detached asset request and `{ maxBytes, signal? }`; `maxBytes` is the smaller of `maxAssetBytes` and 64 MiB (64 MiB if omitted). Return `{ bytes, mimeType? }`; undefined, exceptions, incompatible MIME, shared memory, excess bytes or invalid media reject the entire generation. The returned typed-array view is copied and checked against the same enabled WAVE/MP4 profile as embedded media. Each external asset is resolved once per generation and shared by its references. Byte-backed media continue to bypass the callback, and image `resolveAsset` retains its separate behavior. Shape/profile checks and embedded media validation precede media resolution; poster resolution occurs later. Cancellation stops waiting for a non-cooperative resolver, which remains responsible for its own I/O and cleanup. Import only inventories external media and does not fetch or project them; callers must explicitly create or map an external Core asset to use this export path. No media fetch or path access happens without a resolver.

For explicitly authorized HTTP(S) URL sources, `createHttpMediaResolver({ authorizeUrl, maxRedirects? })` is an optional adapter usable as `resolveMedia`. It calls `authorizeUrl` before each normalized request URL, sends no credentials or referrer, rejects URL credentials and fragments, and follows at most the configured number of redirects (default zero; maximum ten). Only an accessible HTTP 200 body is accepted. It counts actual response-body bytes, including after HTTP decompression, without trusting Content-Length, cancels a failed stream, and propagates the export signal. Concrete HTTP MIME is checked by the media profile; an absent MIME or `application/octet-stream` defers to byte inspection. Local-server tests cover redirects, denied destinations, loops, absent length, compressed oversize bodies, cancellation and retry. Chromium exposes manual redirects as opaque, so the adapter rejects those rather than following an uninspectable destination; direct same-origin streaming and size rejection are tested there.

`authorizeUrl` is caller-owned policy, not network isolation: it must account for DNS, proxies, private addresses and changing destinations in the caller's environment. Browser CORS and fetch restrictions still apply. The adapter does not read paths, issue retries, control caller DNS or guarantee that a URL resolves to a particular address; callers needing those policies should provide their own resolver.

The Node entry `@pptkit/pptx-exporter/node` also exports `createFileMediaResolver({ authorizePath })` for path sources. It requires an absolute path and calls the authorization callback with its normalized absolute form before opening. The adapter requires platform `O_NOFOLLOW` and `O_NONBLOCK`, rejects a final symbolic link and non-regular files, checks file size and cumulative reads against `maxBytes`, closes the handle on success or failure, and checks cancellation before and during reads. Local tests cover shared audio, video, rejected files, a FIFO without a writer, cancellation and retry. This rejects only a final symlink: ancestor symlinks, filesystem races, mount behavior, isolation and the effects of opening an authorized path are the caller's responsibility. Use an OS sandbox or a caller-owned resolver when authorization requires a securely confined directory. Platforms without the required flags reject rather than silently weakening this behavior. A custom `resolveMedia` may dispatch explicitly between the HTTP and file adapters when both source types are needed.

## Optional validation for external images

Pass `externalImageValidation: "signature"` to validate built-in URL loads and Node path loads before packaging. It accepts PNG (including APNG), JPEG and GIF signatures and selects the package extension from the bytes. An asset MIME declaration must match, as must a concrete URL response `Content-Type`. Missing HTTP MIME and `application/octet-stream` let the signature decide; filename suffixes are ignored. Mismatches and unsupported signatures report `asset-read-failed` and omit affected images. The mode validates headers, not full image decoding, and does not authorize or block fetching a URL. Existing size limits and cancellation still apply.

Without the option, path/URL behavior is unchanged. Byte-backed sources and explicit resolver results already use their own signature and conversion rules. Use an explicit resolver for SVG pairs or rasterization, which the built-in strict mode does not handle.
