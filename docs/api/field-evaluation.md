# Explicit field evaluation

`evaluatePresentationField(field, context)` evaluates a detached field descriptor and returns its identity, kind and displayed string. `slide-number`, `static-date`, `dynamic-date` and `footer` are distinct kinds; ordinary text is never inferred to be a field. The result is frozen and does not mutate the input or a document.

A slide number requires `pageOrder`, `pageId` and `firstPageNumber`. The order consists of unique caller-chosen occurrence IDs in final output order. Include or exclude hidden slides explicitly; a copied slide, custom-show occurrence or pagination continuation needs its own occurrence ID if counted separately. The function does not infer those policies from a presentation. Invalid or duplicate IDs, absent pages and integer overflow fail.

`fieldContextForSlide(sequence, options)` snapshots a document's actual slide order or a resolved Layout slide sequence, including table continuations. The caller supplies the start number and whether hidden slides count, and can supply a unique slide-ID subset and order for a custom show. Unknown or duplicate IDs and an excluded target fail. Copying or moving slides after the call does not change the returned frozen context; call it again to reflect the new order. It does not add field text to continuation pages.

For a custom show that visits a slide more than once, `fieldContextForOccurrences(sequence, options)` accepts an ordered list of `{ id, slideId }` pairs. Each occurrence ID must be unique even when slide IDs repeat; hidden filtering uses the underlying slide. A Layout result can also serve as the sequence, with continuation slide IDs as sources. Unknown slides, duplicate occurrence IDs and excluded targets fail. These helpers prepare context only; callers decide where and when to insert or refresh static snapshots.

For slide-owned native field runs, `LayoutOptions.fieldRefresh` explicitly refreshes caches after table pagination using final slide order. Supply `firstPageNumber` and `includeHidden`; if a date/time field is present also supply `instantMs`, `locale`, `timeZone` and at least one cache style. This option flows through the existing `layout` option of PPTX generation and SVG preview. It refreshes text boxes, shapes, nested groups, table cells and notes without mutating authoring data; repeated table headers receive their own continuation-page value. When hidden slides are excluded, their slide-owned fields keep their authored caches. Refresh does not insert fields into continuations where none exist.

Refresh updates shared master/layout date and time fields once when their artwork is visible on an included slide: the explicit instant and formatting context are common across pages. Shared ownership is retained in output rather than copying artwork into each slide. Because the definition is shared, a hidden slide using the same definition can also observe its updated date cache even when hidden slides do not count for numbering. Unused, suppressed or hidden artwork is not refreshed.

Refresh rejects visible shared master/layout page-number fields because one shared cache cannot represent different slide values; per-slide overrides remain open. Without pagination rules, `tableSizing` and `intrinsicSizing` measure a detached copy after its fields have been refreshed, because the final page order is already known. With pagination rules, sizing uses provisional refreshed fields and verifies every field in each sizing target against the final output, including repeated table headers and the original row mapping. If any measured target field changes or is missing from an expected fragment after pagination, the operation throws without returning a layout; a different cache or sizing choice is required. Stable values, including shared dates and page numbers that do not change, can be used. This is a conservative check: it does not iterate to solve changed measurements, even when a different value might have identical dimensions. Native applications may subsequently update or rewrite fields independently; refreshed output is a cache, not a guarantee of application display.

Structural inspection reports the source `firstSlideNumber` and `firstSlideNumberDeclared`, distinguishing an absent default from an explicit 1; it accepts the full signed XML integer range and does not imply PowerPoint compatibility. Core documents accept an optional nonnegative safe integer `firstSlideNumber`, with `setFirstSlideNumber(value)` to set or clear it. Normalization and Layout carry it. Import maps an explicitly declared nonnegative value; negative source values remain source-only and are reported unsupported. PPTX generation writes the authored value as `p:presentation@firstSlideNum` when it is 0–9999; an explicit export `firstSlideNumber` overrides it. Both are independent of `fieldRefresh.firstPageNumber`. PowerPoint documents its native number as the starting value plus the slide index minus one, so an explicit cache policy excluding hidden slides need not match native numbering. [Microsoft documents PowerPoint's 0–9999 restriction](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/76016a6d-35f9-47cc-8fc3-8d47ba713bbb) and [slide-index behavior](https://learn.microsoft.com/en-us/office/vba/api/powerpoint.slide.slidenumber). In a [two-slide LibreOfficeDev headless observation](../testing/first-slide-number-libreoffice-evidence.json), the application displayed 1 and 2 instead of the specified 17 and 18, removed the attribute on resave, and rewrote field IDs; this is an application-specific difference. A [PowerPoint observation](../testing/first-slide-number-powerpoint-observation.md) covers starting number 17 and one save/reopen after slide reordering.

An eligible source-preserving text edit leaves the source presentation part intact; automated tests cover three successive edits for an absent declaration, 0, 1, 17 and 9999. Changing the authored starting value blocks source-preserving saves by default. The opt-in [save profiles](first-slide-number-save.md) admit replacing an existing attribute and, with `attribute-v2`, inserting or clearing it. A fresh export builds a new package and carries an imported nonnegative declaration automatically; values above 9999 require an explicit supported export override. A negative source declaration is not projected to Core and remains source-only, with an unsupported finding. An absent declaration stays absent; the full signed source range is not supported for fresh PPTX output.

A dynamic date/time cache requires `instantMs`, `locale`, `timeZone` and at least one explicit `dateStyle` or `timeStyle`. The evaluator never reads the system clock, locale or time zone. Formatting uses the runtime's `Intl.DateTimeFormat` locale data, so exact localized strings can vary across ICU versions; use a controlled runtime when byte-identical output across hosts is required. Static date and footer values are supplied text and need no date context. Missing context and invalid inputs throw `PresentationFieldError` with distinct stable codes.

`materializeFieldText(paragraphs, context)` takes rich-text paragraphs whose runs contain either literal text or an explicit field, and returns `TextParagraphInput` plus a ledger of evaluated field identities, values and paragraph/run indices. The returned content can be supplied to a text element, shape, table cell or notes and follows existing rendering and export paths. Input data is detached; accessors and non-plain data are rejected. Failure returns no partial result. By default this is an explicit **static snapshot**: reevaluate and replace the authored content after a page order or date changes.

An explicit `output: "native"` on a `slide-number` template run requires a UUID field ID and retains the evaluated string as its display cache. The equivalent direct authored run is `{ text: "1", field: { id: "...UUID...", kind: "slide-number" } }`. PPTX emits an `a:fld` of type `slidenum` with that UUID and cached text; SVG displays the cache. Copying retains the field ID. The caller must choose or recompute the cache and the application decides when to update native fields. In [one LibreOfficeDev headless experiment](../testing/native-field-libreoffice-evidence.json), a slide with cache `42` rendered as `Page 1`; three resaves retained a slide-number field, updated its cache to `1` and each rewrote its UUID. This is a sample observation, not a general identity guarantee. A [two-slide PowerPoint for Mac 16.104 observation](../testing/native-fields-powerpoint-evidence.json) displayed updated page numbers and a `datetime3` date; independent XML inspection of three sequential Save As copies found the field types and UUIDs retained. The GUI observations are recorded without retained screenshots; the inspector verifies captured files, not the GUI. A [follow-up native edit](../testing/native-field-edits-powerpoint-evidence.json) cut and pasted the first slide after the second, then inserted adjacent ordinary text in a new copy; each was saved and reopened once. Page numbers followed their new positions, and independent XML plus Parser no-op checks retained the four field IDs and types. The UI screenshots were displayed but not retained, and three edited reopen rounds, other fields and environments remain unverified.

Dynamic date/time runs can also opt into native output. They require a UUID and `updateFormat` independently of the cache styles, locale, time zone and instant. Update intents `application-default`, `month-day-year`, `weekday-month-day-year`, `day-month-year`, `month-day-year-long` and `automatic-month-day-year` map to `datetime`, `datetime1`–`datetime4` and `datetimeFigureOut`. The remaining intents `day-short-month-year`, `month-year`, `short-month-year`, `month-day-year-time-12`, `month-day-year-time-12-seconds`, `time-24`, `time-24-seconds`, `time-12` and `time-12-seconds` map in order to `datetime5`–`datetime13`. These correspond to [Microsoft's documented field types](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/209a8afb-4ce6-4ad9-ad6b-f18da263502e); a consuming application may update the text according to its own environment, so the displayed result can differ from the explicit cache. Direct authored runs specify `{ id, kind: "dynamic-date", updateFormat }` alongside their `text` cache. Native interactive verification beyond the named two-slide sample remains open.

In [one LibreOfficeDev headless date experiment](../testing/native-date-libreoffice-evidence.json), a `datetime3` field with cache `CACHE-1970` rendered as `October 28, 2026`, and three resaves retained `datetime3`, replaced its cache with that value and rewrote its UUID each time. The observed month-first rendering differs from the documented day-month-year description; it is a specific application/runtime observation, not a general formatting or identity guarantee.

The [read-only capture recheck](../../scripts/recheck-native-date-capture.mjs) verifies all four PPTX hashes and compares the projected field UUID, update format and literal cache with that evidence; all four exact no-op saves passed. It does not launch LibreOffice or repeat its resaves.

`importPptx(bytes, { projection: "content", fieldTextProfile: "slide-number-v1" })` opts into a bounded projection of simple slide-number fields in slide text, shapes, table cells and direct notes text. `date-and-number-v1` additionally maps the first six date update types listed above; `date-time-and-number-v1` adds `datetime5`–`datetime13`. The profiles require a braced UUID, exactly one text cache, at most one run-properties element and no other field attributes or element children. The resulting Core run stores the UUID, update intent and literal cache; it does not evaluate the current page number or date. Unsupported or malformed fields remain source-only and are reported as unmapped. Default content imports and earlier profiles keep their existing behavior. No-op save preserves original bytes. Combined with `text-runs-v1/v2/v3`, eligible ordinary runs can be edited while field cache, identity, format and topology remain unchanged; attempts to edit them block the plan. Field source elements are reported as unmapped text bindings, not as scalar write targets. The field profile can be combined with `chartEditSaveProfile: "existing-values-v1"`; supported chart numeric and adjacent ordinary text edits can be saved together while field caches and identities remain protected. Picture edit, master-artwork and diagram-preview profiles remain excluded. Fresh export is a new package and is not source preservation. Node, browser ESM/global, both dialects, three fresh import/export cycles, three adjacent notes-text preservation rounds, and three combined field/text/chart/starting-number rounds in both dialects are tested. A [PowerPoint sample](../testing/field-chart-powerpoint.md) covers three native reorder/save/reopen rounds after a field, adjacent text and chart-value combination. Other native field kinds, inheritance and automatic cache refresh remain open under AUT-08.1.1–.1.3.
