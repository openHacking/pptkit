# Copying slides and elements with references

`document.duplicateSlide(slideId, toIndex?)` and `slide.duplicateElement(elementId, toIndex?)` copy known Core content within the same document. Existing signatures and insertion behavior are unchanged: omitted destination inserts immediately after the source; explicit destinations use the existing insertion index rules. See the [checked example](../examples/copy-references.ts).

## Identity and reference rules

Copies receive fresh document-wide element IDs, including every nested group descendant. Slide copies also receive a fresh slide ID. All destination element IDs are assigned before references are rewritten, so forward references and sibling order do not affect the result. Existing occupied IDs from slides, layouts and groups are avoided.

| Reference | Copying a whole slide | Copying one element or group |
| --- | --- | --- |
| Connector target inside copied content | Remaps to the corresponding copied element. | Remaps when the target belongs to the copied subtree. |
| Connector target outside copied content | Retains its original ID, including shared layout targets. | Retains its original ID; duplicating a connector alone keeps its original targets. |
| Action targeting the copied source slide itself | Remaps to the new slide ID. | Keeps the same slide target because the copy stays on that slide. |
| Action targeting another slide or URL | Keeps its target. | Keeps its target. |
| Image asset, layout or placeholder binding | Retains the shared identity/binding. | Retains the shared identity/binding. |

Slide-action remapping covers element actions, rich-text runs, shape text, table-cell text, nested groups and notes. Plain text, URLs, names, section labels, tags and custom JSON are copied without searching or replacing coincidentally equal strings. Incoming references on objects **outside** the copy remain unchanged; duplicating a shape does not redirect its original connectors to the new shape.

Connector targets must be in the connector's immediate coordinate scope: top-level slide connectors can target top-level slide, selected layout or master objects; top-level layout connectors can target top-level layout or owning master objects; connectors inside a group can target that group's immediate children. A nested group's descendants are not siblings of the containing group. Core validation reports cross-scope references, which cannot be resolved correctly by the current Layout geometry engine. Direct `resolveNormalizedLayout` callers also receive an error for a missing or out-of-scope target rather than an invented origin point.

Shared layout definitions and their inherited content are not duplicated. A layout's own action remains the action stored in that shared definition, even if it targets the original source slide. Asset bytes are not duplicated into another registry entry; subsequent shared-asset replacement affects both original and copy by design.

## State, validation and limits

Copying deep-clones content and stores new immutable views. Original authoring objects and earlier normalized/layout/render results remain unchanged. Invalid source IDs or destination indices reject before inserting content; invalid destinations are checked before allocating copy identities. Removing the original page/group after copying no longer leaves copied internal connector references pointing to removed IDs.

Copying does not repair pre-existing invalid references or expand supported coordinate scopes. An unresolved target outside the copied set remains unresolved and is reported through ordinary validation. Connector geometry still follows current Layout group-local/scope rules. Default connector export remains the existing custom-path representation; an [experimental native straight profile](native-connectors.md) is now available separately. Successful copy tests alone are not proof of native attached-connector editing.

The behavior corrects two previous cases: copied connectors formerly retained old element IDs, and copied self-links formerly targeted the original slide. Applications intentionally linking the copy back to the original should author that explicit target rather than relying on the old copying behavior.

These methods are same-document authoring copy. For resource-only transfers see [cross-document asset copy](asset-lifecycle.md#copy-assets-between-documents).

## Cross-document slide copy

Factory-managed documents also expose `destination.copySlideFrom(source, slideId, options)`. The caller explicitly selects a destination `layoutId` (or `null` for the default layout), `theme: "destination"`, a geometry policy, a custom-data policy, and the [asset-copy policies](asset-lifecycle.md#copy-assets-between-documents). `index` defaults to the end. The destination theme and layout control inherited appearance. `customData: "preserve"` copies supported JSON slide metadata without rewriting embedded references; `customData: "reject"` requires a plain empty custom-data object, rejecting even hidden or symbol properties on custom source objects. Rejecting one page rejects the whole batch before pages or assets commit. This is not inspection of arbitrary preserved PPTX structures or a proof that empty custom data contains no other unsupported references.

With `geometry: "preserve"`, authored coordinates stay in points. `"fit-explicit-geometry"` uniformly scales the source page to fit the destination page, centered on the unused axis, and transforms explicit top-level boxes, free connector endpoints/routes, and authored table column widths and row heights. Nested group coordinates and group coordinate sizes remain local; the group's explicit outer box is transformed. An element without an explicit box continues to use its target placeholder or other normal defaults. Text font sizes, margins, stroke widths, implicit table row heights, inherited artwork and target placeholder geometry are not scaled. The policy does not promise that text fits or that the entire visual appearance scales uniformly. Layout diagnostics and application-specific overflow review remain necessary, especially for smaller pages, missing boxes, or external connector targets. Tests demonstrate that `resolveLayout` with `diagnostics.textOverflow` can flag a fitted frame that became too short with either synthetic metrics or an explicitly loaded browser font; without a provider it reports measurement unavailable. The browser test uses a 1.1-point tolerance for a one-point ascent beyond its CSS line box. Browser measurements do not establish the target application's font rendering.

A closed round connector retains its mode and matching endpoints when its geometry is fitted; its stroke width and opacity remain unchanged under this geometry-only policy. An integration test also checks the closing segment's selection hit, PPTX closure and reimport. Editing just one endpoint breaks the closed-path invariant and produces a validation error until the endpoints match again.

`slideLinks` maps each action targeting another source slide to an existing destination slide. Self-links and internal connector targets are remapped automatically. `connectorTargets` explicitly maps external targets to existing top-level objects in the selected destination layout or master; missing mappings, newly allocated copied identities and targets outside the connector's coordinate scope reject. `placeholders` and `textPresets` may map source names to destination names; omitted entries retain their names and must exist in the selected destination layout or preset collection. Image assets are copied or deduplicated according to the supplied policies. The result exposes the inserted slide, source-to-destination element IDs and asset mappings. A failure leaves the attempted slide, resources and generated IDs uncommitted; independently reentrant caller mutations remain in place.

Shared `slideLinks`, `connectorTargets`, `placeholders` and `textPresets` mappings are captured as plain enumerable data before source capture; accessors, hidden fields, symbol keys and invalid targets reject. Mutating a supplied mapping during source access does not change the in-flight operation. The same rule applies to the mapping options of layout and master copies.

Layout copy reads the source layout collection once, validates that captured value as an array, and selects from it. A getter that returns a different collection on a later read cannot change which collection is used for the operation.

Optionally set `placeholderRoles: "require-match"` to require every copied placeholder binding to exist in the source page's layout and to have the same role in the selected destination layout. This also checks explicit and per-slide mappings; missing source definitions, duplicate source keys, ambiguous target keys, invalid roles and role changes reject the entire operation. In this mode indexes may differ. `"require-match-and-index"` additionally requires equal explicit unsigned 32-bit indexes on each bound pair and rejects duplicate source indexes or a duplicate destination index for a bound target. Missing indexes are not invented from array positions. Omit this option to retain the existing key/mapping behavior, including deliberate role changes. These checks do not copy a source layout or prove visual compatibility of placeholder styles and dimensions.

With `placeholderRoles: "require-match-and-index"`, callers may additionally set `placeholderMatching: "explicit-index"`. For each binding without an explicit mapping, the source placeholder's explicit index selects exactly one placeholder in the chosen destination layout, even if its key differs. Role and index validation still applies. Per-slide mappings take precedence over shared mappings, which take precedence over automatic matching; explicit mappings do not bypass the strict checks. Missing or duplicated indexes, absent source definitions and role conflicts reject the entire batch. This mode never uses generated ordinals, defaulted native indexes or a same-name guess as a substitute for an authored index.

A cross-package control compares automatic index matching with explicit per-page mappings for a two-page deck containing both boundary indexes, page links, notes and a shared image. It verifies equal Core results and byte-identical uncompressed OOXML parts after source removal; this is a generated-output equivalence check, not an additional native interaction test.

During one batch, destination placeholder keys and indexes are indexed once per selected layout and reused across copied pages. A correctness test covers two pages with 900 renamed bindings against a reversed destination definition; it is not a performance benchmark or a bound on validation cost.

A two-page strict-index fixture with distinct destination layouts and indices 0 and 4294967295 was inspected independently across [PowerPoint for Mac](../testing/copy-placeholder-index-powerpoint-evidence.json) and [LibreOfficeDev](../testing/copy-placeholder-index-libreoffice-evidence.json) saves. Generated slide and layout parts explicitly contain both indexes. After the first PowerPoint save, the title's `idx="0"` attribute is absent and the body retains `idx="4294967295"`; these raw attributes remain so through the next two saves. LibreOfficeDev removes both `idx` attributes on its first save, and its saved slide body also omits the placeholder `type` attribute. The PowerPoint captures show both pages and their notes after each reopen; the final LibreOffice PDF contains both pages' text. Attribute absence is recorded separately from a numeric zero; these observations do not establish interactive placeholder behavior or general identity preservation across applications. The [PowerPoint inspector](../../scripts/inspect-copy-placeholder-index-powerpoint.py) and [LibreOffice runner](../../scripts/inspect-copy-placeholder-index-libreoffice.mjs) record the actual files and relationships.

In the [parser comparison](../testing/copy-placeholder-index-import-evidence.json), content projection reports the absent PowerPoint title indexes as defaulted zero with one parent candidate, while the maximum-index body remains explicit and matched. For all three LibreOffice-saved files, both page placeholders default to zero and each has two layout candidates; the report marks the parent match ambiguous and assigns a fallback finding instead of choosing a candidate. All eight inspected files retain byte-for-byte output through no-op save. These findings concern the named files and do not grant edit-aware preservation or establish native placeholder semantics.

The operation copies authored Core content, including notes and supported slide timelines. It does not automatically copy the bound layout or master, infer source theme adaptation, scale inherited styles, rewrite arbitrary custom-data references, or grant authority to edit imported OOXML. Native observations are limited to the fixtures below; broader cross-document reconciliation remains unverified and AUT-09 remains open.

`destination.copySlidesFrom(source, slideIds, options)` copies a nonempty, distinct ordered selection in one transaction. Links between selected pages, including links in notes, are remapped after all destination slide identities have been allocated; other page links require `slideLinks`. The same policies apply as for single-page copy. `layoutId` supplies the default destination layout, and `layouts` can select a different destination layout or `null` per source slide. `perSlide` can override individual placeholder, text-preset and connector-target mappings for a selected source page; entries not overridden fall back to the shared mapping. Both `layouts` and `perSlide` must be finite plain data with enumerable data properties; accessors, hidden or symbol properties, unknown page keys and invalid overrides reject. The result contains ordered slides, slide and per-slide element identity maps, and resource mappings. Any invalid member or stale destination aborts the whole batch.

Source slide identities are indexed once and the destination tail is appended once, avoiding repeated full-source searches and repeated middle insertions. A 1,200-page reversed cyclic-link test covers order and identity correctness; it is not a performance benchmark or a guarantee for arbitrary asset or content sizes.

The cross-document operations detect destination slide membership/order, resource registry, element-ownership and shared-definition changes made reentrantly during capture, including changes to empty layouts. They reject their own attempted copy; a separate change made by caller code is retained. Changes to unrelated slide-local metadata are not a document-wide lock.

`destination.copySlideLayoutFrom(source, layoutId, options)` separately copies a layout's placeholders, background and authored artwork. Supply a new destination `id`, `masterId` (an existing destination master or `null`), `theme: "destination"` and asset policies. `slideLinks` maps layout action targets; `textPresets` maps artwork and placeholder presets; `connectorTargets` maps external artwork connector targets to objects in the selected destination master. Resources and identities are staged together and invalid layouts or affected slides reject before commit. The source master is not copied automatically and destination theme and master inheritance may change appearance.

Set `reuseEquivalent: true` to reuse the first existing destination layout in definition order when its complete ordered definition, selected master, mapped assets, actions, placeholders and artwork match exactly after owned element IDs and connector references are remapped. All copied assets must already exist in the destination. The returned `layout.id` may then differ from the requested new `id`, and `elementIds` maps source identities to the reused elements. The requested ID must still be available. No staged assets or element IDs are committed on reuse. Slides using the reused layout share it, so later edits to that layout affect all of them. A difference creates a new layout as before; omission or `false` retains the original always-copy behavior. Equivalence is structural, not a visual comparison or general semantic equivalence of different native structures.

Regression coverage includes nested connectors, different external master targets and page actions, resource metadata changes, first-match selection and a 300-element forward-reference graph with a late mismatch. Node and browser ESM/global also agree on a nonempty layout with an owned connector. These tests do not establish a general performance bound.

In a [LibreOfficeDev headless observation](../testing/cross-layout-reuse-libreoffice-evidence.json), two copied pages shared one reused layout and master after each of three saves. Page text, notes backlinks, the selected theme color and picture bytes remained; the producer removed both placeholder-text slide links on its first save. The final PDF contained both page texts. Separate read-only checks recomputed all four PPTX hashes and the PDF hash, then independently traversed both slide-to-layout and slide-to-notes-to-slide edges in each PPTX. A reusable [package inspector](../../scripts/research/oracles/inspect-layout-reuse.py) follows presentation order, records links and media hashes, and rejects a deliberately broken notes backlink; it does not operate Office. The [producer runner](../../scripts/inspect-cross-layout-reuse-libreoffice.mjs) records application version; neither tool establishes interactive editing, link activation, repair-dialog behavior or PowerPoint compatibility.

The same input was opened in PowerPoint for Mac and saved as three successive copies, each closed and reopened. On the third reopen, both pages displayed their expected text, master artwork and corresponding notes; no repair prompt was observed during these opens. The [independent package inspection](../testing/cross-layout-reuse-powerpoint-evidence.json) found the shared layout and master, selected theme color, image bytes, run sizes, notes backlinks and both slide-link relationships in all four files. PowerPoint renamed the theme and media parts on its first save. The [inspector](../../scripts/inspect-cross-layout-reuse-powerpoint.py) checks package contents, not UI behavior. In a later [interactive attempt](../testing/cross-layout-reuse-link-attempt.md), Tab and Return activated the second-page link back to the first in both the original and third saved file. Coordinate clicks instead ended the show; the hit location and cause remain unverified, as does interactive editing.

`destination.copySlideMasterFrom(source, masterId, options)` copies one master's artwork and local background under a new `id`. Set `theme` to `"destination"` to inherit the target document theme, `"source-declarations"` to copy only the master's local theme declarations, or `"source-effective"` to materialize the source document, master and default theme values as a complete master theme. With `"source-declarations"`, undeclared values inherit from the destination. Asset, link, preset and atomicity rules follow the layout copy; master connectors must target objects in the copied master. Layouts are not copied automatically. The effective-theme policy preserves the modeled color and font values, not arbitrary native theme structures outside Core's model.

Master copy also accepts `reuseEquivalent: true`. It reuses the first structurally identical destination master only if its declarations, background, ordered artwork, mapped references and existing resources match; it returns the existing master and source-to-existing element IDs without consuming staged IDs. The requested new ID must be available. Missing and explicit declarations remain distinct even if their current effective colors happen to match, because future inheritance can differ. Layouts referencing a reused master share subsequent edits to it. The default remains a fresh copy; no general native-theme equivalence is inferred.

For example, when copying a template chain, use the returned identities instead of assuming the requested IDs were installed:

```ts
const assets = { deduplicate: "content", external: "reject" } as const;
const master = destination.copySlideMasterFrom(source, "source-master", {
  id: "new-master", theme: "source-effective", assets, reuseEquivalent: true,
});
const layout = destination.copySlideLayoutFrom(source, "source-layout", {
  id: "new-layout", masterId: master.master.id, theme: "destination", assets,
  reuseEquivalent: true,
});
destination.copySlideFrom(source, "source-slide", {
  layoutId: layout.layout.id, theme: "destination", geometry: "preserve",
  customData: "reject", assets,
});
```

This example assumes there are no external connector or slide-action targets requiring explicit mappings. For those targets, supply the corresponding mapping options for each operation.
The [complete TypeScript example](../examples/copy-references.ts) copies the same source page twice and checks the resulting document through the ordinary validation/export APIs.

Resource equality includes accessibility metadata: matching image bytes with different descriptions are kept as separate resources and masters. Reusing byte-identical content does not silently merge those descriptions.

A cross-package regression edits a reused master referenced by two distinct destination layouts: both previews reflect the edit, the source master remains unchanged, and generated PPTX relationships retain the two-layout/one-master chain. It does not test native editing of that master.

A [LibreOfficeDev headless sample](../testing/cross-master-layout-reuse-libreoffice-evidence.json) reuses both an effective-theme master and a layout for two pages. All three saves retained the shared ownership chain, text, notes backlinks and picture bytes; the producer removed both placeholder-text slide links on its first save. The separate package inspector rechecked all four file hashes and independently followed the ownership and notes edges. Core regressions also reject a reentrant change to a previously matching master and distinguish absent from explicitly empty artwork. This is a named sample rather than proof of interactive editing or PowerPoint behavior.

One Core regression compares all three policies in the same destination with different source and destination colors and fonts, then changes the source master and checks that the copied themes stay detached. A cross-package test also checks the expected two colors in SVG and generated PPTX theme parts for each policy. These checks cover selected modeled values, not complete visual or native round-trip equivalence.

## Implementation boundary and evidence

Core owns a private two-pass copy preparation: allocate all identities, then rewrite only modeled connector/action fields on detached input. Existing insertion/materialization owns registration and immutable storage. No public package graph or dependency changes are required.

[Core tests](../../packages/core/test/copy-references.test.mjs) cover forward/nested/shared references, self/external links, all current rich-text locations, repeated copies, metadata isolation, invalid destinations, occupied IDs and a 600-element forward-reference graph. [Cross-package parity tests](../../scripts/copy-parity.test.mjs) remove the original, verify independently expected connection coordinates, inspect SVG paths and PPTX custom geometry, and independently inspect emitted slide/notes relationship targets. Browser and installed consumers exercise the public APIs. Run `pnpm test:copy` for the cross-package suite; it is also part of `pnpm test`.

The cross-document tests additionally cover mapped placeholders and presets, timeline targets, staged failure, nested image deduplication and source detachment. The explicit-geometry policy has Core cases for group-local coordinates, free and anchored connectors, table grids, implicit text height and failed-batch retry; a separate Layout/SVG/PPTX test checks independently expected connector coordinates after source removal. Node and browser ESM/global entries agree on an independently expected batch-fit box. One generated copy retains page text, notes-to-slide correspondence and exact shared PNG bytes through three fresh PPTX import/export rounds. Node, browser ESM and browser global bundles agree on a separate copied-image case.

A [LibreOfficeDev fit observation](../testing/copy-fit-libreoffice-evidence.json) exercises a 400 × 200 point page fitted into a 200 × 200 point page with text, a shape, static connector, group and table. Independent package inspection confirms the original explicit coordinates and table grid against calculated expectations, and all three headless saves retain the text and notes. This is a counterexample to visual-fit guarantees: the source-page control PDF displays all three text strings without line breaks, whereas both the fitted input and final PDF conversions wrap them into narrow frames, including overlap with a shape. On the first save LibreOfficeDev rewrote the group coordinate frame and expanded the table frame from 254,000 to 911,880 EMU in height while recording a 253,800 EMU row; later saves also changed some object extents. The [runner](../../scripts/inspect-copy-fit-libreoffice.mjs) records the actual files and per-round geometry. It does not establish interactive editability, repair-dialog behavior or PowerPoint behavior.

In a [PowerPoint for Mac 16.104 observation](../testing/copy-fit-powerpoint-evidence.json) of the same source and fitted page, the source text displayed continuously and the fitted text wrapped and overlapped a shape on first open and all three Save As/reopen rounds. The third reopen displayed the notes, and independent ZIP/XML inspection confirms the text and bidirectional page/notes links across all saves. PowerPoint retained the recorded geometry of the text, rectangle, static connector and group but increased the table frame height from 254,000 to 911,860 EMU on its first save while retaining the 254,000 EMU row and original grid; that frame height remained in subsequent saves. The [inspector](../../scripts/inspect-copy-fit-powerpoint.py) reads the captured files and screenshots. No repair prompt was observed; interactive object editing was not tested.

A separate [PowerPoint observation](../testing/cross-copy-powerpoint-evidence.json) covers a two-page fixture through three successive Save As and reopen operations in PowerPoint for Mac 16.104. Screenshots show both page texts and their corresponding notes, plus the copied image; no repair prompt was observed. Independent ZIP/XML checks found the page/notes relationships in both directions, identical PNG bytes, four named objects, the copied page's internal self-link relationship and unchanged recorded object offsets and extents through all rounds. The [inspector](../../scripts/inspect-cross-copy-powerpoint.py) operates on the captured files; it does not automate PowerPoint. The link was not activated and the connector is static custom geometry, so this is not evidence of interactive link or connector editing or general visual fidelity.

A separate [LibreOfficeDev headless observation](../testing/cross-copy-libreoffice-evidence.json) covers a two-page copied-slide fixture. Three successive native conversions retained both page texts, both notes bodies, each slide/notes relationship in both directions, the image bytes, the copied page's four named objects, its self-link relationship and its connector's static custom geometry; the final file reopened to a two-page PDF with the expected page texts. The link was inspected, not clicked, and the connector is a static custom path. The producer changed object geometry: by the third save the picture width and height were 1,000 and 1,040 EMU smaller than the input, respectively; the exact per-object deltas are recorded. The [runner](../../scripts/inspect-cross-copy-libreoffice.mjs) records the application version and independently inspects ZIP/XML and PDF contents. This does not establish interactive editability, repair-dialog behavior, complete visual fidelity or PowerPoint behavior.

A separate [three-page batch observation](../testing/cross-batch-libreoffice-evidence.json) exercises two copied pages with mutual page and notes links plus a shared picture. LibreOfficeDev retained the page text, notes text, internal page links and identical picture bytes across three headless saves; the final PDF reopened with all three page texts. It changed the notes' internal slide relationships into external hyperlink relationships on the first save, then rewrote their targets to local file URLs on the second. Consequently the notes links do **not** retain their original package-internal semantics. The Parser maps the original internal links, but reports both altered notes links as unsupported and does not project them as live actions; each inspected source still round-trips byte-for-byte in no-op mode. The [runner](../../scripts/inspect-cross-batch-libreoffice.mjs) records raw targets, relationship modes, Parser findings and per-round comparisons; no links were activated.

A [template-chain observation](../testing/cross-template-libreoffice-evidence.json) covers two mutually linked placeholder pages, two copied layouts and one copied effective-theme master. Three LibreOfficeDev headless saves retained page and notes text, notes backlinks, the selected 20/24-point run sizes, distinct layouts, their shared master, the selected accent color and identical shared image bytes. The producer moved the master picture into each layout and removed both placeholder-text click elements on its first save; neither master ownership nor those page links is therefore preserved. The final PDF reopened with both page texts. The [runner](../../scripts/inspect-cross-template-libreoffice.mjs) independently inventories the package graph and records each round; it does not establish interactive link behavior or full visual fidelity.

An independent [same-page link control](../testing/copy-placeholder-links-libreoffice-evidence.json) compares placeholder and ordinary text links in a two-page batch. LibreOfficeDev removed both placeholder click elements on the first save while retaining both ordinary text links through three saves. This narrows the observed difference to the tested fixture; it does not establish why the producer removed the links or prove behavior for other versions and documents.

These checks establish current Core-reference copying and generated-package consistency, not arbitrary native editability or complete cross-application round-trip fidelity. AUT-09 remains open for broader reuse and its prerequisite template/preservation capabilities.
