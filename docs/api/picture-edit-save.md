# Experimental picture replacement preservation save

`importPptx(bytes, { projection: "content", pictureEditSaveProfile: "replace-v1" })` enables one source-bound slide-local picture retarget per prepared edit plan. It also exposes the [picture source inventory](content-import.md). Default imports and existing text/chart profiles do not gain image write permission. It can be combined with `firstSlideNumberSaveProfile: "attribute-v2"` to replace one picture and change the starting number in the same plan. Text or chart edit profiles, field projection, master artwork, cached diagram previews, and optional font/notes projection profiles remain excluded.

Register exactly one new byte-backed PNG, JPEG or GIF asset with its correct MIME type and header dimensions, then replace one imported image element's `assetId` with the new asset ID. The image's frame, crop, opacity, transforms and all other document state must remain unchanged. Existing assets remain registered; changing their bytes, removing assets, adding multiple assets, retargeting multiple pictures, changing geometry or mixing text/style/structural edits blocks the complete plan. With the combined number profile, a number-only edit is also accepted under the number profile's normal checks. The new asset must have default accessibility metadata and no dedupe key. Path/URL sources are not loaded.

`prepareSave({ mode: "edit" })` checks the complete normalized candidate against the imported baseline plus the single permitted retarget and new asset. It checks the original source relationship closure, package signature/VBA guards and raw picture identity. External-linked pictures, SVG extensions and unverified blip effects block this profile. It then adds a distinct media part and relationship, changes only the selected raw `blip` reference, retains the old media and relationship, validates all archive payloads and reparses the package. Default content projections before and after are compared after matching asset identities by source part. A ready plan reports `scoped-preservation` and two asset changes. For a combined number change, the candidate stages the verified presentation attribute edit before the picture edit, with shared change and validation budgets. The intermediate and final ZIP sizes are conservatively charged together against `maxPreparedOutputBytes`, and analysis work is partitioned among stages. Failure of either stage publishes no plan. The existing plan freshness, cancellation, resource reservations and disposal rules apply. Reimport saved bytes to establish a new baseline.

Unsupported edits or source conditions return a blocked report. Resource exhaustion throws `save-limit-exceeded`, cancellation throws `operation-aborted`, and an inconsistent constructed candidate throws `save-candidate-invalid`; none returns a partial plan.

The JPEG frame and scan component checks follow the bounded fields described in [ITU-T T.81, sections B.2.2 and B.2.3](https://www.w3.org/Graphics/JPEG/itu-t81.pdf); they are not a complete conformance check.

For baseline and extended sequential Huffman DCT frames, each scan's DC and AC tables must be defined before use; baseline selectors are limited to 0 or 1, and extended selectors to 0–3. Progressive Huffman scans require the DC table for an initial DC scan and the AC table for an AC scan; DC refinement does not consume a Huffman table. This profile requires self-contained tables rather than relying on tables supplied externally to an abbreviated JPEG stream. Other frame modes do not receive this Huffman-reference check.

For these DCT frames, baseline requires 8-bit sample precision; extended sequential and progressive permit 8 or 12 bits. This is a framing policy, not proof that the entropy stream matches that precision or that the target application can render 12-bit images. Scan spectral and successive-approximation parameters are also checked: sequential scans require 0/63/0, and progressive scans require bounded bands, single-component AC scans, and valid refinement parameters. For progressive Huffman frames, each component must receive initial DC data before AC data, every transmitted coefficient must begin with an initial scan, and each subsequent refinement must follow its previous approximation level. All frame components need initial DC by the end; untransmitted AC coefficients and unfinished refinement are allowed. These checks do not decode entropy data or establish full JPEG conformance.

The [JPEG framing oracle](../../scripts/jpeg-framing-oracle.test.mjs) compares named 8- and 12-bit files and a malformed progression with `djpeg -strict` when `djpeg` is available; the installed decoder must support 12-bit JPEG for that optional test. A separate [save test](../../packages/pptx-parser/test/picture-save-jpeg-validation.test.mjs) replaces the same picture over three fresh sessions, checking the current relationship's media bytes after each reimport. A [PowerPoint observation](../testing/jpeg-12-native.md) shows two named 12-bit source images and native position edits; one PPTKit preservation replacement underwent three native position-edit, save and reopen rounds and one separate left-edge crop. The programmatic three-round replacement outputs were not opened in PowerPoint.

This profile preserves the existing visible frame and crop values; it does not calculate a new fit, validate every pixel or color semantic, guarantee EXIF/color-profile interpretation, clean old media, support inherited master/layout pictures, or prove semantics of arbitrary opaque application references. PNG replacements require bounded chunk ordering, valid chunk CRCs, required image/end chunks, a valid zlib/DEFLATE stream and Adler-32, exact scanline lengths and legal filter bytes, including Adam7 passes. For indexed PNG, filters are reconstructed one row at a time and actual palette indices are checked, excluding unused padding bits. Transparency chunks are checked against color type, palette size, sample depth and ordering; unknown critical chunks are rejected. GIF replacements require bounded block framing, frame bounds and color tables, a complete LZW end code, the expected number of decoded pixels and valid palette indices. GIF timing, playback, plain-text rendering and opaque extension semantics are not validated; some permissive decoders accept incomplete streams that this profile rejects. Decoded scanlines and GIF frame pixels count against `maxSaveValidationBytes`; inspection shares `maxSaveValidationWork` with candidate comparison. JPEG replacements require bounded marker segments, a frame, at least one nonempty scan and a terminal end marker, with stuffed bytes and restart markers handled inside scans. Frame component IDs must be unique, sampling factors must be 1–4, and each scan must reference distinct declared components. Baseline and extended sequential Huffman frames must cover every frame component exactly once across their scans; progressive scans may repeat components. For baseline, extended sequential and progressive Huffman DCT frames, each scanned component's quantization table must have been defined before that scan. Quantization and Huffman table segments are checked for bounded structure, legal identifiers, nonzero quantizers and non-oversubscribed code lengths. JPEG entropy coding, decoded pixels, remaining cross-table and broader scan consistency and full conformance are not validated. Other PNG color/ancillary semantics are not fully validated. These checks apply to replacements, not ordinary source import. The profile has automated Node and Chromium evidence for shared media and three save/reimport rounds in both dialects; optional Pillow oracles independently check [indexed PNG samples](../../scripts/indexed-png-oracle.test.mjs) and [GIF LZW streams](../../scripts/gif-lzw-oracle.test.mjs).

One [LibreOfficeDev 26.8 headless experiment](../testing/picture-save-libreoffice-evidence.json), reproducible with [the producer script](../../scripts/inspect-picture-save.mjs), opened and resaved an authored two-picture shared-media sample three times. The target and sibling PDF regions, rasterized at 2×, matched the first edited rendering after all three resaves, while LibreOffice changed their left crop values from 12500 to 12264 and 12736 respectively. This is observed behavior for that sample, not exact crop-attribute preservation. No interactive editing or repair-dialog observation was performed in that experiment. A separate [PowerPoint sample](../testing/picture-number-powerpoint.md) combines replacement with a starting-number change and records three reorder/save/reopen rounds; native interactive picture replacement and broader producer coverage remain unverified.

A [mixed-source regression](../testing/mixed-advanced-picture-evidence.json) performs three picture retargets in a deck also containing synthetic SmartArt, timing, WAV and comments. The original shared image remains used by an audio poster and another slide; exact part changes, browser parity and independent media/comment checks are recorded. Native picture editing and playback are not inferred.

See [session lifecycle and budgets](import-session.md) and [file adapter](file-save.md). The source inventory and this profile are distinct from [fresh image authoring replacement](asset-lifecycle.md).

```ts
import { importPptx, type PptxSaveReport } from "@pptkit/pptx-parser";

export async function replaceFirstImportedPicture(
  source: Uint8Array,
  image: Uint8Array,
  mimeType: "image/png" | "image/jpeg" | "image/gif",
  width: number,
  height: number,
): Promise<{ bytes: Uint8Array; report: PptxSaveReport }> {
  const session = await importPptx(source, { projection: "content", pictureEditSaveProfile: "replace-v1" });
  try {
    const slide = session.document.slides[0];
    const picture = slide?.elements.find(item => item.type === "image");
    if (!slide || !picture || picture.type !== "image") throw new Error("No imported top-level picture.");
    session.document.registerAsset({ id: "replacement", kind: "image", source: { type: "bytes", value: image }, mimeType, width, height });
    slide.replaceElement(picture.id, { ...picture, assetId: "replacement" });
    const prepared = await session.prepareSave({ mode: "edit" });
    if (prepared.status !== "ready") throw new Error(prepared.report.diagnostics.map(item => item.message).join("\n"));
    return await session.save(prepared.plan);
  } finally {
    session.dispose();
  }
}
```
