# Authoring inheritance origins

`resolvePresentationInheritance(document)` from `@pptkit/core` returns `{ presentation, origins }`. `presentation` is the same detached Canonical IR v2 returned by `normalizePresentation(document)`. `origins` is a separate immutable snapshot of effective foreground theme and background declaration sources. The wrapper and report are frozen; the ordinary IR remains mutable. Resolve again after editing shared definitions. Manual IR changes do not recompute the snapshot.

```ts
const { presentation, origins } = resolvePresentationInheritance(document);
const origin = origins.find(row => row.target.kind === "slide"
  && row.target.id === slideId && row.property === "theme.colors.accent1");
```

Each row contains a logical `target: { kind, id }`, a `property` and a `source`. Target kinds are `document`, `master`, `layout` and `slide`. Source kinds additionally include `default`, which has no ID. Authored source paths use the input collection positions at resolution time, such as `masters.1.theme.colors.accent1`, `layouts.0.background` or `slides.2.background.opacity`. Paths are authoring locations, not OOXML names or persistent edit handles. Use kind and stable ID to identify owners after reordering. The report contains one row per supported effective property per owner, including unused masters and the generated default layout. Document targets have theme rows only; master targets include effective fallback background rows even when the ordinary master IR omits an undeclared background.

Supported theme properties are `theme.name`, the twelve `theme.colors.<role>` properties, and `theme.fonts.heading/body`. Layout/slide entries describe the selected foreground owner theme, even when the ordinary IR omits an explicit theme on a legacy layout or slide. Equal values from different declarations retain different sources. Missing master fields report document/default sources; merely passing through a layout does not make the layout the declaration owner.

Background properties are `background` (the selected whole paint), `background.type`, for solid paints `background.color` and `background.opacity`, and for linear gradients `background.angle`, `background.scaled`, and `background.stops`. For each gradient stop, `background.stops.<index>.position`, `.color`, and `.opacity` identify their declaration; an omitted opacity uses `defaults.background.linearGradient.stop.opacity`. Stop indices and paths are snapshot locations and can change after edits. An omitted gradient `scaled` reports `defaults.background.linearGradient.scaled`. Precedence remains slide → layout → declared master → built-in background. `none` is explicit and has no color/opacity rows. Paint selection is atomic: a local solid color without opacity uses `defaults.paint.opacity` (1), not a lower paint's opacity. Explicit zero retains its authored source. Fully inherited default paint uses `defaults.background.*`. Theme defaults use `defaults.theme.*`. The existing IR `backgroundSource: "theme"` spelling remains compatible; the origin report identifies the actual built-in background declaration as `default`.

For authored shape linear-gradient fills, element targets also report `style.fill.type`, `.angle`, `.scaled`, `.stops`, and each `style.fill.stops.<index>.position/color/opacity`. Missing scaled and stop opacity use `defaults.shape.fill.linearGradient.scaled` and `defaults.shape.fill.linearGradient.stop.opacity`. Shared master/layout shapes and nested group children identify their own authored element paths. Pattern shapes report their preset, colors and opacity sources as `style.fill` fields. Solid and no-fill shapes also report the effective `style.fill` fields; shapes report `style.stroke.paint`, width, dash and arrow fields. An explicit no-fill has a type origin but no color or opacity origin; omitted fields use `defaults.shape.style.*`. These records do not imply placeholder paint inheritance.

Color properties retain symbolic theme roles and supported transforms in the ordinary IR. A background's theme-role dependency can be followed through that target's `theme.colors.<role>` origin. The origin report does not independently calculate RGB, change the color transform pipeline, or infer declaration ownership by comparing values.

Core selects values and records their sources within one resolver. Ordinary normalization, Layout, SVG and PPTX continue through that same resolver. `resolveNormalizedLayout(result.presentation)` accepts the resolved IR; `generatePptx` continues to accept an authoring `PresentationDocument`. No new exporter input contract is implied.

Validation is the same as ordinary normalization; semantic errors throw `PresentationValidationError` before a report is returned. Legacy custom documents need no new property or method. No report fields are inserted into existing IR or serialized output. Source paths/IDs are snapshot data, not executable callbacks.

The original theme/background scope is now extended by [text formatting origins](text-format-origins.md), including placeholders, presets and font clear barriers. Notes, table/chart text origins, master artwork, visibility/field evaluation, declaration history, arbitrary template graphs and Parser source-format provenance remain in the original backlog. See the [checked example](../examples/inheritance-origins.ts), [ownership ADR](../architecture/decisions/0057-master-theme-ownership.md) and [theme/background verification](../testing/inheritance-origins.md).
