# Opaque custom-property source inventory

`inspectPptxOpaqueCustomProperties(bytes, options?)` is an explicit, read-only Parser entry point. It lists effective custom properties that the existing metadata inspector reports as `uninterpreted`, including their part, format GUID, PID, optional source name/link target and value type. A value containing only direct text and CDATA is returned as `{ status: "text", value }`; nested elements, comments and other mixed content are `{ status: "non-text" }` and are not flattened. Text is XML-normalized, not a byte-exact lexical slice. This is source inventory only: it does not validate a variant's lexical grammar, parse currency, dereference links, project into Core or grant edit permission.

The inventory follows the same effective markup-compatibility branch as structural metadata inspection. It does not list inactive branches. The source part and property identity are not proof of unique raw XML location or safe source edits. Results are detached and frozen. Input and options follow the OPC inspection limits and abort signal; shared-memory input is rejected. In addition, the inventory limits output to 100,000 records and one million UTF-16 text code units across returned opaque values, failing with `package-limit-exceeded`. Lower ZIP/XML/OPC limits may fail first. No network resource is loaded.

The standard `inspectPptx` result and default content-import projection remain unchanged. For example, `vt:cy` remains uninterpreted in that result even though this optional inventory can expose its direct XML-normalized text. [Node tests](../../packages/pptx-parser/test/opaque-custom-inventory.test.mjs) cover both dialects, effective MCE branches, nested/mixed content, limits and cancellation; [browser parity](../../scripts/custom-properties-browser-parity.test.mjs) checks ESM/global against Node for the retained currency sample. The [LibreOfficeDev experiment](../testing/custom-currency-libreoffice.md) is an independent, narrowly scoped preservation observation, not validation of the full currency grammar or authoring support.

A [typed example](../examples/opaque-custom-properties.ts) calls the public entry and supplies a lower aggregate XML text budget.

For direct currency text, `assessPptxCurrencyText(value)` separately checks the ECMA-376 Strict/Transitional `ST_Cy` text restriction. A valid result contains a canonical four-place decimal string and an exact `tenThousandths` integer **string**, never a floating-point conversion. XML whitespace is accepted at the ends; signs, exponents and other whitespace are not. Input over one million UTF-16 code units throws; invalid text returns `{ status: "invalid" }`. This helper does not validate an entire element or package, infer currency units, apply a numeric range, project into Core or enable writing. See the [independent schema comparison and negative control](../testing/custom-currency-libreoffice.md).

`assessPptxCurrencyNumber(value)` adds an explicit binary64 representability check. It returns `{ status: "exact", value }` only when that number equals the decimal source mathematically; otherwise it returns `inexact`, `out-of-range` or `invalid` without a numeric value. For example, `1.2500` is exact and `0.1000` is inexact. The check uses bounded integer arithmetic and does not make subsequent floating-point calculations exact. It shares the text helper's input limit and does not itself change Core projection or source-save permissions.


An explicit content import with `{ projection: "content", customCurrencyProjection: "exact-v1" }` projects eligible, named and unlinked direct `vt:cy` text to Core `real` values only when the mathematical value is exactly representable as binary64. Inexact values, invalid lexical forms, attributes on the value, mixed content and ambiguous names remain source-only. Inspection still reports currency as uninterpreted. The effective MCE branch is used; text is limited to one million UTF-16 code units per value. This opt-in cannot be combined with other optional projection or edit-save profiles. Original-byte no-op save is available, but source-preserving edit save is blocked. A fresh export writes Core reals, not currency types or source lexical forms; the capability report records this fallback. The option is available on byte and Node file imports.

`{ projection: "content", customCurrencyProjection: "exact-save-v2", customPropertySaveProfile: "scalar-v1" }` additionally enables bounded source-preserving value edits for uniquely bound currency properties. Proposed values must be nonnegative finite binary64 numbers that are exactly expressible in four decimal places; negative zero, negative values and values such as `0.1` are rejected. The writer computes the four-place decimal from the binary representation without floating-point rounding, retains `vt:cy` and verifies the prepared package by reimporting its projected state. Unchanged lexical forms and unbound/inexact currency values remain in the source. MCE-processed, mixed-content or attributed currency sources are not bound for editing. The profile can combine with compatible text-run, core metadata and slide-visibility saves; unsupported changes still block the complete transaction. Other optional projection and save profiles remain incompatible. Fresh export still writes a Core real rather than a currency variant. [Tests](../../packages/pptx-parser/test/custom-property-currency-save.test.mjs) cover both dialects, three source-save rounds, precision and malformed-source boundaries; browser and file imports are also exercised. A [LibreOfficeDev headless comparison](../testing/custom-currency-save-libreoffice.md) observed that this synthetic edited value and the control currencies were dropped on first resave; PowerPoint and interactive behavior remain unverified.

[Mixed transaction tests](../../packages/pptx-parser/test/custom-property-currency-save.test.mjs) combine currency, a text run, title and slide visibility in three saves and reopens for both dialects. An inexact currency proposal or unsupported geometry change blocks the entire transaction; Node and browser outputs are compared. The CLI v6 manifest remains value-only and can combine with compatible text, metadata and visibility manifests.
