# Serializable edit operations

Factory-created `ManagedPresentationDocument` objects expose `applyEditOperation(operation)`. The first version supports an atomic batch of slide visibility, slide order, starting slide number, element boxes, explicit text run and string shorthand changes. Each change carries an expected value and a replacement value; a successful result includes the captured changes and an inverse operation that swaps expected/replacement values. Both operations use only JSON data and can be stored or transmitted by the consumer. A typechecked [example](../examples/edit-operations.ts) demonstrates apply, undo and redo.

```json
{
  "schemaVersion": "pptkit-edit-v1",
  "documentId": "deck",
  "changes": [
    { "type": "slide-hidden", "slideId": "slide-1", "expected": false, "value": true },
    { "type": "first-slide-number", "expected": null, "value": 0 }
  ]
}
```

A `text-run` change supplies `slideId`, `elementId`, zero-based `paragraphIndex` and `runIndex`, plus string `expected` and `value`. It targets a slide-owned text element or shape text whose authored content is an explicit paragraph/run array, including inside groups. `table-cell-text-run` uses the same fields plus zero-based `rowIndex` and `cellIndex`, indexing the authored `rows` and `cells` arrays, not visual grid columns: a spanning cell is one authored cell. It also works inside groups. For authored string shorthand, `text-string` and `table-cell-text-string` use the same owner paths without paragraph/run indexes; they preserve the string representation and reject explicit arrays. Conversely run changes reject strings. Shared layout/master elements are not targets. Only the selected text changes; styles, actions, spans and field identity remain attached. For a dynamic field the text is its display cache and may be replaced by a presentation application when it updates the field. The same batch can edit multiple runs of an element. Each distinct path must appear at most once. The operation checks the current text, not the identity or history of the run or cell at that path; inserting, replacing or moving them can therefore produce an undetected conflict when the text matches.

`notes-string` changes existing authored string shorthand; `notes-run` and `notes-run-action` target an existing explicit paragraph/run using `slideId`, `paragraphIndex` and `runIndex`. They cannot create or remove notes, change topology or convert shorthand into runs. A run's text and action can be changed in one atomic batch while retaining other formatting and metadata. The action contract and destination checks are the same as element actions below. Notes edits use value checks, not stable run identities, and an inverse can conflict after later edits. A selected [V2 source-save profile](text-owner-save.md) can save eligible bound notes-run character changes; it does not admit changing run actions. Node tests exercise three source-save/reopen rounds in both OOXML dialects, including stale-plan and blocked-action checks. Node/browser fresh-export parity checks a text-and-action batch, but does not establish PowerPoint interaction with notes links.

`chart-point` changes one existing authored point identified by `slideId`, `elementId`, zero-based `seriesIndex` and `pointIndex`, and `coordinate`: use `values` for categorical and combination charts, `xValues` or `yValues` for scatter and bubble, and `sizes` for bubble. It does not add series or points; holes and missing coordinates reject. Values are finite numbers, explicit `null` blanks where the chart type permits them, or the string `"-0"` for negative zero. JavaScript numeric negative zero is rejected in the operation because JSON would silently serialize it as positive zero; expected values distinguish the two zeros. Bubble coordinates cannot be blank, bubble sizes must be positive, and pie/doughnut values cannot be negative. Indexes do not establish series or point identity after structural edits. Eligible bound numeric changes may be saved using a selected [chart source-save profile](chart-value-save.md); blank insertion and other unsupported source edits remain blocked. Three source-save rounds in both OOXML dialects verify cache/workbook synchronization and negative zero. Separate three-round tests apply operation/undo/redo to combination, bubble and sparse scatter sources; the first bubble round also compares browser and Node bytes. Node/browser fresh-export parity covers the operation. Native chart interaction is not established by these tests.

`chart-category` replaces one existing categorical chart label at `categoryIndex`; scatter and bubble charts have no categorical labels. `chart-series-name` replaces the name at `seriesIndex` for all supported chart families. These string changes can share a batch with point edits and use the same value-based conflict and index limitations. Empty strings remain representable and reversible, but Core validation reports empty category labels and series names; validate before output. Fresh SVG/PPTX tests cover the edited label, chart cache and workbook. The numeric-only source-save profiles reject these label changes, even in a batch with an otherwise supported value edit; undo restores no-op eligibility.

`null` means an absent authored start number; zero is distinct. Number values follow Core's nonnegative safe-integer rule. Exporter may impose a narrower output range; an accepted Core operation is not proof that export will succeed. A `slide-order` change has `expected` and `value` arrays of distinct slide IDs; the replacement must be a permutation of the complete expected order and the expected order must match the current document. Sorting can be combined with visibility and numbering in one batch. Order arrays are capped at 100,000 IDs. Targets must be unique within the batch. The complete batch is captured and checked before any mutation; an invalid shape, different document ID, missing slide or changed expected value throws `PresentationEditError` with `invalid-operation`, `wrong-document`, `missing-target` or `edit-conflict`. The returned result, changes and inverse are frozen and detached. Up to 10,000 changes are allowed; unknown fields, sparse arrays, accessors and unsupported change types reject. No-op changes are allowed and retain their expected-value checks.

An `element-box` change identifies a slide-owned element by `slideId` and `elementId`, including group descendants. Its `expected` and `value` are either `null` for an absent authored box or `{x, y, width, height}` in points; `height: null` means omitted automatic height and is valid only for text. Coordinates must be finite and dimensions nonnegative. Group child values are in the group's coordinate system, and changing a group box leaves its authored child boxes and coordinate size intact. Connectors use endpoints and are excluded. A missing box can be meaningful for a placeholder, but an operation does not validate the complete document: removing a required box or changing a table frame independently of its grid may produce diagnostics or export failure. Run `validatePresentation` and relevant layout/export checks when the consumer needs a renderable document. The operation checks authored box values, not inherited or computed layout geometry; changing other layout inputs may change the final appearance without a box conflict.

`element-hidden` and `element-opacity` target any slide-owned element, including group descendants. Their `expected` and `value` use `null` for an absent authored property, which is distinct from explicit `false` and `1`; opacity otherwise ranges from 0 to 1 inclusive. Effective visibility and opacity also depend on ancestor groups. The current PPTX exporter omits hidden objects rather than retaining a natively hidden object, so an exported file cannot recover such an object merely by unhiding it in PowerPoint. Output support for opacity varies by element and paint; validate the actual exported result for the intended content.

`element-name` changes the authored name of a slide-owned element, including a group descendant, without changing its stable ID. Its expected and replacement values are strings or `null` for an absent name; an empty string is distinct from an absent name in Core. This is a value check, so another change to the same name is detected unless it has returned to the expected value. The exported name is subject to the exporter's normal name and XML handling; this operation does not edit an existing source package.

`element-accessibility` replaces the authored accessibility record on a slide-owned element, including a group descendant. Use `null` for an absent record or `{description, decorative}` with each property set to its authored string/boolean or `null` for absent. An empty description, explicit `false`, an empty record and an absent record remain distinct and are restored by undo. Unknown or explicitly undefined authored fields conflict rather than being discarded. Setting a group decorative may remove it and its descendants from configured reading order; the inverse restores the prior scopes as described below. The existing [accessibility contract](accessibility-descriptions.md) governs SVG and PPTX behavior and warnings, including actionable decorative objects. Imported documents still require a matching source-save profile and eligible bindings; applying the operation alone does not grant source-preserving save support or prove assistive-technology behavior. Node tests cover a mixed name, description, existing decorative value and text batch through three source saves in both OOXML dialects; a separate name/description/decorative batch has Node/browser parity over three rounds. An unbound decorative insertion remains blocked.

`element-transform` replaces the authored rotation and flips on a slide-owned element, including group descendants. Its `expected` and `value` are either `null` for an absent transform, or a record with all three keys: `rotation` is a finite number of degrees or `null`, and `flipH` and `flipV` are booleans or `null`. A null property represents an absent authored property. Thus `null`, `{rotation: null, flipH: null, flipV: null}` and `{rotation: 0, flipH: false, flipV: false}` are distinct and undo restores each form. Existing transforms with unrecognized properties or explicit undefined values conflict rather than lose data. This checks authored values, not computed geometry or ancestor transforms; output support varies by object, and connector-local transforms can fall outside native connector export profiles. [One PowerPoint observation](../testing/edit-transform-powerpoint-evidence.json) covers selection, movement, save and reopen of a single rotated and flipped shape; it does not establish general native transform editing or visual equivalence.

`slide-reading-order` atomically replaces a slide's authored reading-order scopes. Its expected and replacement values are `null` for no configured order, or nonempty arrays of `{elementIds}` for slide roots and `{groupId, elementIds}` for group children. Each scope lists all visible, non-decorative direct children once; values are checked against the **resulting** objects after the batch, while expected values are checked against the original order. Scopes are limited to 10,000 and their IDs to 100,000 in total. Hiding an object or group can reconcile or remove configured scopes: when that happens, the returned inverse automatically includes a reading-order change so undo restores the original scopes. If the order has changed since, the inverse conflicts before restoring visibility. An operation whose inverse would exceed 10,000 changes is rejected before mutation. These checks are value based and do not detect ABA history.

`element-action` replaces or removes the click action on a slide-owned element, including group descendants. Use `null` for no action, `{type: "url", url, tooltip}` for a URL, or `{type: "slide", slideId, tooltip}` for a slide jump; `tooltip` is a string or `null` for absent, distinct from an empty string. Targets must be nonempty and a replacement slide destination must exist when the batch is applied. A stale or unsupported authored action conflicts instead of dropping unknown fields. An inverse that would restore a slide jump fails if that destination has since been removed. URL acceptance follows Core's nonempty-string rule and is not a URL security policy; consumers must apply their own restrictions. This operation does not modify a source PPTX package. Native interaction has only the limited internal-jump evidence below.

`text-run-action` and `table-cell-text-run-action` use the same action values and checks on an explicit run, using the same authored paragraph, run and table-cell indexes as the corresponding text changes. They reject string shorthand and missing runs. A run's text and action are distinct targets and may be edited in the same batch; both changes are checked against their original values and undo together. As with text changes, indexes do not prove run identity if the content topology has changed. [One PowerPoint observation](../testing/edit-action-powerpoint-evidence.json) tests internal slide jumps from a shape and both run owners using keyboard activation before and after one save/reopen, and clicks on the exposed link objects after reopening; full pointer hotspot coverage remains unverified.

The contract uses **value-based** conflict detection. It does not detect an ABA change that returns to the same value, replacement of a slide by another with the same ID and value, or other fields changed concurrently. Document IDs and target IDs are caller-visible identities, not cryptographic authentication or collaboration revisions. Applications requiring stronger conflict detection must maintain and check their own revision/identity protocol. Operations are synchronous on factory-managed documents; custom `PresentationDocument` implementations are not required to provide this managed method. Network transport, undo history, permission checks, cross-document operations, broader object/asset edits and unknown native structures remain outside this slice. Applying an operation does not grant source-preserving PPTX save support.

[Core tests](../../packages/core/test/edit-operation.test.mjs) cover JSON replay, inverse/redo, mixed-target atomicity, stale order and missing targets, zero/null, malformed permutations and accessor rejection. [Cross-package parity](../../scripts/edit-operation-parity.test.mjs) verifies Node/browser behavior and actual PPTX slide order, visibility and number output; it runs under `pnpm test:browser-bundles`. The broader ECO-06 change-event, undo/redo and collaborative contract remains open.

One [PowerPoint observation](../testing/edit-operation-powerpoint-evidence.json) opens a generated slide after a mixed string, grouped run and group-box batch, edits its headline natively and saves/reopens it. A [subsequent observation](../testing/edit-operation-move-powerpoint-evidence.json) nudges the group in PowerPoint and reopens the result. Independent XML checks confirm the changed group position, unchanged nested and headline geometry, and retained text. These samples do not prove complete operation coverage or arbitrary layout fidelity.
