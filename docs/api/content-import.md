# Experimental content import

`importPptx(bytes, { projection: "content" })` adds an explicit content projection to the [import session](import-session.md). `projection: "structure"` keeps its previous behavior. Both modes use the same bounded package/XML/MCE pass, private source snapshot and original-byte no-op plan lifecycle. The content profile is available in Node, `/browser` and global browser bundles.

`pictureSourceProfile: "embedded-v1"` additionally reports `pictureSources` for successfully projected slide-local embedded pictures, including pictures in groups. Each record identifies the Core slide, element and asset, the original slide part and picture path/object ID, the raw one-based preorder index of its `a:blip`, the relationship ID, and the resolved media part. The path identifies the picture owner; `sourceElementIndex` and `source.elementIndex` identify the `blip` within the original XML, including inactive MCE branches in the preorder. Shared media can therefore have multiple distinct picture records. `hasSvgExtension` checks the raw blip subtree, including inactive branches; `hasExternalLink` records a raw link attribute without fetching it. These two flags do not classify all effects or unknown dependencies. Records are frozen and bounded by `maxReportFindings`; unsupported or omitted pictures, inherited master/layout artwork, cached diagram artwork and external-only pictures are not inventoried by this profile. The inventory is source provenance, not permission to replace images or delete resources. It can accompany `firstSlideNumberSaveProfile: "attribute-v2"`; source-bound number and ordinary text edits retain the picture inventory and media. Default imports omit the field, and structure projection rejects this option.

The separate [experimental picture save profile](picture-edit-save.md) opts into one bounded picture replacement and includes this inventory.

When a successfully mapped slide picture has a direct `audioFile`, `videoFile`, `quickTimeFile`, `audioCd` or `wavAudioFile` declaration in its effective nonvisual properties, the image is only a static poster. The report adds a located `media-playback-unmapped` warning, `drawing.media` operation findings and a `drawing.media.poster` preview fallback; `drawing.image.mapped-fields` also marks preview as fallback. This does not project the media resource, fetch links, execute playback, or validate the media declaration. Other encodings, extension-only media markers, inherited artwork and media without a mappable poster remain outside this detection; original-byte no-op retains their source.

## Mapped subset

The profile reads slide-local PresentationML shapes, embedded raster pictures, tables and nested groups in source drawing order. Strict and Transitional expanded namespaces are recognized independently of prefix spelling.

| Source | Core projection |
| --- | --- |
| Local offset/extent, rotation and flips | Point-based frame and transform; 12700 EMU per point and 60000 angular units per degree |
| Unambiguous source placeholder index/type ancestry | Bounded inherited offsets/extents and preset names as local Core values; [source provenance and limitations](placeholder-inheritance.md) |
| Supported text frame/list ancestry for drawing bodies | Bounded per-property frame/paragraph/list/run values with source records; [cascade contract and limits](text-style-inheritance.md) |
| Drawing identity/name/description/hidden flag | Deterministic `source-slide-ID-object-ID`, source report, name/accessibility and hidden state |
| Preset `rect`, `roundRect`, `ellipse`, `triangle`, `diamond`, `rightArrow`, `chevron`, `parallelogram` | Corresponding eight Core shapes; parallelograms admit one bounded integer literal adjustment from local or matched placeholder geometry, including XML whitespace, signs and leading zeroes; unsupported adjustments and custom/other presets are omitted with findings |
| Explicit no-fill or sRGB solid fill | Paint and optional alpha; unknown colors/modifiers are reported |
| Explicit line width/paint, solid/dash/dot/dashDot, supported arrow ends | Stroke subset |
| Rectangular no-fill text box without a line | Core text element; painted/lined text boxes remain shapes with text |
| Paragraphs/runs, literal XML text/CDATA, line breaks and empty paragraphs | Ordered rich text; no trimming or Unicode normalization |
| Run size, bold/italic, single underline/strike, opaque sRGB, literal Latin font and language | Direct run styles; paragraph `defRPr` supplies local run defaults |
| Alignment, left/hanging indent, percentage line spacing, point before/after spacing | Paragraph styles |
| No bullet, character bullet and four mapped numbering formats | Current Core bullet/number model, including start value |
| Nonnegative insets, top/middle/bottom anchoring, wrap and current auto-fit choices | Text frame style |
| Group parent frame and child offset/extent | Group coordinate size; immediate child offsets are rebased once against `chOff` |
| Rectangular embedded PNG/JPEG/GIF with explicit stretch placement | Immutable byte asset and image frame; signature, declared MIME and positive header dimensions must agree |
| Nonnegative source crop with a nonempty remaining rectangle | Core crop fractions, without clamping; missing crop means stretch |
| One fixed alpha multiplier within 0–100% | Image opacity; unsupported effects and repeated multipliers remain reported |
| Authored table grid, rectangular merge anchors, cell rich text/clicks and bounded direct styles | Core table; see the [table profile](table-import.md) for grid/frame, continuation, border and theme limits |

Empty paragraph insertion properties apply to its empty run; properties at the end of a nonempty paragraph do not overwrite the preceding run. Literal text and XML metacharacters survive decoding and fresh export within the tested subset. Supported inherited properties are materialized independently; an unsupported explicit high-priority value blocks an older value for that property. Script-specific fonts, dynamic fields and links are not silently treated as equivalent to ordinary Latin runs. The opt-in [slide-number field profile](field-evaluation.md) maps a bounded field/cache subset without enabling source edit-save.

Groups preserve child frames and local transforms, rather than flattening their world bounds. A nonzero child coordinate origin is subtracted from immediate child frames; nested groups retain their own coordinate origin. Zero child extent cannot form an invertible Core group and produces an unsupported finding instead of fabricated dimensions.

## Embedded image assets

Image relationships resolve against the already validated package graph, including canonical part-name matching. A referenced image part becomes one Core asset across slides and nested groups. Different source parts remain different assets even when their bytes match; import does not merge source identities by content. Asset identity records include the binary part and each picture's source location/relationship ID. Normalized Core objects contain only an asset ID and format-independent image fields.

The reader reuses CRC-checked archive payloads from the original bounded pass. It copies image bytes into Core's immutable Base64 representation and reads PNG IHDR, GIF logical-screen or JPEG frame dimensions for geometry-dependent fits. JPEG scanning skips length-delimited APP/comment/table segments and cooperatively checks cancellation. Header classification and dimensions do **not** validate the complete pixel stream, image-internal checksums, EXIF orientation, ICC color behavior or animated-image playback; a located finding records this limitation for every image. Import does not decode pixels or load a runtime image codec.

Only rectangular picture geometry, explicit stretch and zero destination `fillRect` offsets are mapped. Negative crop outsets, empty/inverted crop rectangles, tiling, shaped/custom clipping and independent fill rotation omit the picture with a reason. Unknown visual modifiers, borders, locking metadata and extensions receive their own findings. Supported base image fields can remain editable without claiming complete picture fidelity.

External-only pictures remain absent from Core: their targets are inventoried in the relationship report, never fetched or registered as live URL assets. A picture containing both an embedded representation and an external link imports the embedded bytes and reports unmapped external updates. Invalid relationship types/modes, missing targets, fragmented embedded references and malformed mapped percentages reject the import. Unsupported formats or mismatched/malformed image headers stay source-only with findings; they do not leave orphan Core assets.

When an image blip contains the Office SVG extension (`svgBlip` in the [2016 SVG namespace](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-odrawxml/2451f45e-5d77-4661-86d1-0a017fced779)), import explicitly reports that only a supported base image can be projected. The SVG extension remains uninterpreted, including its relationship and content; the finding does not certify that the reference is valid or that the base raster matches it. Original-byte no-op save retains the source package, while a separate fresh export of the projection can discard the SVG representation. The extension's generic unhandled-subtree finding is retained as well. In one [PowerPoint save/reopen observation](../testing/svg-pair-powerpoint-evidence.json), an initially blue fallback for a red SVG became red; a [regression test](../../scripts/svg-pair-powerpoint-import.test.mjs) confirms that the two source packages project their respective fallback bytes and no-op save each original exactly.

An [independent LibreOfficeDev probe](../testing/svg-pair-libreoffice-probe.md) deliberately pairs different SVG and PNG colors: the application renders the SVG while the content projection maps the PNG. This named example demonstrates a visible projection difference, not a general application compatibility claim.

`sessionLimits.maxImportedAssetBytes` defaults to 16 MiB and bounds each candidate image payload before scanning or Base64 registration. `maxTotalImportedAssetBytes` defaults to 64 MiB and bounds registered distinct source-part bytes plus the current candidate; repeated mapped uses are charged once. Parts whose declared MIME is outside PNG/APNG/JPEG/GIF are omitted without header inspection or image-projection budget charges; a supported MIME still receives the budget check before scanning even if its bytes later prove malformed. ZIP limits separately bound all expanded input, including omitted resources. Base64 strings, Core snapshots, reports and retained original source bytes add overhead; these limits are not a process-memory cap.

## Partial semantics and provenance

This is a partial editable projection. It imports supported straight, single-elbow and bounded double-elbow connectors with same-scope attachments, safe direct click actions, [direct speaker-notes text](notes-import.md) and [table grids/merged rich-text cells](table-import.md) in addition to the profiles above. The [bounded chart profile](chart-import.md) includes bar, line, pie, doughnut, area and scatter subsets, with explicit cache/workbook priority and approximate preview. [Placeholder dimensions](placeholder-inheritance.md) can supply missing offsets/extents and supported preset names through unambiguous layout/master matches, with per-property provenance. The [bounded text style profile](text-style-inheritance.md) maps supported frame/list/paragraph/run properties from the matched source ancestry without copying prompt text. Optional profiles also cover limited [notes master content](notes-source-inventory.md), [master artwork](master-artwork.md), and backgrounds; consult the profile contracts for their scope and evidence. Unsupported chart families and drawing properties, SmartArt semantics, audio/video playback, animation playback and incomplete inheritance remain outside the projection. Images outside the profile above, unsupported table encodings, unsupported connector routes/actions, unsupported drawing families and shapes without complete local or supported inherited geometry remain absent from Core with source findings. Known siblings continue to import.

Straight `p:cxnSp`/`straightConnector1`, line connectors, unadjusted `bentConnector2`, and `bentConnector3` with its default or one literal `adj1` from 0 to 100000 retain free endpoints, direct stroke, supported target identities and cardinal sites for text rectangles, rectangles, rounded rectangles and ellipses in the same immediate drawing scope. Elbows become explicit Core route points; source rotation/flips are flattened once into the endpoints and waypoints. Endpoints resolve after the complete slide forest is known, so forward references work. Missing, cross-scope, unsupported-target and unknown-site attachments keep their cached free endpoint and receive an explicit unmapped finding; this fallback does not retain attachment semantics. Supported attachment references take precedence over cached endpoint geometry, while waypoints stay at their cached source coordinates. Adjusted `bentConnector2`, nonliteral/out-of-range `bentConnector3` adjustments, other bent and curved routes remain source-only. Fresh export uses the default path mode unless the caller explicitly requests `connectorMode: "native"`; that experimental mode writes native attachments and compatible elbows within its quantization limit, falling back for other routes. Native application editing/reopening remains unverified.

A [bounded custom linear-path profile](../architecture/import-export-boundaries.md) maps suitable `p:sp` geometry to open or closed round Core connectors; broader custom routes remain source-only. This does not create a source edit-save binding. A focused integration test performs three text-only preservation saves beside a closed path, checks that the custom-geometry XML is unchanged, and verifies that changing path geometry blocks the text save plan. This does not establish source path editing or general lossless reconciliation.

Direct click actions on drawing objects and text runs map HTTP/HTTPS/mailto URLs and resolved internal slide links. External links are recorded verbatim and never fetched. Macro, program, file, relative, media, hover, sound, unresolved and otherwise unsupported actions stay source-only with located findings. Paragraph defaults and end-insertion properties are not treated as authored run actions. SVG preview exposes link metadata for supported actions; it does not perform navigation.

Omitted or unresolved style values use reported Core defaults or neutral paints. These are not inferred source appearance. Unknown effects, geometry adjustments, theme colors/fonts outside the bounded profiles, differing script fonts, negative insets, positive first-line indent and unsupported attributes remain visible in the report. The [text-color profile](text-color-transforms.md) maps named color transforms and run alpha atomically; unsupported text transforms block both RGB and alpha. Other drawing paints may still project a base color while reporting unimplemented modifiers; the resulting object is not declared visually equivalent.

For each mapped object, `identities` records its Core ID, source part, numeric drawing identity and effective XML path. IDs are unique within a source slide; the slide identity makes Core IDs document-wide. Repeated numeric IDs within a slide, including its root group identity, reject. Source IDs may repeat in different parts.

Each object has seven operation findings. The `mapped-fields` feature marks only the interpreted subset editable for creation/import/edit/preview/fresh export. No-op is preserved and edit-save is unsupported. Unknown object/property features have distinct unsupported findings, with preserved no-op status. A part-level unsupported entry means the part has no **complete** mapping; it does not negate separately reported mapped fields. Reports also retain the source inspection's MCE decisions. Paths address the effective MCE tree; they are not byte offsets or guaranteed XPaths into the unprocessed XML.

The reader audits consumed source nodes and attributes. Uninterpreted subtrees are reported at their root; unimplemented attributes on interpreted nodes are reported individually. Nested findings inherit their owning object's source/Core identity when available. Reports are frozen, detached and bounded by `maxReportFindings`; source XML budgets cover all input branches, and cancellation checkpoints cover projection/audit work.

## Save boundary

An unchanged content projection supports byte-identical original-source no-op saves. Changing any normalized Core content blocks no-op and invalidates existing plans; restoring the exact baseline restores eligibility. Default edit and all rebuild plans remain blocked. Explicit `editSaveProfile: "text-runs-v1"` adds [existing text-box run character saves](text-edit-save.md) with source bindings, whole-plan guards, local XML/ZIP changes and candidate verification. The explicit [V2 owner profile](text-owner-save.md) also admits mapped shape text and direct notes-body runs; [V3](table-text-save.md) adds existing bound table-anchor characters. General source reconciliation, structural/asset edits, unknown-object closure updates and nonempty loss consent remain planned.

The independent [existing first-slide-number profile](first-slide-number-save.md) admits a single existing presentation attribute replacement; it does not combine with the text profiles.

Calling Exporter directly with the projected Core document creates a **fresh document** containing that projection. It omits unsupported source content and can use different defaults. This is not a preservation save and must not be presented as source round-trip. Consumers must review the report and establish their own explicit intent before choosing that workflow. See the [checked example](../examples/content-import.ts).

## Evidence and remaining work

Independent XML fixtures test both dialects, rich text, direct styles, nonzero/nested group origins, unknown effects/objects/attributes, duplicate IDs, malformed mapped values, report budgets, cancellation, isolation and no-op freshness. Text cascade fixtures additionally cover both dialects, all nine paragraph levels, source blockers/clearing, multiple masters, ambiguity, shared-template isolation and source provenance. A real browser compares normalized content and complete reports with Node, renders imported text and verifies source bytes. Installed consumers test the public runtime/types.

`pnpm test:import` exercises Core → Exporter → Parser → Renderer and fresh export/import using direct text/shape/group/image/connector/action fields. Image cases independently inspect actual image bytes, relationships, crop/opacity/frame XML and resource counts over three fresh projection exports, and replace a shared imported PNG with GIF. Reference cases verify forward and grouped connector attachments, slide/URL actions, copy/delete behavior and fresh export/import. They separately confirm preservation-save refusal. Chromium compares Node/browser reports and bytes, renders imported content, observes no requests for external-only pictures, and checks preview link metadata. These are bounded fixtures, not arbitrary producer certification; complete inheritance, broader image semantics, edit-save and object deletion reconciliation remain open under IMP-04/05/07/09.

The optional `node scripts/inspect-content-import.mjs [soffice-executable]` experiment converts the repository-authored direct-style fixture through LibreOffice, imports that application-produced PPTX and independently compares slide text using Python ZIP/XML inspection. The [recorded result](../testing/content-import-evidence.json) maps three objects and both nonempty text bodies, retains exact source no-op bytes, preserves that text inventory in fresh projection export and reopens the latter to PDF. It also records 32 unmapped-property import findings and three inheritance/default findings. This demonstrates a small native producer sample; it does not establish layout fidelity, arbitrary LibreOffice documents, interactive editing or preservation-aware edits.

The [table profile](table-import.md) adds independent physical-grid and merge fixtures, three fresh rounds, real Chromium pixel equality and installed consumers. Its [native evidence](../testing/table-import-evidence.json) independently compares source grids, anchor text and local transforms; the producer changes geometry/flips and collapses the all-merged 2×2 table into one cell. These producer losses are recorded separately from exact projection of its output. Native style fidelity, interactive table editing and preservation edits remain open.

The separate `node scripts/inspect-image-import.mjs [soffice-executable]` experiment uses a shared PNG across three pictures/two slides, including crop, opacity and a transformed group. Its [recorded result](../testing/image-import-evidence.json) checks the LibreOffice-produced picture relationships, resource SHA-256 digests, local frames at integer-EMU precision and exact crop fractions against an independent Python inventory. The same inventory survives fresh projection export, original-source no-op bytes are identical, and the projection reopens to PDF. LibreOffice changes source geometry and crop values; this experiment compares against that produced source, not the earlier authoring geometry. The separate [connector/action experiment](../testing/reference-import-evidence.json) checks source-produced connector names/sites and supported surviving action inventory against independent ZIP/XML inspection and a fresh projection export. In that run LibreOffice removed connector/group object actions, stripped surviving tooltips and normalized URL escaping; those producer changes are recorded explicitly. Neither experiment proves interactive movement/navigation, PowerPoint behavior, visual parity or preservation-aware edits.


The explicit content option [`diagramPreview: "cache"`](diagram-preview.md) projects bounded cached SmartArt drawing shapes or unavailable placeholders as ordinary Core groups. It defaults off, retains unknown freshness and separate fallback reports, and supplies no native node/edit-save semantics. Captured byte/file options and candidate reprojection retain this selection.


The separate [source master picture inventory](master-picture-inventory.md) reports effective master picture identities and relationships without enabling source edits. Content imports can opt in to `masterArtwork: "pictures-v1"`: verified listed master/layout relationships and explicit `showMasterSp` switches are represented in shared Core owners, and non-placeholder embedded rectangular pictures with complete positive frames use the same bounded image mapping and asset deduplication as slide pictures. Containing groups map their local origin, extent and transform, including nesting up to 48 group levels; groups lacking invertible child coordinates or mapped picture descendants are omitted. Placeholders, other artwork, backgrounds, theme inheritance, and unknown effects are not reconstructed; unmapped source subtrees and attributes are reported. Missing or unlisted ownership falls back to Core's default layout with an unsupported finding. Consequently the projection, its preview and fresh exports can differ substantially from the source. The option cannot be combined with text or chart preservation edit profiles; no-op save still returns original bytes only while the projected document remains unchanged. The default content profile remains unchanged.

`masterArtwork: "artwork-v1"` adds ordinary shapes in the same source drawing order, including within groups. It accepts the eight supported local presets; parallelograms additionally accept one bounded literal adjustment, a positive explicit frame, an explicit local no-fill or sRGB fill, and an explicit supported line paint (with width when visible). Shape text, placeholders, inherited or theme paint, missing lines and other geometry are omitted with findings; effects and other unhandled properties remain separately reported. This is a partial visual approximation, not a full source representation or a preservation editing profile. A [named PowerPoint-edited sample check](../../scripts/inspect-master-artwork-native.mjs) maps the blue backing shape, cropped transparent image and independent green shape, then samples four projected SVG pages; its [result](../testing/master-artwork-projection-evidence.json) binds the source hash. A fresh export was also observed in PowerPoint before and after one Save As/close/reopen, with [scoped evidence](../testing/master-artwork-projection-native-evidence.json); this does not establish arbitrary native fidelity or source-preserving editing.

`masterArtwork: "artwork-v2"` adds the existing direct text reader to eligible shared shapes, including nested shapes. Paragraphs, runs, breaks, empty paragraphs, direct text styles and frame fields use the same partial reader as slide text. It does not map placeholders, fields, hyperlinks/actions, master/layout text inheritance, theme font/color resolution or text preservation bindings; unhandled source nodes and attributes are reported. `textFontProfile` does not extend this master-shape reader. Core defaults can change appearance and the resulting fresh export is not a lossless source conversion. As with the earlier artwork options, preservation edit profiles cannot be combined with it; unchanged no-op save retains the original bytes.

`masterArtwork: "artwork-v3"` additionally resolves supported text theme font and color references in the source owner's scope: master shapes use their master theme, while layout shapes use their layout override and color map above the owning master. Text style provenance and its existing limits apply. Missing or unsupported selected declarations block that property rather than falling through. These values are materialized once in the shared definition: page-specific theme overrides are not applied to inherited artwork, and the profile does not yet resolve master text-style defaults, placeholders, fields or actions. The optional `textFontProfile` affects this reader using the same bounded font rules as slide text. This remains a partial projection with no source-preserving edit bindings.

`masterArtwork: "artwork-v4"` extends that owner-scoped resolution to explicit solid shape and line paints. Supported sRGB, system fallback and theme colors use the existing ordered tint/shade/luminance/saturation/alpha transform subset; an unsupported transform, missing theme slot or unrepresentable paint prevents that shape from being projected and is reported. Resolved paint dependencies are separately charged against `maxTextStyleDependencies`, in addition to the text provenance budget; that is not a hard process-work limit. The profile still requires explicit fill and line declarations, and does not map theme style-matrix references, gradients, inherited paints or page-specific theme changes. Colors are materialized values, not live theme links; unlike text style records, paint resolution does not expose a complete dependency provenance graph. Existing no-op and edit-save restrictions remain in force.

`masterArtwork: "artwork-v5"` additionally maps explicit solid `bgPr` backgrounds on verified masters, layouts and slides using each owner's own theme scope, retaining slide → layout → master precedence. It applies the same bounded paint and transform subset as `artwork-v4`. Absent backgrounds remain inherited; unsupported explicit backgrounds, including style-matrix `bgRef`, gradients and no-fill, are reported and Core's inherited fallback may differ from the source. Background effects, per-page overrides applied to inherited master/layout backgrounds and full dependency provenance are not modeled. This does not enable preservation edits; changing a projected background invalidates original-byte no-op save.

`masterArtwork: "artwork-v6"` additionally resolves `bgRef` against the owning theme's fill or background-fill matrix, including supported `phClr` placeholder colors and ordered color transforms. Only solid selected entries are materialized; missing or unsupported entries and no-fill sentinels remain reported fallbacks. The `artwork.background` finding includes bounded `resolvedFrom` source locations for selected matrix/color dependencies when available; this is not a complete package reference graph. Matrix dependencies share the separate artwork paint dependency budget. Values are fixed in their shared owner and cannot reflect later page-specific theme overrides; full background source editing remains unsupported.

`masterArtwork: "artwork-v7"` additionally projects direct linear `bgPr` gradients with 2–256 ordered stops, supported colors and transforms, an explicit linear direction, and no flip or tile rectangle. Stops share the artwork paint dependency budget. Missing gradient or linear attributes use hardcoded defaults and generate a finding because inherited attributes are not resolved. Unsupported gradients are reported and fall back to Core inheritance; gradient style-matrix entries, path gradients, effects, page-specific inherited theme changes and preservation editing remain unsupported. This profile materializes owner-scoped colors and does not establish PowerPoint visual parity. Older profile behavior remains unchanged.

`masterArtwork: "artwork-v8"` adds direct linear gradient fills on eligible master/layout shapes, including supported grouped shapes. It applies the same bounded stop, color transform and owner-scoped theme rules as direct background gradients. Unsupported gradient fills omit the shared shape with findings rather than silently substituting a solid; the profile does not add slide-local shape gradient projection or source-preserving edits. Native PowerPoint editing and general rendering fidelity remain unverified.

`masterArtwork: "artwork-v9"` additionally maps supported direct slide-local shape linear gradients, including shapes in supported groups. Each stop resolves in the slide's theme scope, and local gradient dependencies have a separate `maxTextStyleDependencies` budget from shared artwork. Unsupported gradients omit the affected shape with a finding; older profiles keep their previous behavior. This is still a partial content projection, not source-preserving shape editing or a claim of native visual parity.

`masterArtwork: "artwork-v10"` adds explicit horizontal, vertical, cross, downward-diagonal, upward-diagonal, diagonal-cross and twelve percentage pattern fills (5, 10, 20, 25, 30, 40, 50, 60, 70, 75, 80 and 90 percent) on supported shared and slide-local shapes, including supported groups. Foreground and background colors and supported transforms resolve in their owner's theme scope; selected dependencies are reported. Missing colors, unsupported presets or colors omit the shape with findings. The profile does not add background/table/line pattern import or source-preserving editing, and native appearance remains unverified.

`masterArtwork: "artwork-v11"` additionally projects one centered outer shadow on supported shared and slide-local shapes, including groups. Distance, direction, alignment, rotation-with-shape, and color must be explicit and within the Core bounds. A missing blur radius falls back to zero with a finding; producer-specific or inherited defaults are not resolved. Supported RGB, system fallback and theme colors are resolved in the owning scope, with selected dependencies reported. Multiple effects, effect DAGs, scaling, skew, unsupported colors and other shadow forms remain unprojected and reported. The rest of the shape can still be projected. No-op save retains original bytes; source-preserving shadow edits and native appearance are not established.

Embedded `image/apng` parts with a PNG signature and positive PNG header dimensions are projected using their declared MIME, like other header-classified raster assets. This does not validate APNG control chunks, decode frames or establish playback; image findings retain that limitation. Rebuilding may package the image as `image/png`, whereas no-op preservation retains the original part and declaration.

For mapped direct gradients, background findings and the `master-artwork.gradient-dependencies` / `drawing.gradient-dependencies` findings include selected stop locations and resolved color dependencies in `resolvedFrom`. Their work is charged to the corresponding existing artwork paint dependency budget. These bounded locations describe selected dependencies, not every attribute or a complete package reference graph; unsupported gradients do not publish partial successful dependency traces.

One [authored background-matrix sample](../../scripts/prepare-background-matrix-native.mjs) with master, layout and slide overrides was displayed in PowerPoint 16.104 before and after projection, and again after Save As/close/reopen. An [independent source, output and screenshot check](../../scripts/research/oracles/background-matrix-native.py) and [bound evidence](../testing/background-matrix-native-evidence.json) cover that sample only; screenshots do not independently prove the UI sequence, and the experiment did not edit objects or perform a source-preserving save.
