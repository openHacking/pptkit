# Missing description inspection

`inspectMissingDescriptions(document)` is an explicit, synchronous Core review of authored image, chart and table objects. It first runs `validatePresentation` and throws `PresentationValidationError` if errors exist. It returns a frozen `DescriptionInspection` with `scope: "authored-definitions"` and frozen `missing-description` findings. Each finding identifies its element type, stable element ID, authoring path and exactly one owning slide, layout or master ID. It does not mutate the document or implicitly run during validation, export or preview.

<!-- doc-test: docs/examples/accessibility-descriptions.ts -->
```ts
import { inspectMissingDescriptions, type PresentationDocument } from '@pptkit/core';

export function reviewDescriptions(document: PresentationDocument) {
  const report = inspectMissingDescriptions(document);
  return report.findings.map(({ elementId, path, slideId, layoutId, masterId }) => ({ elementId, path, slideId, layoutId, masterId }));
}
```

Only an explicit non-whitespace `element.accessibility.description` satisfies the check. An object name or an image asset's description does not: the current exporter and SVG renderer use the element's description or name, rather than the asset description, for object accessibility. A description's presence is not a judgment of its quality. Hidden slides, hidden elements and elements marked decorative are skipped; a hidden or decorative group suppresses its descendants. A described group does not satisfy its children's descriptions. Shape, connector and text descriptions, table header semantics and group-level descriptions are outside this check.

Fresh PPTX export writes the explicit decorative flag as an Office Drawing decorative extension on the object's nonvisual properties, including a group and both physical owners of a transformed table. Hyperlink markup precedes the extension. Content import projects a unique recognized extension with explicit `1`, `0`, `true` or `false` into the mapped object's flag and records its source path. The selected shared-master artwork profiles do the same for mapped objects. Ambiguous duplicates, missing or invalid values, unknown namespaces, attributes or nested content stay source-only and are reported; unrelated neighboring extensions remain reported. Original-byte no-op retains the complete source. Projection does not grant permission to edit the decorative flag in a preservation save, and fresh generation from a partial projection can omit unsupported source content. The extension is an authored declaration, not proof that a target application or assistive technology suppresses the object or its descendants. Asset-level decorative metadata is not substituted for the element flag. [Microsoft's decorative schema](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-odrawxml/1c5cfa5e-0042-48e3-ba41-2cc88fcc0266) defines the flag; [export tests](../../packages/pptx-exporter/test/decorative.test.mjs), [import tests](../../packages/pptx-parser/test/decorative-import.test.mjs) and [cross-package tests](../../scripts/decorative-export-parity.test.mjs) cover owner identity, both dialects, negative inputs, three fresh projections, byte-exact no-op and browser parity. Native interactive and assistive-technology verification remain pending.

For a bound text-box run, the text-only preservation profile can update characters without changing the decorative extension or neighboring unknown extensions. The import tests independently compare all package parts and exact affected XML across three successive saves in both dialects; the cross-package test also compares Node and browser outputs over three rounds. This does not admit changing the decorative property itself, unrelated formatting or an unknown extension.

`importPptx(bytes, { projection: "content", descriptionEditSaveProfile: "existing-v1" })` explicitly admits one changed existing slide-object description per edit plan. The `attribute-v2` profile additionally permits inserting a missing description or removing an existing one; an empty string is an explicit empty attribute, distinct from absence. `batch-v3` admits multiple such changes atomically, including several in one source part or on different slides. `mixed-v4` requires `editSaveProfile: "text-runs-v3"` and additionally combines bound text-run edits with these description changes, including in the same XML part. `mixed-v5` also permits the optional `chartEditSaveProfile: "existing-values-v1"` and `firstSlideNumberSaveProfile: "attribute-v2"`, allowing bound chart/workbook values and the starting page number in the same transaction. Views of a shared raw attribute must agree; conflicts block the entire plan. Analysis, per-part editing and candidate comparison are bounded by the existing change, output and validation budgets. Multiple property edits in one XML part are bound together, patched in one pass and verified by one candidate parse; duplicate or conflicting attribute targets reject atomically. Seeded mixed-presence batches are compared byte-for-byte with the existing single-attribute edit path across UTF-8 and UTF-16, and a 200-object slide is checked under a bounded transaction budget. The source attribute or its absence must be directly bound to the raw object/nonvisual/property ancestry, dialect, drawing ID and imported value; a property promoted through an MCE wrapper stays unbound. After changing the imported object's `accessibility.description`, prepare an `edit` plan and save it through the same session. A finding `drawing.description-existing` or `drawing.description-attribute` identifies binding eligibility; package policy, source closure, snapshot stability, output limits and full candidate reimport still gate the plan. The resulting assurance is `scoped-preservation`. No-op plans retain original bytes. V1 still rejects insertion/removal and V1/V2 reject multiple descriptions; V1–V3 reject text edits. Description profiles without the optional drawing-name or decorative profiles reject those changes, shared master/layout ownership and other unsupported extended profiles rather than silently dropping them. This is not a general-purpose property editor or native application verification.

`importPptx(bytes, { projection: "content", drawingNameSaveProfile: "existing-v1" })` separately permits a batch of existing, directly bound slide-object `name` attribute changes. The source attribute must exist and match the projected name; absent or MCE-promoted properties remain unbound. Empty strings are explicit names, not attribute deletion. Alone, the profile admits no other edit or optional content projection profile. It may also be combined with `descriptionEditSaveProfile: "mixed-v5"` and `editSaveProfile: "text-runs-v3"`, plus the optional compatible chart-value and starting-number profiles, so names and descriptions on the same object can be changed atomically with other supported edits. Each plan checks the complete document, shared-source conflicts, source closure, budgets and candidate reprojection; non-target bytes are retained. A `drawing.name-existing` finding identifies eligible bindings without guaranteeing a save. Both dialects, exact affected XML, three reopen rounds, rejection and browser/Node file parity are tested; native application editing and assistive technology effects remain unverified.

`importPptx(bytes, { projection: "content", decorativeSaveProfile: "existing-v1" })` permits changing the Boolean value of an existing, unique, directly bound Office decorative extension. It neither inserts nor removes the extension. The raw object, nonvisual, extension-list, extension and decorative-node ancestry must all match the effective projection; missing, ambiguous, MCE-promoted or unsupported content is not bound. Unknown sibling extensions remain untouched. The option can also join `mixed-v5` with the compatible name, text, chart and numbering profiles; complete snapshot, source closure, shared-source consistency, validation budgets and candidate reimport still gate each plan. Both dialects, three reopens, non-target bytes, browser parity and rejection cases are tested. A [LibreOfficeDev headless experiment](../testing/drawing-properties-libreoffice.md) records retained names, descriptions and `val="1"`, but loss of explicit `val="0"` and the starting-number declaration after conversion. Interactive application and assistive technology behavior remain unverified.

The private character-valued XML primitive and its bounded batch variant's [tests](../../packages/pptx-parser/test/xml-relationship-id.test.mjs) cover exact non-target bytes across UTF-8 and UTF-16, Unicode and XML whitespace, stale values, namespace identity, bounded expansion, cancellation and three edits; a [browser DOM comparison](../../scripts/xml-relationship-browser.test.mjs) independently checks decoded values. [Description save tests](../../packages/pptx-parser/test/drawing-description-binding.test.mjs) cover both dialects, source ownership, nested groups, insertion/empty/removal, batches and text/description combinations across source parts, table cells and notes, three rounds, exact target XML, non-target part bytes, shared-source conflicts, budgets, unsupported combinations and stale plans; [cross-package browser parity](../../scripts/decorative-export-parity.test.mjs) checks the first four profiles on decorative objects and mixed-v5 with chart and numbering over three rounds. [Chart save tests](../../packages/pptx-parser/test/chart-save.test.mjs) check the mixed-v5 transaction in both dialects, including names and descriptions on the same XML nodes, unbound chart rejection and a shared change limit. Insertion or removal of the decorative extension remains unsupported.

Slides are visited in source order, then each layout and master definition once, with nested children in source order. Layout/master objects are reviewed even when currently unused or suppressed on a particular slide; the result is a definition inventory, not per-slide effective visibility or an assistive-technology reading order. IDs and paths locate current authoring state and should be recaptured after edits. The analysis does not evaluate contrast, inherited occurrences, source-preserving editability, native application behavior or accessibility conformance. SVG and native PPTX may expose different semantics; check them separately in the intended application and assistive technology.

`inspectEffectiveMissingDescriptions(document, { maxFindings })` expands the same authored findings into modeled slide occurrences. The optional nonnegative safe-integer limit defaults to unlimited; exceeding it throws `EffectiveDescriptionLimitError` without returning a partial report. Each frozen finding includes the affected `slideId`, definition `path`, object ID and frozen `source: { kind, id }` for its slide, layout or master owner. Hidden slides and suppressed hidden/decorative subtrees are excluded. A slide's `showInheritedShapes: false` suppresses both inherited owners; a layout's `showMasterShapes: false` suppresses only its master. Unused definitions do not produce occurrences. A shared object can produce a separate finding for each affected slide. Results are emitted in slide order and then master, layout, slide owner order, with definition preorder inside each owner; this is an inventory order, not a native or assistive-technology reading-order guarantee. Only modeled artwork is covered, not imported unknown objects, runtime animation states, native placeholders or application-specific visibility. The function validates first and never changes the document. Recapture paths and occurrence identities after edits, copies or layout changes.

The [Chromium accessibility-tree test](../../scripts/svg-accessibility-tree.test.mjs) observes named images and charts, a named table, and ordinary groups with their children, and verifies that a decorative group, its child and a decorative image are absent from unignored nodes. SVG exposes an ordinary group with role `group`, using its description or name. A nested group retains its chart and table descendants, and a link on the group remains a separate ancestor. An action on a decorative group still exposes its outer link; an action inside that group's hidden subtree is absent. Core validation emits a located `decorative-action` warning for actions on decorative objects or within their descendant objects and text runs, since target renderers can expose them differently. The warning does not remove the action or change PPTX export. In SVG, links inside the decorative subtree are skipped by Tab and Shift+Tab, including object links in nested groups and links in text runs, shape text and table cells. The outer link on a decorative object remains in the tab sequence unless it is itself inside a decorative group. Descendant links still have URLs and can be activated with a pointer or focused by script; the tab-order change is not an interaction block. Review the intended interaction before marking an actionable object decorative. The test also observes a table and cell; a separate case checks the explicit table header roles described below. The nested-group behavior is checked both inline and in a standalone SVG document. These are Chromium DevTools accessibility-tree observations for controlled fixtures, not a test with a named assistive technology, other browser or PowerPoint.

The same test traverses the tree by parent/child links for three shapes and a group before and after moving, atomically reordering top-level objects and group children by stable ID, duplicating and deleting objects; the observed object sequence matches the generated PPTX drawing XML order at each step. It also verifies new identities for a duplicated group and its children. Batch reordering changes drawing and stacking order; it is not a separately authored reading-order model, proof of native application reading order, or a guarantee about other object types or assistive technologies.

[Core tests](../../packages/core/test/accessibility-descriptions.test.mjs) cover owner identities, nested and suppressed groups, hidden slides, names/assets, blank descriptions, invalid documents, frozen results and unchanged normalized state. [Browser parity](../../scripts/accessibility-descriptions-parity.test.mjs) covers Node, browser ESM and global exports. ADV-10.1.1 and its parent remain open for native reading-order authoring, native table header semantics and native/assistive-technology verification; ADV-10.1.2 contrast remains separate.

### Table header roles in SVG

Set `headerScope: "column"` or `headerScope: "row"` on a table cell to identify an explicit header. The option is independent of styles such as `firstRow`; cells without it remain data cells. On a merged cell, set it on the anchor. SVG exposes one header at the anchor's physical row and column, with its full row and column spans. The legacy HTML table path emits a scoped `th`. A decorative table suppresses its cell roles in the observed Chromium tree.

Both SVG renderer paths put the object description, or its fallback name, on the table node itself. The surrounding SVG frame retains the object ID, and an object link remains a separate accessible link. Chromium tests verify that the named table contains the headers and cells, with no duplicate image node, including horizontal and vertical merges and unmarked styled cells. They do not establish a specific screen reader's header announcements or support custom header associations. PPTX export keeps the native editable table and its formatting unchanged and emits `table-header-semantics-not-exported` for each table with authored roles. PPTX import does not infer these roles from native style flags. The separate `nativeFirstRowStyle` option retains the native toggle; see the [PowerPoint Header Row experiment](../testing/powerpoint-table-header.md).

### Independent SVG reading order

Author a slide's reading order in `addSlide({ readingOrder: [...] })`, in CLI authoring JSON or with the managed slide's `setReadingOrder` method. The scope uses `{ elementIds }` for roots and `{ groupId, elementIds }` for group children. Core captures a frozen snapshot and carries it through normalization and Layout. Deleting, hiding or marking an object decorative removes its references from configured scopes; newly eligible objects append in drawing order. A removed or inaccessible group loses its scope. Whole-slide copies remap the IDs and layout rebind keeps the order on local objects. Table continuation slides have their own default order; the original slide retains its order.

Pass `readingOrder: [{ slideId, elementIds }]` to `renderPresentationToSvg`, `renderLayoutToSvg` or `renderIncrementalSvg`. Without `groupId`, the array is a complete permutation of the visible, non-decorative top-level objects owned by the slide. With `groupId`, it orders the direct children of a visible, non-decorative slide-owned group, including a group nested inside another group. You can specify one root order and separate orders for several groups on the same slide. Inherited artwork and unconfigured groups keep their order. Targets use stable object IDs; an entry cannot move an object across owners. Renderer overrides must be recaptured after editing the corresponding objects. Without an override SVG uses the authored order on visible slides; an explicit empty list renders every slide in drawing order. An omitted order preserves the default SVG.

The renderer keeps the painting order and uses the [WAI-ARIA ownership relationship](https://www.w3.org/TR/wai-aria/#aria-owns) for the accessibility tree. For this opt-in preview, the slide root is a named group. Use separate `idNamespace` values when embedding separate results together. Because this does not reorder keyboard focus, a permutation containing URL actions on the reordered artwork or its accessible descendants is rejected. Slide-target metadata is not an interactive link in standalone SVG. Changing one permutation invalidates that slide's incremental preview only. Changing the order of the scope entries has no effect.

Chromium tests inspect traversal, independently reordered nested groups and exact screenshot equality for overlapping objects in the default and reordered inline SVG. They also check standalone SVG, side-by-side ID isolation and incremental reuse. PPTX generation keeps native drawing order and reports `reading-order-not-exported` for slides with authored orders. No independent reading order is written to, or inferred from, native PPTX. In a [PowerPoint 16.104 experiment](../testing/powerpoint-reading-order.md), changing the Reading Order pane also reversed shape-tree order and visible stacking after save/reopen. Named screen-reader behavior and other browser engines are unverified.
