# Core metadata source-preserving save

Factory-owned documents expose `setMetadata(metadata)`, which replaces the **complete** metadata value with a detached, frozen snapshot after validating supported field types. To change one field while keeping the others, pass `{ ...document.metadata, title: "New title" }`. Invalid values throw before mutation; custom `PresentationDocument` implementations may omit the optional method. The setter does not read a clock or infer author, revision or timestamps.

`importPptx(bytes, { projection: "content", metadataSaveProfile: "core-strings-v1" })` admits character edits to existing directly bound core-property `title`, `creator` (Core `author`), `subject`, `description` and `language` elements. The unique OPC core-properties part and relationship must already exist, and each admitted element must be a direct child of the raw core-properties root with its imported text unchanged at binding time. Empty existing elements and character-only CDATA are eligible; replacing their contents may normalize their target text syntax. Attributes and other source regions are preserved. Missing properties or properties containing comments, processing instructions or child markup cannot be inserted or rewritten by this profile.

The opt-in report provides `coreMetadataSources`, one bound/unmapped record for each of the five fields. A bound record identifies the source element but does not guarantee a save; absent parts, missing properties and mixed content are reported unmapped. Several fields may be changed atomically. Other metadata fields, including revision, keywords, company and dates, remain outside this write profile; an unadmitted change blocks the entire plan. No author, revision or timestamp is updated unless the caller explicitly changes an admitted field. Compatible text, chart, visibility and starting-number edits may join the transaction; description, object name and existing decorative-value edits may join through `descriptionEditSaveProfile: "mixed-v5"` and `editSaveProfile: "text-runs-v3"`. Picture replacement and other excluded content projections cannot be combined. Source package policy, part guards, relationship closure, snapshot stability, budgets, package comparison and full candidate reprojection still apply. No-op retains the original ZIP bytes.

The CLI supports `inspect source.pptx --projection content --metadata-values --json` and a hash-bound `--metadata-edits` manifest; see [CLI save](cli-save.md).

`metadataSaveProfile: "core-values-v2"` additionally admits an explicit change to an existing direct `revision` element whose source text is a canonical nonnegative safe integer. The report adds a revision binding; absent, mixed, noncanonical or unsafe values remain unmapped. Set `document.metadata.revision` explicitly to another nonnegative safe integer; negative zero is rejected because it cannot round-trip as a distinct value. The writer never increments it automatically. V2 can be combined with the same compatible edit profiles as v1. The CLI exposes this through its opt-in v2 metadata manifest.

One [LibreOfficeDev headless control and three-resave experiment](../testing/core-revision-libreoffice.md) retained the explicit revision value; both branches had their keywords rewritten. PowerPoint and interactive behavior remain unverified.

`metadataSaveProfile: "core-keywords-v3"` additionally admits replacing the sole Core keyword entry when the existing `keywords` element contains only one unsegmented text/CDATA segment (or is empty), has no language annotation, and matches the projected aggregate string. Keep `keywords` as a one-element array; adding, removing or splitting entries is unsupported. Missing, language-tagged, child-value, mixed and multi-segment sources stay unmapped. V3 includes the v2 revision behavior. Parser and CLI tests cover three reopens in both dialects and mixed revision changes; browser ESM and global bundles match Node. A [LibreOfficeDev headless comparison](../testing/core-keywords-libreoffice.md) shows comma removal in both the edited and unchanged samples. PowerPoint and interactive editing remain unverified.

`metadataSaveProfile: "extended-company-v4"` additionally admits an existing direct character-only `Company` element in the extended-properties part. Its raw root and parent, source value and reimported candidate are verified; compatibility-processed, missing or mixed-content sources remain unmapped. The profile retains v3 capabilities and supports the same compatible mixed transactions. [Parser tests](../../packages/pptx-parser/test/extended-company-save.test.mjs) and CLI tests cover both dialects, three reopens and preservation of neighboring values; browser ESM and global bundles match Node. A [LibreOfficeDev headless comparison](../testing/extended-company-libreoffice.md) retained this sample's edited and control values while rewriting other extended properties. PowerPoint and interactive editing remain unverified.

`metadataSaveProfile: "core-insert-v5"` additionally allows missing `title`, `author`, `subject`, `description` and `language` elements to be inserted into an existing unambiguous core-properties part. The source report marks such fields `insertable`; a changed Core value triggers insertion, subject to the same guards and candidate reprojection. An absent core-properties part cannot be created by this profile. Because normalized defaults can equal an absent title, author or language, setting such a field to its existing normalized default does not itself constitute a detectable edit. Use `prepareSave({ mode: "edit", coreMetadataInsertions: ["title", "author", "language"] })` to explicitly insert selected missing fields, including those defaults. The selection must contain unique supported fields with insertable source bindings and string values in the normalized candidate; it may be combined with other supported edits. An absent optional subject or description must first be assigned a string. [Tests](../../packages/pptx-parser/test/core-metadata-insert.test.mjs) cover both dialects, three reopens, mixed operations, signature guards and failures. [Browser parity tests](../../scripts/custom-properties-browser-parity.test.mjs) cover explicit insertion and three saves in Node, browser ESM and global bundles. The CLI exposes v5 through `--metadata-insert` and a hash-bound manifest; tests cover both dialects and three reopens. [A scoped LibreOfficeDev headless comparison](../testing/core-insert-libreoffice.md) recorded three resaves and application changes in the control. [One PowerPoint sample](../testing/core-insert-powerpoint.md) was saved and reopened three times with the inserted values retained; metadata UI editing and broader source coverage remain open.

`createdAt` and `modifiedAt` are optional Core metadata fields containing explicit canonical UTC timestamps with millisecond precision, such as `2020-02-29T12:34:56.123Z`. Core validates them and never infers the current time. Fresh export writes supplied values as `dcterms:created` and `dcterms:modified` with `xsi:type="dcterms:W3CDTF"`; absent values are omitted. Import projects explicitly zoned values that are valid and exactly representable in milliseconds to UTC, while retaining the source lexical value in the inspection inventory. Unzoned, unknown-offset, invalid or sub-millisecond values remain source-only.

`metadataSaveProfile: "core-date-values-v6"` adds source-bound edits of existing direct created and modified dates. It retains v5 behavior, verifies raw ancestry and the original source text, writes explicit canonical UTC replacements, and preserves the original type attribute and non-target bytes. Missing dates cannot yet be inserted and unsupported date values cannot be edited. [Tests](../../packages/pptx-parser/test/core-date-save.test.mjs) cover both dialects, offset conversion, three reopens and unsupported sources. [Browser parity tests](../../scripts/custom-properties-browser-parity.test.mjs) cover Node, ESM and global bundles. The CLI exposes the same profile through `--metadata-dates` and a v6 hash-bound manifest. [A LibreOfficeDev headless comparison](../testing/core-date-libreoffice.md) observed three resaves of an existing created-date edit and a modified-date insertion; it lost fractional seconds in both branches. PowerPoint and interactive behavior remain unverified.

`metadataSaveProfile: "core-date-insert-v7"` also inserts missing created and modified dates into an existing unambiguous core-properties part. Set the corresponding Core field to a canonical UTC timestamp; the report identifies eligible missing fields as `insertable`. The inserted direct element declares its own date namespace and `xsi:type` as `W3CDTF`. Existing dates retain the v6 behavior, and eligible title and other string insertions can share the transaction. Missing parts and unsupported existing date values remain blocked. Parser and [browser parity](../../scripts/custom-properties-browser-parity.test.mjs) tests cover three reopens, both dialects, encoding and guards. The CLI exposes this profile with `--metadata-date-insert`. A [LibreOfficeDev headless comparison](../testing/core-date-libreoffice.md) lost fractional seconds on the edited and control branches; PowerPoint and interactive behavior remain unverified.

`metadataSaveProfile: "core-create-v8"` additionally creates a missing core-properties part for supported string or date insertions. It plans a collision-free part and package relationship, checks raw relationship closure, content-type declarations, candidate differences and reimported Core state. Explicit `coreMetadataInsertions` can create a default-valued string; date fields are inserted when explicitly set. It can create the custom-properties part in the same transaction, with both declaration changes merged. Unsupported or ambiguous sources remain blocked; missing revision and keywords cannot be created by this profile. [Tests](../../packages/pptx-parser/test/core-property-create.test.mjs) cover both dialects, three reopens, combined creation, collisions and guarded failures. The CLI exposes v8 using `--metadata-create` and a hash-bound manifest. A [LibreOfficeDev combined-creation comparison](../testing/combined-property-create-libreoffice.md) observed retained sample values alongside timestamp precision loss and type/ID rewrites; PowerPoint and interactive editing remain unverified.

`metadataSaveProfile: "core-revision-insert-v9"` adds insertion of a missing revision in an existing or newly created core-properties part. A changed nonnegative safe integer is inserted automatically; to insert Core's normalized default `1` when it equals the baseline, pass `coreMetadataInsertions: ["revision"]` to the edit plan. Existing malformed, noncanonical or unsafe source revisions remain unmapped. This profile retains v8 behavior; it never increments the revision automatically. [Tests](../../packages/pptx-parser/test/core-revision-insert.test.mjs) cover both dialects, default and changed values, combined creation, guards and three reopens. The CLI exposes v9 through `--metadata-revision-insert`. Application behavior remains unverified.

`metadataSaveProfile: "core-keywords-insert-v10"` adds insertion of a missing core `keywords` element in an existing or newly created core-properties part. Assign exactly one Core keyword string, including an empty string; empty arrays mean no insertion and multiple strings are rejected by the save profile. Existing segmented or language-tagged keyword sources remain unmapped. The operation can be combined with v9 edits and custom-part creation. [Tests](../../packages/pptx-parser/test/core-keywords-insert.test.mjs) cover both dialects, empty and escaped values, three reopens and guarded failures. The CLI uses `--metadata-keywords-insert`; native application behavior remains unverified.

`metadataSaveProfile: "extended-company-insert-v11"` allows inserting a missing company string into an existing unambiguous extended-properties part without compatibility processing. Set `company` to a string, including an empty string; the report marks eligible sources `insertable`. The source root, sibling bytes, guards and reimported state are verified. This profile retains v10 behavior and can combine company insertion with core and custom part creation. A missing extended-properties part cannot yet be created. [Tests](../../packages/pptx-parser/test/extended-company-insert.test.mjs) cover both dialects, three reopens, encoding and protected sources. The CLI uses `--metadata-company-insert`; application behavior remains unverified.

`metadataSaveProfile: "extended-create-v12"` additionally permits creating a missing extended-properties part when the raw package declarations and relationship closure allow it. Set `company` to a string; core and custom parts can be created in the same transaction. Collision-free part and relationship identities, the resulting package declarations, preserved parts and the reimported document are validated. Ambiguous or conflicting declarations remain rejected. [Focused tests](../../packages/pptx-parser/test/extended-property-create.test.mjs) cover both dialects, combined creation and three reimports. The CLI exposes this profile with `--metadata-extended-create`. A [LibreOfficeDev headless observation](../testing/extended-create-libreoffice.md) retained one sample's title, company and custom numeric value across three resaves while rewriting the custom type; PowerPoint and interactive behavior remain unverified.

`metadataSaveProfile: "metadata-remove-v13"` adds removal of existing bound `subject`, `description` and `company` properties. Omit the corresponding optional Core field and prepare an edit; an empty string remains an existing property. Only direct character-only elements without non-namespace attributes and without compatibility processing are eligible. Bound source reports expose `removable`; a true value is eligibility rather than a guarantee that package guards will permit a save. The writer removes the selected element without reserializing neighbors, retains its containing part and checks the candidate package and reimported document. Other metadata deletion, ambiguous sources and unknown attributes remain unsupported. The profile retains v12 capabilities and may combine deletion with supported edits and insertions. [Tests](../../packages/pptx-parser/test/metadata-remove.test.mjs) cover both dialects, three reimports, neighboring edits and rejection paths. The CLI exposes `--metadata-remove`. A [LibreOfficeDev comparison](../testing/metadata-remove-libreoffice.md) retained absence of company but replaced the deleted subject and description with empty elements; PowerPoint and interactive behavior remain unverified.

`metadataSaveProfile: "metadata-date-remove-v14"` extends v13 to remove bound `createdAt` and `modifiedAt` by omitting them from the metadata. Dates must be exactly representable in Core and have only namespace declarations and the validated `xsi:type` attribute; other attributes or compatibility-processed parts are not eligible. The raw typed element is removed, not normalized first, and `removable` reports source eligibility. [Tests](../../packages/pptx-parser/test/metadata-date-remove.test.mjs) cover both dialects, offset dates, three reimports, mixed edits and rejection paths. The CLI exposes `--metadata-date-remove`. A [LibreOfficeDev headless comparison](../testing/metadata-date-remove-libreoffice.md) kept dates absent in one edited sample but dropped fractions from its control; PowerPoint and interactive behavior remain unverified.

`metadataSaveProfile: "metadata-keywords-remove-v15"` extends v14 to remove one bound, unsegmented keyword by setting `keywords` to `[]`. A one-element array containing an empty string retains an empty keyword element. Language-tagged, segmented, mixed-content or compatibility-processed sources are not eligible; other attributes beyond namespace declarations are excluded. The writer preserves the part and neighboring bytes, and the report indicates `removable` eligibility. [Tests](../../packages/pptx-parser/test/metadata-keywords-remove.test.mjs) cover both dialects, three reimports, empty values, mixed edits and rejection paths. The CLI exposes `--metadata-keywords-remove`. A [LibreOfficeDev comparison](../testing/metadata-keywords-remove-libreoffice.md) kept the keyword absent in one edited sample while removing a comma from its control; PowerPoint and interactive behavior remain unverified.

`metadataSaveProfile: "metadata-revision-remove-v16"` extends v15 with explicit removal of a bound canonical revision. Omit `revision` from the metadata and request `prepareSave({ mode: "edit", coreMetadataRemovals: ["revision"] })`. Normalization uses 1 for a missing revision, so the explicit selection is necessary even when the source value is already 1; the normalized candidate must equal 1. The same field cannot be simultaneously inserted and removed. An unbound, noncanonical, mixed-content or compatibility-processed source cannot be removed. The source report marks eligibility, not a guarantee that package guards will permit the transaction. [Tests](../../packages/pptx-parser/test/metadata-revision-remove.test.mjs) cover both dialects, default and nondefault revisions, three reimports and mixed/failed transactions. The CLI exposes `--metadata-revision-remove`. In one [LibreOfficeDev comparison](../testing/metadata-revision-remove-libreoffice.md), a removed revision was reintroduced as `0`; PowerPoint and interactive behavior remain unverified.

`metadataSaveProfile: "metadata-default-remove-v17"` extends explicit removal to bound `title`, `author` and `language`. Omit selected fields from the metadata and include them in `coreMetadataRemovals`; the corresponding normalized candidate values must be `PPTKit Presentation`, `PPTKit` and `en-US`. This explicit selection also handles sources already equal to these defaults. Eligible direct character-only source nodes must have no non-namespace attributes or compatibility processing. All selected removals and compatible edits are checked atomically; a field cannot be both inserted and removed. [Tests](../../packages/pptx-parser/test/metadata-default-remove.test.mjs) cover both dialects, three reimports, mixed edits, defaults and failure paths. The CLI exposes `--metadata-default-remove`. A [LibreOfficeDev comparison](../testing/metadata-default-remove-libreoffice.md) observed empty title and author plus `zh-CN` language after one sample's removal; PowerPoint and interactive behavior remain unverified.

The same test also combines v17 default-property removal with `create-and-append-v5` custom-property creation in one transaction, then reinserts/removes the defaults while editing the custom value through three reopens in both dialects. An invalid addition blocks the entire plan and a corrected request can be retried; non-target payloads remain byte-identical and package relationships and content types change only during creation. [Node and browser ESM/global parity](../../scripts/custom-properties-browser-parity.test.mjs) covers the same sequence for the Transitional fixture. This is a synthetic package test, not native application or UI evidence.

```ts
import { importPptx } from "@pptkit/pptx-parser";

export async function removeSourceTitle(source: Uint8Array): Promise<Uint8Array> {
  const session = await importPptx(source, { projection: "content", metadataSaveProfile: "metadata-default-remove-v17" });
  try {
    const title = session.report.coreMetadataSources?.find(item => item.field === "title");
    if (!title?.removable || !session.document.setMetadata) throw new Error("Title source is not eligible for removal.");
    const metadata = { ...session.document.metadata };
    delete metadata.title;
    session.document.setMetadata(metadata);
    const prepared = await session.prepareSave({ mode: "edit", coreMetadataRemovals: ["title"] });
    if (prepared.status !== "ready") throw new Error(prepared.report.diagnostics.map(item => item.message).join("\n"));
    return (await session.save(prepared.plan)).bytes;
  } finally {
    session.dispose();
  }
}
```

## Authored custom properties

`PresentationMetadataInput.customProperties` optionally contains an ordered array of `{ name, type, value }` records. Supported types are `string`, `boolean`, `integer` (signed 32-bit), `real` (finite JavaScript number) and `date` (a valid canonical UTC timestamp such as `2020-01-02T03:04:05.000Z`). Names are nonempty and unique with exact string comparison. The managed document validates and snapshots the array; `setMetadata` replaces the whole metadata object atomically. An absent array produces no custom-properties part; an empty array produces an empty part. Fresh PPTX export assigns sequential package property IDs and writes the corresponding typed values. These IDs are output identities, not stable Core identities.

Structural and content import project the supported named, unlinked source subset into Core; unsupported values remain inspection-only with individual findings. The opt-in custom scalar save profile described below supports selected source-preserving value edits; no-op save retains original bytes. Unsupported variant types, arbitrary precision, date offsets, original format IDs and source lexical spelling are not mapped into this authoring model. Cross-application resaves can reorder, renumber or change variant types as shown by the [LibreOfficeDev observation](../testing/custom-properties-libreoffice.md); A [three-round LibreOfficeDev headless experiment on PPTKit-authored properties](../testing/authored-custom-properties-libreoffice.md) records actual rewrites; PowerPoint UI behavior remains unverified.

[Cross-runtime tests](../../scripts/custom-properties-browser-parity.test.mjs) compare Node, browser ESM and global output, imports, source findings and no-op bytes for the authored subset.

Fresh export protects literal `_xHHHH_` sequences in custom-property names and string values by escaping the initial underscore. Import projects that escaped-literal form while inspection retains the source spelling. Other encoded values remain inspection-only. Overlapping escape-like sequences, such as `_x005F_x0041_`, reject on fresh export and remain inspection-only: a LibreOfficeDev headless probe changed such a value on resave. Decoded-name collisions are reported unsupported. The earlier unescaped-value observation is recorded with [hashes and scope](../testing/custom-property-escape-observation.json); Microsoft describes the literal escape convention for [variant strings](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.varianttypes.vtbstring?view=openxml-3.0.1).

`importPptx(bytes, { projection: "content", customPropertySourceProfile: "raw-v1" })` adds `customPropertySources` to the report, one record per inspected custom property. A bound record identifies both the direct property and direct scalar value elements in the original XML; commented values, opaque variants and compatibility-processed parts remain unmapped. This is an identity inventory only: it does **not** authorize custom-property edits or guarantee a save plan. The profile also works through the Node file import API and is subject to the session finding budget.

## Source-preserving custom scalar edits

The [fresh-property application comparison](../testing/fresh-properties-libreoffice.md) independently checks authored types, identities, absent/empty semantics and observed LibreOfficeDev rewrites over three resaves.

Core also supports exact `decimal` custom properties represented by canonical decimal strings. Fresh PPTX output uses `vt:decimal`; explicit import and source-value save profiles are documented in [ADR 0066](../architecture/decisions/0066-exact-decimal-custom-properties.md). `exact-save-v2` requires `scalar-v1`, patches only uniquely bound decimal values, retains unchanged source lexical text and reprojects the candidate. Explicit `exact-save-v3` with `append-and-remove-v4` or `create-and-append-v5` permits exact decimal appends, including custom-part creation, and compatible renames/removals. The profiles without this opt-in continue to reject decimal insertion. An [explicit combined currency and decimal profile](opaque-custom-properties.md) can edit both types in the same source transaction.

Explicit opt-in currency source-value editing is documented in the [currency projection and save profile](opaque-custom-properties.md).

`customPropertySaveProfile: "scalar-v1"` with content projection admits value changes to existing, directly bound custom properties projected as strings, booleans, int32 integers, finite real numbers or canonical UTC dates. Names, types, order, membership and source identities must stay unchanged in `scalar-v1`. The opt-in `scalar-and-name-v2` additionally permits changes to existing bound names, including alongside value edits; types, order and membership remain unchanged. Multiple edits may change atomically. The profile can be combined with core string, slide visibility, starting-number, text-run and chart-value profiles. Drawing name, description and decorative edits require the compatible `mixed-v5` profile. Picture, artwork, field and optional text-inheritance profiles remain excluded. Unmapped properties, comments inside values, complex variants, compatibility-processed parts and overlapping escape-like strings cannot be edited; any unsupported change blocks the entire plan. Unchanged unknown and opaque properties remain in their source part. The profile exposes the same raw source inventory as `customPropertySourceProfile`; entries that also map uniquely to Core include `projectedIndex`. A bound entry or index is not itself a guarantee of a valid plan.

Canonical source integers of types `i1`, `i2`, `i4`, `int`, `i8`, `ui1`, `ui2`, `ui4`, `uint` and `ui8` project when their value fits Core's int32 contract. Edits must also fit the original variant's range; the source tag and identity remain unchanged. Values outside Core's range and noncanonical lexical forms remain source-only. Fresh export uses Core's integer representation rather than preserving an imported variant tag. [Variant tests](../../packages/pptx-parser/test/custom-property-integer-variants.test.mjs) cover both dialects, boundaries, three reopens and overflow refusal. In a [LibreOfficeDev headless comparison](../testing/custom-integer-variants-libreoffice.md), six of ten synthetic variants disappeared from both edited and unedited branches and the remaining four became `r8`; PowerPoint and interactive editing remain unverified.

Canonical finite `r4` source values project only when the JavaScript number is exactly representable in binary32; source saves enforce the same condition on replacements and retain the `r4` tag. Values such as `0.1` that would require binary32 rounding remain source-only or block the edit; negative zero is retained. [Tests](../../packages/pptx-parser/test/custom-property-r4.test.mjs) cover both dialects, binary32 extremes, three reopens and rejected rounding/overflow. This is a deliberately bounded mapping, not support for all valid `r4` lexical forms. A [LibreOfficeDev headless comparison](../testing/custom-r4-libreoffice.md) changed all sampled tags to `r8` and altered the binary64 value of extreme samples; PowerPoint and interactive editing remain unverified.

The source `vt:decimal` variant maps to Core `real` only when its canonical plain decimal text is mathematically identical to the binary64 value, verified with integer arithmetic; for example, `1.25` is admitted while `0.1` remains source-only. Replacement values must satisfy the same exactness rule and serialize as plain decimal text. Noncanonical forms, negative zero and values whose JavaScript representation uses exponent notation remain source-only or block edits. The source tag and ID are preserved, while fresh export uses the Core real representation. [Tests](../../packages/pptx-parser/test/custom-property-decimal.test.mjs) cover both dialects, precision loss, unchanged neighbors and three reopens; [Paired LibreOfficeDev](../testing/custom-decimal-libreoffice.md) and [PowerPoint](../testing/custom-decimal-powerpoint.md) experiments each lost all decimal properties in both edited and control samples; this observation is limited to the synthetic fixture. Interactive property editing and other files remain unverified. The [Open XML SDK reference](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.varianttypes.variant?view=openxml-3.0.1) identifies `decimal` as a variant type.

Existing `bstr` basic strings also map through the same conservative Unicode and literal-escape rules as `lpwstr`; source edits retain the original tag. The [Open XML SDK reference](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.varianttypes.vtbstring?view=openxml-3.0.1) describes the Unicode string and escape representation. Encoded control characters, linked values and ambiguous overlapping escapes remain source-only. [Tests](../../packages/pptx-parser/test/custom-property-bstr.test.mjs) cover both dialects and three reopens. A [LibreOfficeDev headless comparison](../testing/custom-bstr-libreoffice.md) retained the sample XML text but converted the type to `lpwstr` and reassigned IDs; PowerPoint and interactive editing remain unverified.

Existing `lpstr` values use the same bounded Unicode and escape handling; source edits retain their tag. [Parser tests](../../packages/pptx-parser/test/custom-property-lpstr.test.mjs) cover both dialects and three reopens, and CLI/browser tests cover the public paths. A [LibreOfficeDev headless comparison of a PPTKit source save](../testing/custom-lpstr-save-libreoffice.md) retained the sampled XML text but converted types to `lpwstr` and reassigned IDs; the source was synthetic. PowerPoint and interactive editing remain unverified.

Existing `date` values use the same bounded UTC representation as `filetime`: seconds and fractional forms that are exactly representable in milliseconds, with `Z` or an explicit offset up to ±14:00, project to Core UTC dates. Unchanged source values retain their original lexical text; an explicit edit writes a canonical UTC replacement and preserves the original type tag. Unknown offset `-00:00`, local times, nonzero sub-millisecond precision, invalid dates and UTC results outside four-digit years remain source-only. The Open XML SDK describes both [`date`](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.varianttypes.vtdate?view=openxml-3.0.1) and [`filetime`](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.varianttypes.vtfiletime?view=openxml-3.0.1) as date-time variants. [Tests](../../packages/pptx-parser/test/custom-property-date-variant.test.mjs) cover both dialects, offsets, three reopens, mixed edits and invalid values. In [LibreOfficeDev headless UTC](../testing/custom-date-variants-libreoffice.md) and [offset](../testing/custom-date-offset-libreoffice.md) comparisons, both types lost fractional seconds and `date` became `filetime`; PowerPoint and interactive editing remain unverified.

A [separate fractional-form comparison](../testing/custom-date-fraction-libreoffice.md) found the same loss of nonzero fractions in one- and two-digit samples and a trailing-zero sample; its zero-fraction sample retained the second-level instant.

The writer verifies raw property/value ancestry, source text, closure, budgets and candidate reprojection. Tests cover both OOXML dialects, three save/reimport rounds, exact non-target part bytes, opaque neighbors, mixed edits including chart/workbook and drawing properties, cancellation, stale plans, limits and explicit failure of structural changes. A [LibreOfficeDev headless control and three-resave observation](../testing/custom-property-save-libreoffice.md) covers one five-value edit; PowerPoint and native UI behavior remain unverified.

For `scalar-and-name-v2`, a rename patches the existing name attribute and independently verifies property/value ancestry. Decoded-name collisions or a collision with an unprojected source property block the edit. A simple encoded source name is reserved after one escape-decoding pass, so unrelated renames remain available. Ambiguous overlapping escape forms still make all renames in that part unavailable; bound value edits remain possible. The v2 source report marks rename eligibility with `nameEditable`. The CLI exposes rename through its opt-in v2 custom-property manifest. A [LibreOfficeDev headless control and three-resave observation](../testing/custom-property-rename-libreoffice.md) covers one rename plus value edits; PowerPoint and interactive behavior remain unverified.

`customPropertySaveProfile: "remove-v3"` adds explicit deletion of already-bound projected properties. Remove those entries from `document.metadata.customProperties` (use an empty array to remove the last one), then pass their exact `sourceObjectId` values from `customPropertySources` as `customPropertyRemovals` to `prepareSave({ mode: "edit", ... })`. The explicit IDs decide which original elements are deleted; the remaining Core order must match the source after those deletions, apart from separately admitted value or name changes. Unbound or opaque properties cannot be deleted by this profile. The existing custom-property part and relationship remain, even if no mapped properties remain. IDs, other part payloads and unknown source siblings are retained. The profile supports the same compatible mixed transactions as v2, subject to shared guard, work and change budgets. The CLI exposes deletion through its opt-in v3 custom-property manifest.

`customPropertySaveProfile: "append-and-remove-v4"` adds explicit appending to an existing, unambiguous custom-properties part. Append validated Core entries to `document.metadata.customProperties`, then provide their contiguous indexes in `customPropertyAdditions` when preparing an edit. New IDs are allocated from 2 upward while avoiding every source PID, including unknown and explicitly removed properties. Existing IDs and opaque siblings are not renumbered. Explicit deletion followed by reappending the same Core value is also an edit: the reappended source property receives a new ID even when the normalized document is unchanged. An empty existing part is supported; a missing part, compatibility-processed part or ambiguous overlapping opaque name makes insertion unavailable and is reported by `customPropertyInsertion`. The profile may combine explicit additions, removals, supported value/name edits and compatible other edit profiles. The CLI exposes appending through its opt-in v4 manifest. V4 does not create a missing part or support arbitrary insertion positions; the conservative bounded serializer may reject inputs that exceed its serialization budget.

The parser's opt-in `customPropertySaveProfile: "create-and-append-v5"` also permits appending when the source has no custom-properties part. It allocates a collision-free part and root relationship, rejects ambiguous raw package relationships, and checks the candidate package and reimported document before offering a plan. The same explicit contiguous indexes and value restrictions apply. Arbitrary insertion positions are still unsupported. The CLI exposes this profile through its opt-in v5 manifest.

For one created-part sample, [LibreOfficeDev headless resaves](../testing/custom-property-create-libreoffice.md) retained the five tested values over three rounds while rewriting IDs and one type. PowerPoint and interactive editing remain unverified.
