# Table region style authoring

`TableElementInput.style?: TableStyleInput` provides a format-independent table cascade: whole-table defaults, alternating row/column bands, first/last rows and columns, four corners, outer/interior borders, and cell text defaults. It composes with existing local cell styles and named text presets. Normalization resolves it once into effective cells; Layout, SVG and PPTX consume the same result. There is no Office GUID, automatic native-style lookup or new document registry.

See the [typed example](../examples/table-style.ts), [ADR0042](../architecture/decisions/0042-table-region-style-materialization.md), [shared border contract](table-borders.md) and [independent native observations](../testing/table-style-evidence.json). This advances AUT-05.1.1. Full native reusable styles, source table-style/theme inheritance and source style writes remain open; [authoring property origins](table-format-origins.md) are now available.

## Rules and exact priority

Each region uses `TableRegionStyleInput`: existing cell `fill`, `stroke`, `borders`, `margin`, `verticalAlign`, `textDirection`, plus `text: { paragraph?, run? }`. `TableBandStyleInput` has positive physical `size` (default 1), `first` and `second` regions. Priority is low to high:

1. Core defaults, then `wholeTable`.
2. Table `borders.outer`, `innerHorizontal`, `innerVertical` as appropriate for each cell's logical outer sides.
3. `bandedColumns`, then `bandedRows`.
4. `firstColumn`, `lastColumn`, `firstRow`, `lastRow`.
5. `topLeft`, `topRight`, `bottomLeft`, `bottomRight`.
6. Cell's named `textStylePreset` (text and applicable frame margin/alignment).
7. Local cell style and local content paragraph/run fields.

All supported properties are merged independently; absent and explicit `undefined` inherit. Zero metrics, false flags, noFill and alpha zero remain explicit. Paint replaces atomically: a new solid paint without opacity is fully opaque, rather than inheriting alpha from the lower paint. Stroke properties merge separately. Within each layer, uniform `stroke` applies to all four logical sides before that layer's sparse `borders`; a later uniform stroke therefore overrides the properties it supplies on inherited edge candidates. Missing stroke properties retain prior edge values. Insets merge by side; scalar margins set all four sides. Text bullet/discriminated union values replace atomically.

The final cell has a normalized uniform stroke and sparse normalized side candidates; omitted sides use the uniform fallback. Shared physical-edge conflicts are then resolved by the existing [Layout rules](table-borders.md#conflict-rules). A local override changes its cell's candidate, not an adjacent cell's candidate; visible/width/dash/upper-left conflict priority still decides the physical shared edge. Region layers are not an Office table-style cascade or native border precedence emulation.

## Bands, merges and empty cells

Bands use zero-based **physical** row/column anchor positions and positive band size. If `firstRow`/`firstColumn` is present, even `{}`, that first physical line is excluded and body band counting starts at one. A present last-row/column region excludes an anchor starting on the final physical line. Omit a first/last rule to include that line in ordinary band counting. Band selection uses the merged anchor's starting position; it is never averaged across covered slots.

First/last/corner regions apply when a merged rectangle **touches** their physical boundary. A merge spanning the whole table can match all four corners; fixed priority makes bottomRight last. One-row/one-column tables use the same rule. A merged cell remains one content/fill owner; conflicting region styles do not split its body. Its internal grid lines remain hidden. The outer/interior table-border roles are selected from the full merge rectangle, not the anchor's single physical slot.

Normalization materializes omitted, unoccupied slots as empty unit cells so blank areas participate in fills/bands/borders. It never duplicates merged content. Styled tables therefore may contain more canonical cells than their authoring rows. They gain no invented stable source cell IDs. Explicit empty content arrays or zero-run paragraphs receive an empty styled run so their text defaults remain representable. The authoring input stays frozen/detached and compact; only the canonical output is materialized. Tables without `style` retain the existing path and defaults.

`editTable` retains the root style rules and recomputes bands/boundaries on the next normalization after insertion/deletion/merge/split. It does not freeze the old band fill onto newly inserted cells. Existing local styles still follow editTable's content/anchor rules. Layout sizing and pagination operate on already resolved styles: repeated headers and source body rows retain their effective source formatting, rather than restarting stripes or applying the original lastRow to every fragment. No implicit page-specific continuation style is introduced.

## Theme, ownership and transport

Colors and font families can retain existing semantic theme roles. Copying the same authoring table into another presentation resolves its roles against that presentation; direct RGB/font overrides remain fixed. No new mutable theme setter or native table-style registry is added. Text shaping/font substitution remains outside Core.

`NormalizedTableElement.styleSource?: "materialized-regions"` records that effective cell formatting came from authoring rules. It is an origin marker, not property-level provenance or a saved rule definition. The normalized table contains no unresolved `style` object. JSON/IR/Layout retain the marker and effective cells. SVG renders effective cells/shared edges normally.

Fresh native PPTX writes effective direct cell properties and theme references. Located `table-style-materialized` warns that reusable region rules are absent from the native file. Subsequent native row insertion or native style editing is not promised to reproduce authoring-rule reevaluation. Fresh reimport produces direct cells and cannot recreate original regional rules. Three RGB fresh rounds retain effective fills/text/margins/spans/shared edges, not the source authoring abstraction. Native table style authoring/import and source-preserving style writes require their separate gates. Parser continues to block adding these rules to an imported source during an edit save; restoring the baseline allows no-op retry.

## Validation and resource policy

The new region grammar is closed: unknown regions/keys, invalid paints/strokes, arrowheads, unsupported text flags/alignment/fonts, negative/nonfinite metrics, malformed records and invalid band sizes produce located `invalid-table-style` diagnostics. `normalizePresentation` fails with the existing `PresentationValidationError`, without changing authoring state or emitting a partial canonical document.

Styled tables require nonempty rows/columns and at most **100,000 physical slots per table**. This fixed cap is checked before ownership-grid allocation. Band size is a safe integer in `1..100000`. The compact-grid proof rejects overflowing/overlapping rectangles; omitted unoccupied slots become blanks. Ownership, blank materialization and rule traversal are linear in the bounded slots/cells with a fixed number of regions per anchor. Validation and normalization perform their own detached proof. This is per-table accounting, not a total-document or hard peak-memory budget. Downstream Layout's separate cumulative border limits still apply; very wide tables may need explicit edge-limit settings even when their Core slot count is valid. Normalization is synchronous and owns no timers/resources/cancellation handles.

## Verification

- [Eight Core groups](../../packages/core/test/table-style.test.mjs): priority/property composition, explicit zero/false/alpha, physical bands/exclusions, degenerate corners, two-dimensional merges, implicit blanks, presets/rich paragraphs, detach/undefined/restore/edit recomputation, closed grammar and exact slot boundary. 160 independently partitioned rectangles compare effective fills against a separate geometric region-selection oracle.
- [Four cross-package groups](../../scripts/table-style-parity.test.mjs): three RGB fresh/source-no-op rounds, Node/ESM/global canonical equality with blocked network, independent Chromium DOM native/preview cell fill/text properties, semantic theme roles across two presentations, edit/sizing/pagination integration and source-rule mutation rejection/restoration. Installed runtime/declaration consumers exercise the public region/band types and native-ID rejection.
- [Independent runner](../../scripts/inspect-table-style.mjs): Python ZIP/ElementTree verifies every source anchor's effective fill/text/run flags/font size/color and margins, and rejects deliberate fill corruption. The recorded named LibreOffice headless resaves retain fill/text in RGB, theme and structurally edited scenes. Saved PDFs retain required header/body/control text; RGB/theme PNGs have been visually inspected. This evidence covers **fill/text observations only**. It does not certify border segmentation, strict width/alpha/transform fidelity, native rule retention or interactive editing. The previous shared-border native limitations remain in force; the displayed merged boundary still illustrates producer-specific segment behavior.

Cells and regions may specify `textDirection: "horizontal" | "rotate90" | "rotate270"`; omission preserves the previous horizontal default, and explicit horizontal can override a region. PPTX emits DrawingML [`tcPr/@vert`](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.tablecellproperties.vertical) (`horz`, `vert`, or `vert270`); direct cell attributes in those forms are imported. Other native direction values remain source-owned and are reported. SVG previews use sideways CSS writing modes and emit `table-text-direction-approximation`: glyph orientation, margin, line wrapping and Office fidelity are not guaranteed. Tables with rotated text use resolved physical cell geometry to prevent HTML table expansion from clipping text; a frame/grid mismatch emits `table-text-direction-frame-grid-mismatch` and clips to the authored frame. Chromium tests check run rotation and both renderer cell paths; tests also cover three fresh export/import rounds and three source-preserving text edits; One [PowerPoint 16.104 observation](../testing/table-text-direction-powerpoint-evidence.json) covers horizontal and both quarter-turn directions through one save/reopen, with screenshot glyph masks and XML checks. PowerPoint removed an explicit `horz` attribute in that sample; shared-style override semantics, broader rendering and interaction are not yet verified. Layout can estimate quarter-turn bounds by rotating horizontal measurements, with a `table-text-direction-measurement-approximate` warning. A fixed-font Chromium test compares two unwrapped Latin samples against SVG glyph bounds within 6 logical points; it is not native Office parity evidence. Automatic table row sizing uses the unwrapped horizontal extent as a conservative row-span height and remeasures at the resolved height, reporting `table-text-direction-sizing-approximate`. When the unwrapped extent exceeds a finite row-span maximum, Layout tests wrapped text at that maximum, probes up to 16 intermediate heights and verifies the selected result; failures preserve authored geometry unless the existing explicit clip policy applies. It does not guarantee the smallest fitting wrapped height.

AUT-05.1.1, AUT-05.1.2, IMP-06.1.4/.5 and IMP-09 remain open at full scope. Source theme/table-style cascade, named native styles, broader geometry/content origins, additional vertical and bidirectional text modes and native-interaction evidence remain requirements. [Authoring formatting origins](table-format-origins.md) now cover this model’s supported cell fields.

Source import now has a separate [direct-region profile](table-style-import.md) for selected source definitions and theme dependencies. Its native region order is deliberately independent of this Core custom authoring policy. Style-matrix/default appearance, full native reuse and source style writes still remain open.

### Native first-row toggle

`nativeFirstRowStyle` is a table-level Boolean separate from the Core `style.firstRow` formatting rules and `headerScope` cell roles. Authored tables continue to export with the native toggle enabled by default. Set it to `false` to write `firstRow="0"`. Content import maps explicit true/false and the DrawingML default (off when omitted). Unrecognized lexical forms remain source-only. A fresh export retains the Boolean meaning; a no-op save preserves the original spelling or omission. The toggle is not a source-edit target and does not change SVG styling or imply accessible per-cell headers. See the [native experiment](../testing/powerpoint-table-header.md).

The remaining native switches are available as `nativeTableStyleFlags: { firstColumn, lastColumn, lastRow, bandedRows, bandedColumns }`. For authored tables, banded rows remain enabled by default and the other four switches default to off. Content import records the DrawingML effective Boolean values (omitted attributes are off); a fresh export writes those values without preserving their lexical form. The [DrawingML table properties](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.tableproperties?view=openxml-3.0.1) are separate from the Core region definitions. The flags do not change SVG cells, retain an arbitrary source style ID or provide a source-edit target. SVG emits `native-table-style-flags-not-rendered` for nondefault native switches. A [PowerPoint save/reopen](../testing/powerpoint-table-header.md#additional-table-style-switches) confirms a mixed switch state.

### Named native preset references

Set `nativeTableStylePreset: "medium-2-accent-1" | "medium-2-accent-2"` to select a verified PowerPoint gallery reference. The default remains Accent 1. PPTX exports the selected reference and retains existing direct cell formatting; direct overrides can mask the preset's colors, borders or text. This option does not embed the preset's definition. Export reports `native-table-preset-direct-formatting` so consumers can distinguish the reference from a guarantee of native preset appearance. SVG uses effective Core cells rather than applying native themes or rules, and reports `native-table-preset-not-rendered` for Accent 2.

Content import maps either name only from an explicit reference with no resolved definition for that ID. An embedded definition takes precedence even if its ID matches a known preset; an inactive definition with the same ID also blocks preset inference; unrelated compatibility markup does not; its supported effects materialize as before. Unknown IDs and arbitrary native definitions stay source-owned. Changing this field is not a preservation edit. See the [native preset observation](../testing/powerpoint-table-preset.md).
