# Asset identity, replacement and cleanup

Core provides explicit method-managed asset operations. They operate on the known authoring graph and do not fetch resources, rewrite source PPTX packages or infer references from custom JSON. See the [typechecked example](../examples/asset-lifecycle.ts) and [byte source contract](byte-assets.md).

## Optional content matching

`registerAsset(input, { deduplicate: "content" })` searches existing byte assets for exact canonical byte content **and matching metadata** before allocating a generated ID. Raw Uint8Array and equivalent Base64 compare identically. MIME hints, dimensions, accessibility and dedupeKey must match; differences produce separate assets unless an existing explicit ID/dedupe identity requires a conflict error. MIME case and explicitly different optional values are not normalized for matching. Object property insertion order does not affect known metadata equality.

Explicit `id` always wins: content matching never substitutes another identity for an explicit ID. Existing `dedupeKey + source` registration semantics still run first, including metadata conflict checks. Omitting the option preserves default registration behavior. URL/path sources are never loaded or merged by byte equivalence. This is exact comparison without hash collision assumptions; it scans registered candidates and is not a global content-addressed store. Registry changes immediately affect future matching; there is no stale content cache.

## Atomic batch registration

Factory-created `ManagedPresentationDocument` instances expose `registerAssets(requests)`, where each request is `{ asset, options? }` with the same input and deduplication rules as `registerAsset`. Requests are evaluated in order against a staged registry, so later items may reuse an earlier batch item. The returned frozen array follows request order and can contain the same asset more than once. An empty batch returns an empty frozen array.

If any item fails, no batch item is committed and generated ID allocation remains unchanged; callers may correct the input and retry. The batch detects reentrant registry mutation by getters and rejects instead of overwriting it. Such caller-initiated side effects are not rolled back. Existing asset handles and previous collection snapshots remain valid. Inputs are captured synchronously as each request is processed, including copying raw bytes. The stage shares already-frozen assets and allocates a separate registry; matching can scan the registry repeatedly and has no separate work or peak-memory bound.

The batch is an additive managed-document capability; custom implementations of the base `PresentationDocument` contract do not acquire a required method. It is a prerequisite for cross-document resource reconciliation, not a cross-document slide transfer or a source-package preservation operation.

## Copy assets between documents

`destination.copyAssetsFrom(source, ids, { deduplicate, external })` copies explicitly selected Core assets into a different managed destination in one atomic batch. `ids` must contain distinct nonempty source IDs; the source inventory must have unique identities. The frozen result is ordered like `ids` and contains `{ sourceId, destinationId, reused }`. A reused destination can have existed before the call or been created by an earlier item in the same batch. Source IDs are not copied as destination IDs; a generated ID avoids destination collisions. Existing source and destination snapshots remain detached, and later source replacement or removal does not change copied bytes.

Both policies are mandatory. `deduplicate: "registry"` uses ordinary registration behavior, including existing `dedupeKey` identity rules; `"content"` additionally reuses exact byte-and-metadata matches. Explicit source IDs do not prevent content matching because they identify the source, not a requested destination ID. Conflicting dedupe metadata rejects the whole batch. `external: "reject"` rejects path or URL sources; `"preserve"` copies their strings without reading them. A preserved relative path is interpreted by a later consumer in its own environment and may not refer to the original file. No network or filesystem access occurs during copying.

Unknown asset/source/accessibility fields, symbol keys and non-enumerable fields reject before cloning or committing any copied resource, including fields added by getters during capture. Invalid or duplicate source IDs, missing assets, unsupported sources and conflicts also reject. Destination registry changes caused by reentrant getters during capture reject; caller-initiated side effects are not rolled back. Custom `PresentationDocument` implementations must supply stable source snapshots while their asset inventory is read. The operation does not rewrite slide/image references, copy layout or theme, interpret custom metadata, migrate opaque PPTX content or provide source-preserving save permission. Those cross-document transactions remain open.

Export has a separate opt-in `deduplicateResolvedAssets: true`. After each asset is independently resolved and checked, the exporter can share package media parts when the resolved base bytes, extension, normalized MIME and optional SVG pair bytes match exactly. This works across byte, path, URL and explicit resolver sources, does not merge Core assets or element metadata, and emits diagnostics separately for each asset. Different SVG pair bytes never share, even when their fallback bytes match. Each source is still resolved and charged against its own asset budget; this option does not reduce reads or resolver calls. A non-cryptographic fingerprint only selects candidates: full byte comparison decides equality, including when fingerprints collide. Work is synchronous after resolution and is not preemptible during comparison. Default export behavior remains unchanged, and this fresh-output optimization does not deduplicate or garbage-collect opaque imported package resources.

A [named LibreOfficeDev probe](../testing/resolved-media-dedup-libreoffice.md) checks shared red and distinct blue media across two pages, a layout and a master over three headless saves. It records an ownership change by LibreOffice rather than assuming that the application preserves the authoring structure.

## Full replacement

`replaceAsset(assetId, replacement)` returns a new frozen asset under the same ID and registry position. `PresentationAssetReplacement` contains the same fields as registration except `id`; specifying an ID at runtime rejects. It is a full replacement, not a patch: omitted dimensions, MIME, accessibility and dedupeKey are removed. Unknown target IDs, invalid byte sources and cloning failures reject before this operation changes the registry. If caller getters replace/remove the target during input capture, the outer replacement rejects rather than overwriting the newer value; caller side effects themselves are not rolled back.

Every image using the ID sees the new asset on subsequent normalization/render/export. Existing asset handles, collection snapshots, normalized documents, SVG strings and PPTX byte outputs remain detached previous results. Input source getters are captured once, raw buffers are copied, and no mutable source aliases enter stored state.

Element boxes, crop fractions, transforms and IDs remain unchanged. Layout resolves contain/cover again using new declared source dimensions, so visible fitted geometry can change. This API does not implement per-image replacement policies, EXIF orientation correction or automatic crop retargeting; those remain AUT-04.4. Replacing a shared asset deliberately changes all its uses. To change one use, author a separate asset and replace that image element through existing element operations.

## Per-image replacement plan

`planImageReplacement(image, targetAsset, policy)` returns detached, deeply frozen `replacement` and `previous` image inputs without modifying the document or either asset. Pass `replacement` to the owning slide's `replaceElement` to change that one image; pass `previous` to restore it. This snapshot is not a concurrency-aware undo transaction: check that the target and element are still current before committing or undoing. Other images referencing the old asset are untouched, and neither asset is removed. The caller must ensure the target asset belongs to the destination document; planning does not register it or inspect unknown package references.

The explicit `fit` policy chooses behavior:

- `preserve` retains the authored frame, fit and crop fractions. This preserves fractions, not necessarily the same visual content when the new image has a different aspect ratio.
- `stretch`, `contain`, or `cover` retains the authored frame, clears the old crop and uses that fit. `contain` and `cover` require positive finite target dimensions and frame dimensions with finite nonzero aspect ratios. Layout later resolves them from the target's declared dimensions.
- `size` takes positive finite `width` and `height` in presentation coordinate units, keeps the authored top-left position, clears crop and uses stretch. It does not infer a physical or pixel-to-slide size.

A [cross-package test](../../scripts/image-replacement-parity.test.mjs) exercises one transparent PNG replacement with `contain`, confirms an unchanged shared image and preview pixels in Chromium, checks fresh PPTX output and content import, and verifies undo. In an imported session even the text edit profile blocks the image mutation; after undo and removing the newly registered asset, no-op save returns the original bytes. This is not an image-edit preservation writer or a native transparency test.

`planVisibleImageReplacement(document, slideId, elementId, targetAssetId, fit)` from `@pptkit/layout` is the alternative when the current **resolved** image frame is the intended replacement frame. It resolves the current document at invocation, selects a top-level slide image and registered target asset, and uses the resolved box in the replacement plan. An optional sixth argument `{ composition }` captures and applies the supplied composition rules before image fitting; any layout diagnostic blocks the plan instead of accepting a partial result. It rejects a nonpositive resolved frame and an original `contain`/`cover` whose dimensions or frame leave the fit unresolved. `preserve` carries the resolved fit and crop fractions; `stretch`, `contain` and `cover` reset crop as above. For `contain`, the new visible image may be smaller inside the preserved frame. The previous snapshot retains the original authored image, so undo restores authoring rather than freezing the resolved box. The composition result is a geometry snapshot, not a persistent rule or an update to other elements: applying the same composition again after committing can reposition or resize the image again. Pagination, intrinsic/table sizing and inherited master/layout objects require separate handling. Check document freshness before applying or undoing either plan.

For an image nested inside a slide-owned group, `planNestedVisibleImageReplacement(document, slideId, imageId, targetAssetId, fit, options?)` returns `rootElementId` and detached, deeply frozen whole-group `replacement` and `previous` snapshots. Commit or undo with the slide's `replaceElement(rootElementId, snapshot)`, retaining sibling elements and identities. The resolved box is in the immediate parent group's local coordinates, not slide-wide axis-aligned visual bounds; existing parent scaling, rotation and flips remain on their authored groups. Optional composition may position the image within its group. By default, a changed ancestor group frame or transform rejects because committing only the image would not reproduce its composed position. Explicit `commitAncestorGeometry: true` instead includes changed ancestor frames, coordinate sizes and transforms in the group snapshot and reports their IDs in `committedAncestorIds`, outermost first. This also changes the screen positions of sibling descendants; review the whole group before committing. Other composition changes to siblings are not committed. As with the top-level plan, reapplying composition later can change the result and the caller must guard against stale state. This does not support inherited master/layout groups or preservation-aware package writes.

A [named LibreOfficeDev probe](../testing/nested-image-composition-libreoffice.md) follows a nested replacement, sibling and unselected-page control across three headless saves. It records correct sampled colors and media relationships as well as application-written group transform changes and geometry drift.

For ordinary artwork owned by a shared master or layout, `planSharedVisibleImageReplacement(document, { kind, id }, imageId, targetAssetId, fit, options?)` returns a discriminated plan with complete detached `previous` and `replacement` definition snapshots. Apply them through `replaceSlideMaster` or `replaceSlideLayout` using `ownerId`. The definition is shared: the edit affects every page that displays its artwork, subject to visibility switches; it does not create per-slide copies. Both direct and group-nested images are supported in their owner-local coordinates. The same composition, unresolved-fit, optional ancestor geometry and stale-plan rules apply as for slide-owned plans; committing ancestor geometry can move siblings on every affected page. Definition replacement validates affected references through Core; this planning API does not automatically commit, alter unknown native content, or provide source-preserving PPTX edits.

A [named PowerPoint slideshow observation](../testing/master-image-replacement.md) covers a generated shared-master transparent replacement on two visible pages, one hidden-inheritance page and another-master control. A separate copy also underwent one native master-picture crop edit and save/reopen. This does not establish source-preserving replacement or semantic import of the master image.

The image frame and any existing crop are validated before a plan is returned. Source pixels, EXIF orientation and ICC profiles are not decoded or transformed; dimensions are caller-declared. A resolved visual frame may differ from the authored frame under contain/cover, so a caller wanting to preserve that specific visible rectangle must supply it deliberately before planning. The plan applies to a standalone image input; nested groups or master/layout definitions require their owning replacement operation. Image replacement in an imported PPTX remains subject to the parser's separate preservation-save capabilities.

As with existing registration, general semantic metadata validation remains `validatePresentation`/normalization's responsibility. Replacement does not decode images or certify source dimensions.

## Reference inventory

`getAssetReferences(assetId)` returns a frozen detached array of readonly `AssetReference` records: asset ID, element ID, authoring path and slide ID or layout ID. Ordering is slide order with depth-first element order, followed by layout definition order. Paths identify the current array position; stable IDs remain available after reordering.

Hidden slides/elements, nested groups and **all** reusable layout and master definitions count, even when a layout is not currently used. Inherited layout/master uses are reported once at their authoring definition rather than expanded once per slide. Querying an unregistered ID can still locate dangling image references. Custom-data strings, external consumer state and unknown format content are not interpreted as asset references.

## Explicit removal and cleanup

`removeAsset(assetId, { retainAssetIds? })` returns the removed frozen asset. It rejects unknown IDs, known image references and explicitly retained IDs; it does not delete referencing objects or offer a force flag. After removing all known uses, the ID can be explicitly registered again. Generated IDs remain allocator-owned and are not promised to be recycled.

`removeUnusedAssets({ retainAssetIds? })` removes only entries with no known image reference and no caller-specified retention, returning a frozen array in original registry order. It is explicit; deleting a slide or element never silently removes assets. Repeating cleanup without new changes returns an empty array. The keep-list is per operation, not persistent state; callers must supply it each time.

Both removal operations validate the complete keep-list before mutation. Duplicate retained IDs are allowed; unknown IDs, non-string entries, non-array lists and unknown option keys reject. This catches retention typos before removing anything. No asset is removed when this validation fails. Previously returned immutable snapshots remain usable after removal.

## Preservation boundary

Core cleanup is **not** a PPTX garbage collector. A format-aware consumer must supply Core IDs used outside the known authoring graph, or avoid cleanup when it cannot enumerate them. Source package parts/relationships are not Core IDs and must not be passed as a substitute. Parser preservation closure and copy/delete reconciliation remain format-layer responsibilities under IMP-07/09.

Current structural import sessions retain original bytes privately. Adding/replacing/removing Core assets never deletes those original parts. Save-plan freshness compares normalized state: added assets invalidate no-op plans, and exact cleanup restoring the baseline permits their reuse. This proves lifecycle integration with current no-op semantics; it does not prove safe edit-aware preservation of arbitrary unknown objects.

## Evidence and compatibility

[Core lifecycle cases](../../packages/core/test/asset-lifecycle.test.mjs) cover reference traversal, full replacement, stale snapshots, atomic failures, reentrant mutation, retention and content matching. [Export tests](../../packages/pptx-exporter/test/assets.test.mjs) verify that replacing PNG with GIF updates media names, content types and shared relationships without retaining stale parts. [Preview tests](../../packages/svg-renderer/test/byte-assets.test.mjs) verify changed fitted geometry and detached old results. Browser tests actually decode the replacement GIF, and installed consumers exercise the public methods/types. Parser session tests cover freshness and baseline restoration.

These are additive document methods. Consumers implementing the `PresentationDocument` interface themselves must implement the new methods. No IR version change, new package, runtime dependency or implicit I/O is introduced. Automatic preservation closure, cross-source resource resolution, cross-document remapping and richer image-edit policies remain separate work; AUT-04 is not complete as a whole.

Master image references add `masterId` and actual master/group paths. Hidden and unused master artwork protects resources through the same lifecycle; see [master ownership](master-artwork.md).
