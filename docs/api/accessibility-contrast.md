# Conservative text contrast observations

`inspectSlideTextContrast(document)` normalizes and validates an authoring document, then returns frozen observations for nonblank text runs visible on each modeled slide, including inherited text. It does not mutate the document. Findings contain slide/element IDs, normalized definition path and indices. Inherited occurrences include a frozen `source: { kind: "master" | "layout", id }`; a shared definition can have different results on different slides. Results follow slide order, then master, layout and local drawing order. Results do not contain the text itself. Invalid documents throw `PresentationValidationError`. Optional `maxFindings` accepts a nonnegative safe integer; exceeding it throws `TextContrastLimitError` without returning a partial report.

<!-- doc-test: docs/examples/accessibility-contrast.ts -->
```ts
import { inspectSlideTextContrast, type PresentationDocument } from '@pptkit/core';

export function reviewTextContrast(document: PresentationDocument) {
  return inspectSlideTextContrast(document).findings;
}
```

The calculable case is a foreground text object, no event timeline, full object opacity and a uniform resolved color behind the text. Visible artwork behind it may consist of text-free, unrotated, full-slide solid rectangles without visible strokes or shadows. They are composited in master, layout and slide drawing order. Each uses its owning theme. An opaque cover establishes a known field even over a gradient; translucent covers require a known color behind them. A single shape's text can also be calculated when its fill is absent, fully transparent, or exactly matches the background, and it has no visible stroke or shadow. An unrotated solid rectangular shape whose box covers the slide can instead supply its own uniform text background; an opaque fill works over any slide background, while a translucent fill requires an already known opaque color field for composition. Flips preserve the rectangle. Coverage must hold both in authored coordinates and after the PPTX origin, extent and slide size are independently rounded to EMU. A single table's cells qualify when every normalized cell fill is absent or the same color as the background, and every uniform and per-edge stroke is invisible. This includes merged anchors and materialized regional styles; a differently colored fill remains indeterminate even at zero opacity because the legacy SVG table path may ignore fill opacity. These restrictions keep the field uniform across the slide even if text overflows its frame. Theme colors use the slide's effective layout theme. Each run's solid text color is composited over that background in sRGB using its declared color opacity. The implementation converts sRGB channels to relative luminance using the 0.04045 breakpoint and computes `(lighter + 0.05) / (darker + 0.05)` without rounding.

The thresholds follow [WCAG 2.2's text contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html): 4.5 for normal text and 3 for large text. PPTX stores font sizes in points, while the SVG renderer emits the same nominal number in CSS pixels. Therefore the result reports both `nativeThreshold` (18 pt, or 14 pt bold) and `nominalSvgThreshold` (24 px, or 56/3 px bold, at one SVG unit per CSS pixel). The calculation accounts for the serializers' font-size and shrink-scale rounding; `effectiveFontSize` is the unrounded authored size times explicit shrink scale. `ratio` uses declared text and shape-fill opacities; `nativeRatio` uses their PPTX rounding to 1/100000. If the nominal output decisions differ, the result is `indeterminate` with reason `output-size-dependent` when thresholds differ, otherwise `output-opacity-dependent`; both ratios and thresholds remain available. If both agree on pass/fail, `threshold` is the stricter one. Actual SVG embedding, zoom, fonts, native autofit and display settings can change effective size; these nominal comparisons do not assert WCAG conformance or actual device-rendered pixels.

An observation is `meets-threshold`, `below-threshold`, or `indeterminate`. A foreground object can also sit inside nested translation-only groups. Each group must have full opacity, no rotation or flip, matching box and child coordinate extents, and exactly one visible child. A visible decorative sibling still counts as paint. A shape inside a group cannot establish a slide-wide field using its local coordinates. Partial covers, nonuniform artwork, paint above the text, other grouped text, object opacity, unresolved backgrounds and event timelines remain indeterminate. The check does not approximate the bounds of glyphs or infer geometry for partial overlaps. The modeled slide `showInheritedShapes: false` suppresses layout and master artwork, and layout `showMasterShapes: false` suppresses master artwork only; the background remains independently resolved. Other shape and table-cell text is reported indeterminate under `unsupported-text-owner`. Hidden slides/elements and decorative subtrees are excluded, as are blank runs. Chart labels, text in images, alternate slide states, actual font substitution, text effects and native renderer differences are not assessed. A clean result does not imply complete coverage or accessibility. The returned paths identify the normalized representation, so recapture them after changes.

[Core tests](../../packages/core/test/accessibility-contrast.test.mjs) cover RGB/theme color and alpha, exact threshold categories, shrink, shared layouts and masters, merged cells, regional/edge border controls, unknown backgrounds/owners, hidden content, invalid documents and immutable outputs. Layout/master lookup and eligible shared backdrop layers are built once per inspection; normalization and validation still have their own costs. [Node and browser parity](../../scripts/accessibility-descriptions-parity.test.mjs) exercises public browser exports. A [Chromium pixel test](../../scripts/accessibility-contrast-pixels.test.mjs) compares actual rendered glyph pixels with computed ratios for text boxes, uniformly filled shapes and single-cell tables, using opaque and transparent theme colors on white and dark backgrounds, including a master-specific theme and two translucent layers over a master cover. It also checks the same master text against two slide backgrounds and compares nested translated text to the same text placed directly on the slide, including exact Chromium screenshots and matching PPTX group extents. It is a scoped browser observation, not evidence for other fonts, backgrounds or native apps. ADV-10.1.2 remains open for partial overlaps and general transparent scenes, more text owners, rendered backgrounds and native evidence; reading order and description review remain separate.

For authoring JSON, `pptkit validate deck.json --check-contrast --json` exposes these observations. The [CLI contract](cli-generation.md) specifies its separate optional failure policy, including indeterminate cases.
