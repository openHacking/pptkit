# ADR 0066: Exact decimal custom properties

## Decision

Add a format-independent `decimal` custom-property variant to Core. Its value is a canonical decimal string, not a JavaScript number, currency amount or unit: optional minus, integer digits without leading zeroes, and an optional nonempty fractional part with no trailing zeroes. Zero is `0`; negative zero, signs on positive values and exponent notation are excluded. Input is limited to 10,000 UTF-16 code units. Core validates, snapshots and normalizes this value without numeric conversion. Arithmetic, scale significance, currencies, rounding and units remain outside the model.

Fresh PPTX export maps this variant to `vt:decimal` using the exact canonical text. Existing string, boolean, integer, real and date mappings remain unchanged. Adding a member to the public TypeScript discriminated union can require exhaustive consumer switches to handle `decimal`, even though existing inputs and runtime behavior continue to work.

Parser retains its existing default projection, where only the existing binary64-exact decimal subset becomes a Core real. `customDecimalProjection: "exact-v1"` is a separate content-import opt-in: supported source decimal text is canonicalized with string operations and mapped to Core decimal without rounding. Source lexical text and identity remain in inspection; a no-op save retains original bytes. The `exact-v1` opt-in excludes preservation edit profiles. A separate `exact-save-v2`, paired with `customPropertySaveProfile: "scalar-v1"`, admits value edits for uniquely bound direct decimal sources and reprojections of the candidate without floating-point conversion. It may combine with compatible text-run, core metadata and slide-visibility saves. The separate `exact-save-v3` profile pairs with `append-and-remove-v4` or `create-and-append-v5` to append exact decimals, including by creating a missing custom-properties part, and to rename or remove eligible bound properties. Existing profiles without this explicit decimal opt-in continue to reject decimal insertion. The CLI exposes this profile through an explicit v7 manifest; see [CLI save](../../api/cli-save.md). When `customCurrencyProjection` is also `exact-save-v3`, bound currency and decimal values can be edited together; appending a Core real still creates `vt:r8`, not `vt:cy`. A [typed public example](../../examples/exact-custom-decimal.ts) shows authoring and explicit import.

## Consequences and evidence

A value such as `9007199254740993.0001` survives Core, fresh export and explicit import without binary64 conversion. Canonicalization preserves numeric value but intentionally drops source signs on positive values, insignificant zeroes and surrounding XML whitespace; it is not lexical preservation. A bounded source value outside the opt-in limit remains in inspection. Strict and Transitional fixtures, fresh output, no-op, invalid values, Node file capture and browser parity are covered by [projection tests](../../../packages/pptx-parser/test/custom-property-exact-decimal.test.mjs). [Source-save tests](../../../packages/pptx-parser/test/custom-property-exact-decimal-save.test.mjs) cover three edits and reopens, unchanged source lexical text, mixed transactions, ambiguous sources and stale plans. [Structural-save tests](../../../packages/pptx-parser/test/custom-property-exact-decimal-structural-save.test.mjs) cover creation, appending, renaming, removal and three reopens for both dialects. A [LibreOfficeDev comparison](../../testing/exact-decimal-save-libreoffice.md) of the new exact-decimal source-edit profile also dropped its three sampled decimal properties on first resave; previous [LibreOfficeDev](../../testing/custom-decimal-libreoffice.md) and [PowerPoint](../../testing/custom-decimal-powerpoint.md) observations dropped their decimal samples; this decision does not claim cross-application retention or native interactive editing.
